# Article: Testing Layers and the Gherkin Contract

**Audience:** product, coder, architect - **Read when:** when authoring a .feature, a step module, or an e2e spec; when adding a *.browser.test.ts; in architect CONTRACT mode.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 167-172, 184-203, 209, 211, 213-218. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

### Testing structure (three test layers plus the contract they answer to, deliberately separate)

1. **Unit/property tests** — `src/*.test.ts` and `src/*.property.test.ts` (fast-check via `@fast-check/vitest`) for each of the framework-free modules (`src/equality/`'s own tests are one directory deeper, but land in the same two projects), plus `src/hooks/*.test.ts` (`@testing-library/react`'s `renderHook`) and `src/components/*.test.tsx` (`@testing-library/react`'s `render`/`screen`/`fireEvent`, jest-dom matchers via `src/test-setup.ts`) for the thirteen unit-tested components (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `GridLines.tsx`, `HoverIndicator.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`). These run across three vitest projects, not one (see `vite.config.ts`'s `test.projects`): the framework-free-module tests run under the `unit` and `property` projects in plain Node — no `document`, no jsdom cost — while the hook and component tests run under the `dom` project in jsdom, since only those actually render. A new test file lands in `unit` by default (it's the project that subtracts rather than includes) and fails loudly if it needed jsdom after all. One consequence worth knowing before writing a property test: `property`'s `include` is the bare `**/*.property.test.ts`, which is _not_ rooted at `src/` root, so a `*.property.test.ts` placed under `src/hooks/` or `src/components/` would be collected by both `property` (Node, no React plugin, no jsdom) and `dom`, and fail in the first. That is a feature, not a gap — property tests belong in the framework-free layer, and a hook-resident invariant worth quantifying over is a signal to extract the rule into a module rather than to reach for a config exception. This is where implementation correctness lives — edge cases, invariants, and the numeric precision (`-0` handling, clamp boundaries, same-reference no-ops) that a Gherkin Examples table can't express.
2. **Browser-required unit tests** — `src/**/*.browser.test.ts` (co-located with the module they cover, run by `npm run test:browser` via `vitest.browser.config.ts` — Vitest Browser Mode driving real Chromium, reusing the Playwright binary `npm run test:e2e` already installs). Same kind of test as layer 1, and owned by the same roles (`coder`/`cleaner`/`architect` — never `product`): it imports one module directly and never boots the app. It exists only for contracts jsdom has no faithful equivalent for, currently just `useElementSize.browser.test.ts`, which pins down that the real `ResizeObserver` fires an initial callback from `observe()` itself and delivers an update on a real size change — neither of which the jsdom stub in `src/test-support/domStubs.ts` reproduces (it fires only when a test calls `.resize()`). This layer is **additive only**: `vite.config.ts` excludes the `*.browser.test.ts` suffix, and since `crap4ts`/`npm run test:mutation` both run through that config, neither can see these files. Moving an assertion out of a jsdom test into one of these silently drops coverage and mutation score on the module — always leave the jsdom test in place. See `.claude/agents/articles/engineering.md` for which layer a given test belongs in.
3. **The Gherkin contract — no longer a test layer of its own.** `features/*.feature` (plain-English specs) is `product`'s manifest and the user-facing contract, end to end. It used to have a second executable form beside the browser one — `features/*.steps.test.ts(x)`, step definitions on `@amiceli/vitest-cucumber` run by vitest in Node or jsdom, plus the `features/harness/` modules the jsdom form mounted `<App />` through. **`delete-step-test-layer` removed all of it**: seven step files and the harness, 1,326 lines, the `acceptance` vitest project, and the `@amiceli/vitest-cucumber` dependency. **`features/` now contributes zero tests to `npm test`.** Every `.feature` file is executed exactly once, by playwright-bdd against the step modules in `features/steps/*.ts`, which is item 4 below — read this item as _what the contract is_ and item 4 as _how it runs_. The **suffix** is still what separates the artifacts inside the directory: `.feature` (the contract), `.e2e.spec.ts` (the hand-written Playwright specs) and `e2e-helpers.ts` (their barrel). **There are two subdirectories, and neither holds a test file**: `features/steps/` (the step definitions bddgen compiles the contract against) and `features/screenplay/` (the helper modules the barrel re-exports), both described in item 4. This layer's purpose is the stakeholder-readable, accepted-behavior contract and the `product`→`coder` handoff (see CLAUDE.md's Subagent pipeline section), not incremental defect detection beyond the unit tests — its assertions overlap substantially with the unit tests covering the same functions, and that overlap is expected rather than duplication to eliminate. The one feature that isn't overlap-redundant is `pattern-library.feature`, whose Examples table is the only place the exact cell geometry of all 8 patterns is pinned down — the unit and property tests check names, categories, and the bounding-box anchor convention, but never the shapes themselves.

4. **Black-box e2e tests** — `features/*.e2e.spec.ts` (Playwright, real Chromium, run against `npm run dev` on a fixed 1280×900 viewport), alongside the Gherkin layer in `product`'s one directory. `features/e2e-helpers.ts` is the barrel over the shared helpers, which live one module per Screenplay role in `features/screenplay/`; many pixel-math assertions are derived from the exact default camera (`offsetX: -32, offsetY: -22.5, cellSize: 20`) that results from that fixed viewport, declared once in `features/screenplay/viewport.ts` — read that module's comments before changing default camera values or the viewport size. **A hand-written spec is no longer the browser-level counterpart of a `.feature`, and reading it that way is the mistake `triage-paired-specs` existed to correct.** Since playwright-bdd landed, the browser-level execution of a feature _is_ its generated `bdd` spec — same real Chromium, same viewport, driven by `features/steps/*.ts`. A hand-written spec sharing a `.feature`'s name therefore holds only the **residue**: the part of that feature's subject matter no Gherkin scenario can state. An assertion in it that a scenario already makes is duplication rather than defence in depth, which is what that triage deleted 35 tests and one whole spec file on.

   **Three pairing states, all three normal.** A `.feature` **with** a hand-written spec beside it (`camera-pan-and-zoom`, `cell-life-and-death`, `grid-reference-lines`, `grid-scrollbars`, `mouse-wheel-controls`), holding residue only. A `.feature` **without** one (`appearance-preference`, `generation-control`, `infinite-grid`, `keyboard-grid-navigation`, `keyboard-grid-reachability`, `pattern-library`, `while-the-pattern-library-is-open` — seven of twelve, and the majority state) — this is the _default_ rather than a gap, and says the feature's claims are stated in Gherkin and driven by its generated spec with no residue left over; an absent `.e2e.spec.ts` is not missing browser coverage. And a hand-written spec **with no** `.feature` (`hover-click-agreement`, `hud-layout-and-shortcuts` — two, since `convert-modal-inertness-to-scenarios` restated the third as `while-the-pattern-library-is-open.feature`), whose subject matter is residue end to end — those are specified by `product`'s plain-English outline instead, which each records in its own header comment so the accepted behavior stays written down.

   **What residue is — four categories, and nothing else may be added here.** (1) **Hit-testing and stacking**: which element receives a pointer event where two overlap. (2) The **computed accessibility tree** — what a browser's own accessible-name/description algorithm delivers, as distinct from the attributes it is computed from, which a step module can read for itself and jsdom only reimplements. (3) **Rendered pixel geometry**: a measured box, a pixel coordinate, an element resolved by point. (4) **Native-event delivery** — an event carrying fields no step sends, such as a wheel with both axes populated. **Anything expressible as a `.feature` scenario goes there instead.** **Rendered COLOUR is none of the four, and was adjudicated rather than assumed** (`dark-mode-following-system-appearance`, CONTRACT): category 3 is pixel _geometry_ — a box, a coordinate, an element resolved by point — and a palette is not that. Which appearance is in effect _is_ expressible at domain altitude, so it is Gherkin (that feature states it in seven scenarios); what the palette actually looks like is a judgement the user makes by eye, and per that slice's standing ruling it is asserted **nowhere** rather than pinned in a spec a palette tweak would break. Note this enumeration binds the hand-written `*.e2e.spec.ts` layer only: a screenplay question helper reading a rendered colour for a `.feature` step, as `appearanceInEffect` does, is outside it. A claim that seems to need implementation vocabulary is a prompt to re-read `.gherkin-lintrc`'s altitude rules, not a licence to write it here.

   **Every hand-written test carries a header naming the claim it uniquely holds**, and that header is what licenses the test to keep existing — the `feature-prose-honesty` pattern generalized from `.feature` prose to this layer by `triage-paired-specs`, and the durable form of that triage. The reverse obligation comes with it: a test may not be deleted here without its claim being restated in `features/**`. A deletion resting on **subsumption** — a surviving sibling that happens to make the same claim — rather than on a demonstrated failure is the weak case and must say so in the commit that makes it, because such coverage is usually _incidental_ (it holds only for the sibling's current inputs) and can evaporate later with nothing going red. That is the same failure `ruler-label-axis-affordance` measured one affordance earlier.

   **What the header must record — three things, and the third is the one that stops it rotting.** (a) The **claim**: what this test uniquely holds, in the vocabulary of the product rather than of the assertion. (b) The **channel that does not carry it**, named specifically. "The zoom badge rounds to whole percents, so it cannot see a difference of a tenth of a pixel" is a channel; "category 3" and "no scenario can state this" are not. A category number records which drawer the claim was filed in and licenses nothing — the four categories above are a closed list of where claims have landed, not an argument any one test may borrow. (c) **What would make (b) false** — the invalidating condition, written as a condition someone could later observe: _if the badge ever announces a precise value, this test is redundant_. Note (b) and (c) are what `engineering.md`'s three placement questions produce as a by-product, so a header is cheap to write at the moment the placement is decided and expensive to reconstruct afterwards.

   **An invalidating condition is not a deletion trigger, and the two are opposite instructions to a later reader.** A deletion trigger belongs to a **workaround that owes a payoff** — an ARIA reach-around confined to one function, naming the slice that will retire it — and it invites someone to clear it; the debt is the point. An invalidating condition belongs to a **decision that is correct today** and invites someone to re-check it, not to clear it. A test whose condition still holds is not debt and its header is not a to-do list. (The same distinction is drawn again below, where `rules/no-domain-imports-in-bdd-steps.yml` is recorded as carrying invalidating conditions rather than a deletion trigger, for exactly this reason.)

   **Standing obligation: whenever you edit a file, re-check the header of every test in it.** Headers rot silently and in the licensing direction — a stale one keeps arguing for a test that no longer needs to be here, and nothing goes red. The audit that opened `favor-generated-e2e-in-guidance` read all 33 hand-written tests: 25 were irreducible for stated, still-true reasons, and **seven headers carried a justification that was inaccurate**, most of them true when written. Three decay modes, one example each, the first two re-verified in this slice's DESIGN pass — a **misremembered rule** (a header claiming `.gherkin-lintrc` bans the pixel vocabulary its own scenarios use freely — `camera-pan-and-zoom.feature` and `grid-scrollbars.feature` both say "pixel" in step text; what that config bans is _altitude_ vocabulary, which is a different list); a **capability gained elsewhere** (a header claiming no step sends both wheel axes, after `features/steps/mouse-wheel-controls.ts` had grown a `page.mouse.wheel(sideways, down)` that sends exactly that); and an **argument outliving its subject** (a header reasoning against jsdom, a layer deleted several slices earlier). Note none of the three is discoverable from the test it sits on: each was falsified by an edit to a _different_ file, which is why the obligation is attached to editing rather than to authoring. Those seven are `product`'s to correct, the whole directory being its manifest.

   **Two Playwright projects, one directory, both alive.** `playwright.config.ts` defines `e2e` (`testDir` `features/`, `testMatch` `**/*.e2e.spec.ts` — the hand-written specs above) and `bdd` (`defineBddProject` from playwright-bdd 9.2.0, which compiles `features/*.feature` against the step definitions in `features/steps/*.ts` and writes generated specs into `.features-gen/bdd/features/`). **Every `features/*.feature` generates**: the `pattern-library-steps` slice wrote the step module the last one was missing. Measured with `npm run test:e2e -- --list` on the current tree (`slice/stable-hook-identities`): **33 tests in `e2e` (8 files), 94 in `bdd` (11 files), 127 together in 19 files**, against 11 `.feature` files (measured on `slice/preview-follows-pointer-may-be-statable`; the 41/78/119 this sentence carried before it is that slice's own starting point, not an older tree). The figure this sentence carried until then — 28 / 46 / 74 across 7 files each — is the history the rest of this paragraph reasons from, and every number below it is likewise about the tree it was taken on — the `e2e` figure was 27/73 until `scrollbar-thumb-overflows-its-track` added its thumb-containment test to an existing spec file, which is why the file count did not move with it — `e2e` was **62** tests in 8 files immediately before `triage-paired-specs` cut the hand-written specs down to what the generated `bdd` layer can't reach. `bdd`'s count is untouched at 46, but **not** because that slice left `features/` alone: its VERIFY pass reworded `infinite-grid`'s first scenario and rewrote that feature's step module, taking back the pan-away-and-back claim the triage had deleted a hand-written test for. A reword adds no test — playwright-bdd generates one spec per scenario or Examples row, so only adding one of those moves this figure, and that is the fact to reason from rather than "no `.feature` was touched". **Take 62 rather than the 59 this sentence carried until the `triage-paired-specs` architect review, and don't reconcile it with line 128's 59 — they are two different trees.** 59 was correct until `scrollbar-visible-proportion-affordance` added three e2e tests and didn't recount here, so a figure that was merely stale got re-labelled as history. Three independent measurements say 62: `--list` run against this slice's merge base (`8d36233`), the `61 passed / 1 failed` of the F11 fault run recorded in `features/grid-reference-lines.e2e.spec.ts`, and 27 + the 35 deletions `features/screenplay/elements.ts` counts. Subtracting from 59 instead yields 32 and contradicts all three. `testDir`/`testMatch` sit on the `e2e` project rather than at the config root precisely so the second project cannot inherit a glob built for the first and silently match nothing. **bddgen is all-or-nothing**, which is the standing constraint on adding a feature rather than a fact about any one of them: a single `.feature` with a missing step definition and it exits 1 having generated nothing at all, so a new `.feature` lands together with its `features/steps/` module or the entire `bdd` project stops generating — not just that feature's spec.

   **`.features-gen/` is this repo's first generated artifact. Never edit it, never cite it as source, never commit it.** It is gitignored, Prettier-ignored, oxlint-ignored, and subtracted from `vite.config.ts`'s `sharedExclude` (without that last one vitest's unrooted `unit` include collects the generated specs — measured, 63 files instead of 61). The `.feature` file and its step module are the source; a generated spec has the same status as `dist/`, so a finding in one is a finding in one of its two inputs.

   **Nothing regenerates it automatically, which is why `npm run test:e2e` is the only supported way to run Playwright here.** With `.features-gen/` absent the `bdd` project's `testDir` matches nothing and Playwright reports the `e2e` project alone — `Total: 59 tests in 8 files`, exit 0, no warning (measured before the guard described next existed, back when the `e2e` project held 59 tests in 8 files; `triage-paired-specs` has since cut that project to 27 tests in 7 files, but the guard now refuses to load before this scenario is ever reached again, so the figure is left as the historical measurement it is rather than re-run) — the same failure shape as a Stryker `ignorePatterns` glob matching nothing, a `-t` pattern matching nothing, and a vitest project `include` matching nothing, all documented in `mutation-testing.md`. A **stale** `.features-gen/` is quieter still: playwright-bdd has no staleness detection of its own, so an edited `.feature` runs against the previous generation's spec. `playwright.config.ts` therefore refuses to load when the generated output is missing, empty, or older than any `features/*.feature` or `features/steps/*.ts`, and says which. That check is skipped only during the generation phase itself, which bddgen marks by setting `PLAYWRIGHT_BDD_GEN=1` (playwright-bdd 9.2.0; read as a bare env var because the helper that sets it is not exported from the package index) — without that branch the guard would refuse to load the config bddgen needs in order to clear the guard. bddgen rewrites every output file unconditionally (measured: two consecutive runs on an unchanged tree advance every mtime), so the staleness check self-heals and a spurious fire costs one `npm run test:e2e`.

   **The step registry is global across `features/steps/`, and bddgen is the only thing that checks it.** playwright-bdd loads every step module for every feature, so a step text defined in two modules is an ambiguous-step error rather than an override, and a step text moved out from under a feature that borrowed it is a missing-definition error. Both exit 1 naming the files involved — measured in both directions. The convention that keeps this legible: **a step shared by several features is defined once, in the module the step is _about_.** `camera-pan-and-zoom.ts` owns the camera and zoom steps `grid-scrollbars` and `mouse-wheel-controls` borrow; `cell-life-and-death.ts` owns the grid, generation and cell-state steps `infinite-grid` and `pattern-library` borrow — the latter takes **five** of them ("an empty grid", "a live cell at (<x>, <y>)", "I toggle the cell at (<x>, <y>)", "the cell at (<x>, <y>) should be alive", "the cell at (<x>, <y>) should be dead") — it read "three" until `re-audit-hand-written-e2e-residue` counted them, the toggle and dead clauses having been borrowed since the "next click" scenarios were written and gets them by writing the same text and defining nothing. No import expresses that dependency and none should — `rules/no-domain-imports-in-bdd-steps.yml` forbids a step module importing another, since the sharing is a registry fact and an import would dress it up as a module dependency. **This is the second guarantee riding on the guard above**: skipping bddgen skips the cross-module check as well as the tests, and there is no other. No ast-grep rule can supply it, either — ast-grep matches within a single file and has no cross-file aggregation, and since the shared orientation steps are `RegExp` patterns rather than cucumber expressions, whether two step texts collide is decidable only by cucumber-expressions' own matcher against actual `.feature` text. A homegrown text-uniqueness checker would be answering a different question than the runner does.

   **A step's `Given`/`When`/`Then` keyword is not part of its identity here, and that is a config default rather than a property of the runner.** Read on playwright-bdd 9.2.0's `dist/steps/finder.js`: `StepFinder.findDefinitions` matches by step text alone and filters by keyword only `if (this.config.matchKeywords)` — an option this repo does not set and which has no default, so a step registered with `When(...)` matches from a `Given` position and vice versa. `pattern-library.feature` leans on that: its cancel scenario borrows `keyboard-grid-navigation.ts`'s `When('I press {word}')` from a `Given`, and passes. **The trigger to know about is asymmetric.** Turning `matchKeywords` on makes `StepDefinition.matchesKeywordType` require `Given`↔CONTEXT / `When`↔ACTION / `Then`↔OUTCOME, so that one `Given`-position use becomes a missing-step definition while the `When`-position uses of the same step in the same file are untouched — and because bddgen is all-or-nothing (see the paragraph above), the whole `bdd` project then stops generating rather than only that scenario. So the option is not a tidy-up to reach for when a keyword reads oddly; rewording the step is, and that is `product`'s call. Note the option would also be the only thing that could make two same-text definitions unambiguous, which is why a `Given` twin of an existing `When` is not an available fix today: it is an ambiguous-step error.

   **`features/e2e-helpers.ts` is the single module a step module may import**, mandated rather than conventional: `rules/no-domain-imports-in-bdd-steps.yml`'s allowlist is exactly `playwright-bdd`, `@playwright/test` and `../e2e-helpers`. Anything a step needs that it cannot reach through that module is **added to the `features/screenplay/` module that owns it and re-exported from the barrel**, never imported around. Post-split that is the whole of the instruction that used to read "added there": `e2e-helpers.ts` is now a pure re-export file, so writing a function body in it would be the wrong fix in the other direction. **The mandate was re-asked after the decomposition and re-ratified, and what it survives on is a reason that did not exist before the split** — `barrel-mandatory-for-step-modules` widened the allowlist to `../screenplay/*`, repointed `features/steps/infinite-grid.ts` at the seven modules it reaches, read the cost, and reverted the probe. The argument in full lives beside `rules/no-domain-imports-in-bdd-steps.yml`; the decisive measurement is that **the barrel is a curated surface rather than a full republish** — `features/screenplay/*` exports 92 names and the barrel publishes 80, and the 12 it withholds have no importer outside the layer, nine of them raw `Locator` factories in `elements.ts` (`rulerGroup`, `scrollbarThumb`, `appearanceControl`, `hoverIndicator`, …; only 4 of that module's 13 locator functions are published). Those nine are what make "this module names no selector of its own" structurally true of a step module rather than aspirational, **and a path allowlist cannot express it**: it sees paths and never names, so `../screenplay/elements` is one specifier whether the import pulls the published `cellLocator` or the withheld `rulerGroup` out of it. The "an import states which Screenplay role it depends on" argument fails its own measurement in the bargain — the ten step modules import from a median of **5 of the 7** roles each (`infinite-grid.ts` from all seven), so repointing turns 10 import statements into 45 that answer "nearly all of them". The third option, barrel for the specs and `../screenplay/*` for the steps, is **inverted** rather than merely unsupported: the eight hand-written specs sit at a median of 4 roles, so the step modules are the broader consumer of the two. And widening was separately measured **not** to weaken what this rule mainly does — the anchored single-segment class leaves the `src/` and traversal guards firing — so the ruling rests on the curation alone, and the rule records its invalidating conditions rather than a deletion trigger. The layer is shared with the hand-written `*.e2e.spec.ts` specs — same layer, same rules — and it is where this layer's ARIA reach-arounds are confined whenever one exists. **The confinement is the discipline, and it is general rather than a note attached to whichever one is outstanding**: a reach-around lives in exactly one function, never as an idiom several call sites reach for, and it carries a **deletion trigger** beside it naming the slice that will retire it. **Zero are live.** Both that have ever been filed have now been paid off, in consecutive slices, and in each case the confinement is what made the landing a small edit rather than an archaeology exercise — which is the argument for keeping the discipline, not evidence that it is finished. `rulerGroup` (in `features/screenplay/elements.ts`) and `axisLabelValues` (in `questions.ts`) read a Tailwind edge class until `ruler-label-axis-affordance` added the named `role="group"` they now reach the ruler through, and that landing was the only edit `features/` needed. `thumbTrackFraction` measured the thumb's bounding box against its parent track's until `scrollbar-visible-proportion-affordance` gave the thumb an `aria-describedby` → visually-hidden description of what proportion of the grid is in view; `visibleProportionPercent` (in `questions.ts`) reads that instead. The second payoff was larger than a swap, and that is the part worth generalizing: the pixel read needed a `FILLS_TRACK = 0.99` threshold and a `toBeCloseTo(0.25, 2)` to absorb sub-pixel layout rounding, where an announced integer serves both dependent `.feature` clauses **exactly** — 100 for "fills its track", 25 for "covers a quarter of it" — so both tolerances were deleted with the function. A reach-around's cost is rarely just the one function; it is usually the slack every assertion downstream of it had to carry. **`patternCategoryInLibrary` is deliberately not a third one, and the distinction is the criterion to apply to the next candidate.** It reads the modal's `h3`-then-buttons document order, which _is_ the affordance heading navigation gives an AT user; the `h3` selector is query mechanics (no by-role locator spans two roles, and the interleaving is the signal), not a substitute for something the user cannot perceive. A reach-around stands in for a perception the accessible tree does not offer at all — a paint class, a pixel proportion — and owes an affordance idea named beside it; a structural query for something a user genuinely can perceive owes nothing, which is why that function has no idea filed and should not grow one. Adding `aria-labelledby` to those sections for query convenience was ruled out as a test hook wearing an affordance's name, and would also stop the check exercising what a user actually relies on. **It has been split, and the file survives the split as a re-exporting barrel** — the `screenplay-e2e-decomposition` slice moved its 468 lines into `features/screenplay/`, one module per Screenplay-pattern role: `viewport.ts` (the fixed camera/viewport facts, importing nothing), `notepad.ts` (scenario-scoped scratch state, keyed by the `page` fixture since this suite has no Actors), `elements.ts` (the PageElements — how a thing is reached), `questions.ts` (reads, never asserts), `interactions.ts` (one user act each), `tasks.ts` (goals composed of interactions) and `expectations.ts` (the assertions). The layering under the barrel is a DAG — viewport and notepad import no sibling, elements none either, questions and interactions import elements, tasks imports elements/interactions/viewport, expectations imports elements/tasks — and `rules/no-barrel-import-in-screenplay.yml` keeps it acyclic by making the barrel a sink: a module reaching back through `../e2e-helpers` closes a cycle ESM tolerates silently until a `const` lands in its temporal dead zone. `rules/no-expect-in-screenplay-questions.yml` holds `questions.ts` to its non-assertion contract, scoped to that one file because Playwright's retrying assertion is the sanctioned _wait_ primitive and `interactions.ts` legitimately uses it as one. `e2e-helpers.ts` keeps publishing the names the step modules and specs were already using, each explicitly named rather than an `export *`, so the surface is readable as a list. **No count of them is recorded here, on purpose**: the barrel grows with the layer, and this sentence carried "40 runtime plus `ScrollbarOrientation`" until `barrel-mandatory-for-step-modules` measured 77 runtime plus 3 types — by which point the idea file proposing that slice had itself gone stale twice, at 58 and then 64. Count it when you need it; don't write it down. That retention is what answers the objection this paragraph used to record: the import allowlist above is not widened by a character, and the file stays the single mandated entry point rather than becoming a directory a step module would have to navigate. The other objection — that several exports exist only for the hand-written specs and die with them when those specs are retired, so the split should wait — was measured rather than reasoned about, and did not survive: of the 41 exports the barrel then held, 6 were unused by any step module, and 4 of those 6 survived a rewrite of the paired specs — `patternsButton`, `patternLibraryModal` and `blurFocus` served only the unpaired `hud-layout-and-shortcuts` spec, and `elementAtPoint` served that one as well as three paired ones — so at most 2 (`toggleFarCell`, `rulerGroup`) would die when the paired specs were rewritten. Waiting would have meant writing those rewritten assertions twice.

   **Read that as the argument it was, not as an inventory: every noun in it has since moved, and the conclusion survived all of them.** Re-measured in `favor-generated-e2e-in-guidance` by resolving each name the barrel exports against the names the step modules and the hand-written specs actually **import**, counting no comment mention as a use. `patternsButton` and `patternLibraryModal` have since gained step-module callers in `features/steps/pattern-library.ts`, and `blurFocus` one in `features/steps/keyboard-grid-navigation.ts` (recorded here by `re-audit-hand-written-e2e-residue` for `blurFocus` alone), so none of the three is retired by any spec's deletion. `rulerGroup` is no longer a barrel export at all, and the reason **vindicates the historical claim rather than correcting it**: `triage-paired-specs` dropped the re-export as dead (`2554553`, found with `git log -S 'rulerGroup' -- features/e2e-helpers.ts`) when it cut the paired specs down, which is precisely the death that sentence predicted for it. _Second, harness-style code is test infrastructure and is **not** expected to carry its own unit tests._ **This is the fact that outlived its subject.** The harness is gone, but `features/steps/` and `features/screenplay/` are the same category and inherit the ruling verbatim: they are the `features/`-side peers of `src/test-support/`, which is already excluded from `crap4ts.config.ts` and `stryker.config.json` for exactly this reason, and requiring coverage of it would gate a category this repo has deliberately decided not to gate. That is not the same as unverified — three things check a harness, and a conversion should be able to point at all three: the steps suite going green end to end (which exercises every mount, query and teardown path a scenario uses), `npm run acceptance-mutation`'s per-mutant collected-test-count discipline, and the harness core's own `assertWindowMounted()`, which fails loudly if the mounted world rectangle ever stops containing the `WorldWindow` the feature's own harness module declares its scenarios and their mutants need. (It took no argument and read a module constant until `split-acceptance-harness` parameterized it — the required window is per-feature state, so it could not stay in the core.)

_Third, a `fireEvent.click` on a cell in this layer is **not** the route a mouse user takes, and the difference is not a jsdom artifact._ `useGridPointerGestures` takes pointer capture on `#grid-content`, which retargets the subsequent native `click` to the container — so `Cell`'s own `onClick` never fires for pointer-driven interaction, and `Grid`'s `onTap` resolves the cell from pointerup pixels through `screenToWorld` instead. `Cell.onClick` is therefore the **keyboard-activation** route (Enter/Space), and jsdom's `fireEvent.click` dispatches a bare `click` with no pointer sequence — so this layer drives that keyboard route and never exercises hit-testing at all. **There is now exactly one black-box layer, and this is why losing the other cost no reach.** The two used to be nested rather than complementary, and the survivor is the outer one. The e2e layer drives _both_ routes: Playwright's `.click()` for the pointer route, and `page.keyboard.press('Enter')` on a focused cell button for the keyboard one (now `features/generation-control.feature` and `keyboard-grid-navigation.feature`'s Enter scenarios — this cited `features/hud-layout-and-shortcuts.e2e.spec.ts:102` until `re-audit-hand-written-e2e-residue` moved the claim to the contract, and that line is now a bare comment). The acceptance layer saw a strict subset of the routes the browser layer sees, plus no hit-testing — it reached nothing Playwright structurally cannot, which is the measured basis for deleting it without replacing its coverage. Measured on this tree by injecting `Cell`'s `onActivate(x, y)` → `(y, x)`: the acceptance project fails (5 of its 48 step-tests), the full Playwright run is **58 passed / 1 failed** — the failure being that keyboard test, on `aria-pressed` — and all **14 tests** in the paired `cell-life-and-death.e2e.spec.ts` pass, every activation there being a `.click()`. What survives of this is the narrow half only, and it is now a warning about a layer nobody can run: **a green jsdom run was never evidence about hit-testing**, which is exactly what it could not see. (Commit `4f6e14d`, "record why the e2e layer cannot see `Cell.onClick`", concluded the opposite — "disjoint activation routes", "passes all 14 e2e specs" — from a Playwright column pre-registered as that one paired spec file, and generalized to the layer; `product`'s VERIFY pass refuted it by running the whole layer. Its subject line and body cannot be rewritten, so this paragraph is the correction.)

There is no single default jsdom run any more — `vite.config.ts`'s `test.projects` splits the main vitest config into `unit`/`property` (Node) and `dom` (jsdom) projects (see CLAUDE.md's compact module map, and `architecture.md`) — but all three projects still exclude `**/*.e2e.spec.ts`, `**/*.browser.test.ts`, and `**/*.perf.spec.ts` via the shared `exclude` list, so the three runners (this config, `vitest.browser.config.ts`, and Playwright) never collide. That same shared list also subtracts whole **directories** — `scripts/`, `ideas/`, `.claude/`, `.stryker-tmp*/` and `.features-gen/` — because the `unit` project inherits an **unrooted** include (see `vite.config.ts`'s comment on why it subtracts rather than declaring its own), so every directory in the checkout is reachable unless `sharedExclude` names it. That is a live hazard rather than housekeeping: measured on this tree, a stray `.test.ts` dropped into `perf/`, `rules/`, `rule-tests/`, `patches/` or `public/` is still collected into `unit` and run in Node. Those five are deliberately left unexcluded — a name added here to a directory that might one day hold a legitimate colocated test would exclude it silently — and the merge protocol's mutation-invariant clause explains which paths the exclusion is genuinely owed to.

`npm test`/`npx vitest run` with no `--project` flag runs all three (`unit`, `property`, `dom`); `npm run test:unit` and `npm run test:property` narrow to a subset via `--project`, which is the only way to filter which project(s) run once `test.projects` is set — a plain `--exclude` on the CLI has no effect there. `--project` matches by the project's `name`, so `npx vitest run --project dom <path>` (or the bare `name`, or a `!name` negation as `test:unit` uses) is how to run just one project's slice of the suite. Be aware a vitest project whose `include` glob matches nothing simply reports 0 files and exits 0 — there is no warning — so if `dom`'s globs (`src/components/**` and `src/hooks/**`) ever stop matching anything (e.g. one of those directories gets renamed), `npm test` stays green while quietly running 23 fewer files (measured on this tree: `dom` collects 23 files, 175 tests); see the comment in `vite.config.ts` for the other files that same rename would need to update.

`perf/` is a fifth top-level directory of Playwright specs, and deliberately **not** a fifth test layer: it measures render cost and asserts nothing about performance (see `perf/README.md`). It is outside every quality gate on purpose, which is why the split described in `quality-tooling.md` matters — the numbers themselves are computed in `scripts/perf-report/`, which is gated.
