# Article: Architecture: the framework-free modules

**Audience:** coder, cleaner, architect - **Read when:** before adding, moving, or splitting a module, and at the start of every architect REVIEW or DESIGN pass.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 107-127, 129-142. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

### Core logic: twenty framework-free modules, sixteen hooks, thirteen unit-tested components

Twenty framework-free modules — sixteen at `src/` root (`appearance.ts`, `gameOfLife.ts`, `patternLibrary.ts`, `camera.ts`, `zoomGlide.ts`, `gridGeometry.ts`, `cellTiles.ts`, `cellAnchor.ts`, `dragGesture.ts`, `scrollbars.ts`, `patternPlacement.ts`, `liveCellStore.ts`, `liveCellWindow.ts`, `gridFocus.ts`, `liveCellSeed.ts`, and `cache.ts`) and four in `src/equality/` (`container-equality.ts`, `is-shallow-equal.ts`, `is-deep-equal.ts`, `is-strict-equal.ts`) — hold every non-UI rule in the repo, and together with sixteen hooks in `src/hooks/` (`useCamera.ts`, `useElementSize.ts`, `usePatternPlacement.ts`, `useWheelInput.ts`, `useGridPointerGestures.ts`, `useInitialCentering.ts`, `useLiveCells.ts`, `useGridFocus.ts`, `useContentBounds.ts`, `useCellTiles.ts`, `useRafCoalescedPan.ts`, `useZoomGlide.ts`, `useReducedMotion.ts`, `useMatchMedia.ts`, `useSystemAppearance.ts`, `useAppearance.ts`) and thirteen components in `src/components/` (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `GridLines.tsx`, `HoverIndicator.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`) are the modules covered by unit tests and mutation testing (see `stryker.config.json` / `crap4ts.config.ts` — both scope by glob-minus-exclusions rather than by an enumerated list, and `scripts/halstead4ts/run.ts` resolves `crap4ts.config.ts`'s globs rather than restating them, so a new module at `src/` root, `src/hooks/`, or `src/components/` is covered the day it lands with no config edit). Every framework-free module is additionally covered by property tests (the `property` vitest project's `include` is `**/*.property.test.ts`, so a new file with that suffix is picked up automatically) with two deliberate exceptions in `src/equality/`: `is-strict-equal.ts` is a three-line `Object.is` wrapper with no invariant to quantify over, and `container-equality.ts` has no contract of its own to state — it is the shared walker both comparators inject into, so their property tests (reflexivity, symmetry, clone round-trip, Set-member order-independence) are what cover it, from both sides. `gridFocus.property.test.ts` and `liveCellWindow.property.test.ts` closed the last gap here at that slice's REVIEW pass, and each records the fault battery it was shown failing against rather than only the invariants it states — including two that a first battery did **not** catch, which is why the batteries are written down: `stepFocus`'s left/right-inverse property survives a wholesale axis swap (the one-axis property is what fails), and `centerCell`'s in-range and half-a-cell properties both survive losing the even-count tie-break (only the pinned symmetric-range case fails). `zoomGlide.property.test.ts` continues that practice and records a **13-fault battery** in this file's REVIEW handoff, with two deliberate non-kills worth knowing: `glideDurationMs` ignoring the reduced-motion preference is caught by unit tests in three files and by **no** property (a two-point function has no invariant to quantify), and `clamp01` losing its `Math.min(1, …)` half is a **hand-applied equivalence with no corresponding mutant** — Stryker generates exactly two `MethodExpression` swaps on that line and both are Killed, so nothing there can survive and the score cannot speak to the removal in either direction; the whole 889-test suite stays green under the hand-applied version, and the note at the site is now headed that way rather than as an "equivalent mutant", which sent `hardener` hunting for a survivor that does not exist. It also found two facts about the landed code rather than only confirming it, both recorded as pinned cases beside the properties: an in-then-out double click nets to exactly zero only at rungs whose factor round-trip is float-exact (at the 64% rung it leaves a two-ULP residual glide, invisible at every observable), and it nets to zero at all only when neither click was clamped — from 41%, out-then-in correctly lands on 50%, exactly where settled clicking lands. **And one of those properties then found a real defect that the same properties had only a ~0.35% per-run chance of catching** — a latent flake `hardener` surfaced by replaying at volume rather than by trusting a green run, which is the transferable half: `easeOutCubic` rounds to exactly `1.0` for progress values strictly below 1, so keying the exact-landing branch off `progress >= 1` left a window where `glideCellSizeAt` returned `fromCellSize + (toCellSize − fromCellSize)`, and that sum is not `toCellSize` for **7.2%** of endpoint pairs drawn from the cell-size range (measured, 14,482 of 200,000) — so the module could return a value outside the closed interval it publishes. Adjudicated as a module defect rather than an over-strict property, on the rule that **a property weakened to accommodate a defect stops being the thing that found it**; the branch is now keyed off the eased value, which is strictly conservative (`progress >= 1` implies `eased >= 1`) and measured at 0 escapes where the old form had 1 in 20,000 replayed runs and 0 in 3.2M adversarial endpoint/eased probes, independently reproduced by `hardener` at **22.2M** evaluations. **The acceptance check for a property whose failure mode is a rare float boundary is a repeated run, not a run** — a single green run is not evidence about a ~0.35%-per-run flake, and the numbers `slice/smooth-zoom-transitions` settled on are **120–150 repeated file runs** plus a bulk replay of the file's own arbitraries. The obvious-looking alternative — anchoring the lerp at the far endpoint, `toCellSize − (toCellSize − fromCellSize) * (1 − eased)` — is recorded in the module as **four orders of magnitude worse** (8,250 escapes in those same 20,000 runs), because it moves the inexactness to the end nothing short-circuits. `src/App.tsx`, `src/main.tsx`, and `src/components/LifeBoard.tsx` remain excluded — still composition-root/bootstrap code exercised by browser testing rather than unit tests, specifically `features/hud-layout-and-shortcuts.e2e.spec.ts`, which drives the HUD and App's own state wiring (including that a stamped pattern really does come to life) through the real app — as does `src/test-support/`, which is shared test infrastructure (jsdom stubs for `ResizeObserver`, `getBoundingClientRect`, and pointer capture in `domStubs.ts`, the fast-check arbitraries the camera-side property tests share in `arbitraries.ts`, the brute-force Life oracle `gameOfLife`'s and `liveCellStore`'s property tests both check against in `lifeReference.ts`, the `#grid-content` DOM query both `Grid.test.tsx` and `LifeBoard.test.tsx` need in `gridDom.ts`, the single encoding of how a cell's aliveness is expressed in the DOM (the `aria-pressed` attribute/value constants and the `Cell x, y` label format, shared by `src/components/*.test.tsx`, `features/*.e2e.spec.ts`, `features/screenplay/`, and `perf/`) in `cellQuery.ts`, and its sibling `rulerQuery.ts` — the single encoding of how the ruler's two axis groups are named (`rulerGroupLabel`, shared by `src/components/GridRuler.test.tsx` and `features/screenplay/elements.ts`); a sibling rather than an addition to `cellQuery.ts`, whose header scopes it to cell aliveness, and deliberately a name function with no CSS-selector twin, since an accessible name is computed rather than stored and only the role engine queries it faithfully, and their sibling `scrollbarQuery.ts` — the single encoding of how a scrollbar words the proportion of the grid currently in view, added by `scrollbar-visible-proportion-affordance` and the **first module here to export a parser alongside its builder** (`visibleProportionText` for `src/components/Scrollbar.test.tsx`, `parseVisibleProportionText` for `features/screenplay/questions.ts`), which makes it the first whose two encodings could drift apart rather than being one shared constant; its header carries both decisions that are invisible from the call sites — why `percent` is spelled out rather than `%`, and what actually catches that drift, measured: breaking the parser's literal alone fails **7 of the 105 tests** in `npm run test:e2e`, the whole `grid-scrollbars` bdd feature, each reporting the function's own named throw) rather than product code. Nothing in `src/` outside a test file may import from `src/test-support/` — the directory sits outside every gate, so such an import silently moves what it pulled in out of mutation testing and coverage scoring; `rules/no-test-support-in-product-ts.yml` and `rules/no-test-support-in-product-tsx.yml` check that mechanically. Keep new domain logic in a framework-free module rather than in a component whenever it can be expressed as pure logic, so it stays covered by property tests and mutation testing, not just unit tests.

- **`src/appearance.ts`** — the appearance-preference rules: `resolveAppearance` (a fixed `'light'`/`'dark'` preference wins outright, `'system'` defers to whatever `useSystemAppearance.ts` currently reports) and `parseAppearancePreference` (reads a persisted preference back, with anything other than the two fixed values — absent, empty, corrupted, or written by an older version of this app — resolving to `'system'` rather than throwing). `APPEARANCE_STORAGE_KEY` names the one `localStorage` key both `useAppearance.ts` and this module's own tests agree on. Imports nothing; `src/hooks/useSystemAppearance.ts` and `src/hooks/useAppearance.ts` are the browser-facing adapters (`matchMedia`, `localStorage`, the `<html>` class toggle) that call into it.
- **`src/gameOfLife.ts`** — the actual Game of Life model. Live cells are stored as a sparse `Set<CellKey>` (`CellKey` = `"x,y"` string), not a bounded 2D array — the grid is conceptually infinite. Core functions: `toggleCell` (mutates an Immer draft), `advanceGeneration` (one generation **plus** the exact set of cells whose aliveness flipped, computed in the same pass that decides survival — the delta is never recovered afterwards by diffing two finished sets, and `countNeighbors` seeds each live cell at zero precisely so the isolated cell that dies of underpopulation is a candidate that single pass can see), `getNextGeneration` (a projection of `advanceGeneration` for callers with no use for the delta — `liveCellStore.ts`'s own `advance()` since `collapse-dead-cell-layer` retired the per-cell subscription channel, plus the Gherkin step definitions; deliberately not a second implementation of the rules). **`advanceGeneration`'s `changed` delta consequently has no production consumer left** — the store was its last one — and survives on a ruling rather than a caller: it is a domain fact about a generation, computed free inside the pass that already decides survival, and it is covered by `gameOfLife.ts`'s own unit and property tests. Read a green run of those as the whole of what guards it, `computeContentBounds` (bounding box of live cells, used to size scrollbars). Neighbor counting is done only around currently-live cells, never by scanning a bounded region.
- **`src/patternLibrary.ts`** — the catalog of the 8 known Life patterns and the queries over it (`getPatternByName`, `patternsByCategory`), plus the anchor convention shared by `patternCellPositions` and `placePattern`: a `Pattern`'s cells are stored relative to its own bounding-box top-left corner, so stamping and previewing can't drift apart. Split out of `gameOfLife.ts` so the Life rules aren't fused with a data table; the dependency runs catalog → model, never the reverse. Distinct from `patternPlacement.ts` below, which owns the _interaction_, not the data.
- **`src/camera.ts`** — the camera and every transform that produces a new one, independent of both the game rules and what's on screen. `Camera` = `{ offsetX, offsetY, cellSize }` in world-space coordinates. Key conversions: `worldToScreen` / `screenToWorld`, with `rectRelativePixels` as the single translation point from a DOM event's client coordinates into the viewport-relative pixel space every pixel-taking function here (and in `scrollbars.ts`) expects. Handles pan, zoom-at-point (keeps the world point under the cursor fixed), and wheel input (shift+wheel **or** ctrl+wheel = zoom, plain wheel = pan, with a Firefox/Windows axis-swap workaround — see comment in `applyWheelInput`). `ctrlKey` is the wheel event every major browser delivers a **trackpad pinch** as, which is why it shares the zoom branch and why nothing here tries to tell a pinch from a mouse user's ctrl+scroll. A zoom's **magnitude** is the rolled distance rather than its sign: the private `wheelZoomFactor` maps `WHEEL_ZOOM_NOTCH_PX` (100) of `deltaMode`-0 pixels to exactly one `ZOOM_FACTOR` step and everything between it continuously, so two half-notch rolls land where one whole-notch roll does — a `deltaMode` of 1 or 2 reports a line/page count this repo has nothing to calibrate against, so it collapses to `Math.sign` and takes exactly one step whatever it reports. The exponential form is what buys that composition, and `camera.property.test.ts` pins it as reciprocality plus additive composition rather than by restating the formula — read the fault battery in that file's header before judging it adequate: the base and the notch size are invisible to both properties by construction, and are held by unit tests instead. Note the deliberate sign asymmetry: wheel-pan and scrollbar-drag follow the "document scroll" convention, drag-to-pan doesn't.
- **`src/zoomGlide.ts`** — the toolbar zoom-in/out glide, as pure arithmetic over elapsed time: `advanceZoomTarget` (what a click asks for), `glideCellSizeAt`/`isGlideComplete` (where it has got to), `glideDurationMs` (200ms, or **0** for a reduced-motion snap — a duration rather than a second code path, so nothing anywhere branches on the preference). Takes `nowMs` as a parameter and reads no clock, which `rules/no-ambient-time-in-domain.yml` enforces; `src/hooks/useZoomGlide.ts` is the adapter that reads `performance.now()` and drives `requestAnimationFrame`. **Only the toolbar route glides** — wheel zoom, drag-pan, scrollbar drag and reset all stay instantaneous and never reach this module, which is both the product call (animating a continuous gesture fights the user's own input) and the perf one (the wheel route is where the expensive zoom numbers are). Two rules in it are load-bearing and each has a comment arguing it: the easing is **ease-out**, never ease-in or ease-in-out, because a curve that lingers near its START reads as at-rest to the acceptance layer's `zoomAtRest` before it has moved; and a click's target chains off the PENDING glide's own target while starting from the DISPLAYED cellSize, which is what makes two quick clicks land two rungs up while extra clicks past a clamp bank nothing.
- **`src/gridGeometry.ts`** — which part of the infinite grid is on screen and which coordinates are reference lines: `computeVisibleRange` (viewport plus a small buffer) and major-gridline computation every 10 cells. Takes a `Camera` but never returns one.
- **`src/cellTiles.ts`** — the tile-virtualized mounting policy: which world tiles are mounted, and when that set changes, replacing the retired `cellLattice` module's coverage half. Tiles are fixed `TILE_SPAN_CELLS` (4) cells square, world-anchored rather than viewport-relative, so a retained tile's own cells never change coordinates while it stays mounted — a pan re-renders only the entering/exiting strip of tiles at a boundary, not the whole mounted set. `coveringTileRange` computes the exact minimal `TileRange` a camera/viewport needs; `tileRangeHolds`/`nextTileRange` are eviction hysteresis (`EVICT_LAG_TILES` = 1): keep the previous range while it still contains the required one and exceeds it by at most one tile per side, and otherwise rebuild onto the **eviction-lag-clamped union of the previous range and the required one** — not onto the required range exactly, which is what the `fix-tile-hysteresis` slice changed and what makes a sub-cell wobble at a tile boundary cost one rebuild instead of one per pointermove. That retention is deliberately not admission overscan, and the distinction is the whole design: per axis the clamp can only ever keep a bound the previous range already held, so it defers an eviction rather than admitting a tile (see the module header, which also records the two costs it does add — a monotone pan can rebuild twice per tile span instead of once, eviction-only, and a zoom-**in** rebuild retains a four-sided ring where a zoom-out one does not). `nextTileRange` returns its input **by reference** when it holds and is idempotent on its own result, the same no-infinite-loop guarantee the retired `cellLattice` module's `nextLattice` used to carry alone. Stores no `cellSize` — zoom needs no special case, since zooming out fails containment and zooming in fails the lag test, both already covered by the hold/rebuild rule.
- **`src/cellAnchor.ts`** — precision bounding, and nothing else: keeps `(worldCoordinate − anchor) × cellSize` small enough that the compositor's float32 transform matrix stays exact, which is the only half of the retired `cellLattice` module's old origin this module inherits (coverage moved to `cellTiles.ts`, and the two are independent — `cellAnchor.ts` takes `spanCells` as a parameter rather than importing `cellTiles.ts`). `ANCHOR_DRIFT_CELLS` (4096) is how far the camera's offset may drift from the anchor before `nextAnchor` re-quantises, chosen against the float32 integer-exactness cliff at 2²⁴ px. `anchorOffsetPx` is the retired `cellLattice` module's old `latticeOffsetPx`, deliberately just `worldToScreen`: `screenToWorld` resolves taps and hover, and the two must stay exact inverses or a click lands on a different cell than the one under the cursor — `cellAnchor.property.test.ts` pins that identity. `nextAnchor` carries the same by-reference/idempotent contract as `cellTiles.ts`'s `nextTileRange`, applied independently. Because coverage no longer forces a re-anchor, this re-quantises roughly once per 4,096 cells of camera travel instead of on nearly every rebase — rare enough that the cost of that full re-render (~180–200 ms) is an accepted trade rather than a per-pan concern.
- **`src/dragGesture.ts`** — the pointer-drag gesture: `beginDrag`/`advanceDrag` decide when a drag has crossed `DRAG_THRESHOLD_PX` and become a pan rather than a click (the flag latches, so a drag returning near its origin doesn't fall back to a click), and report the incremental pan delta. Deals only in client pixels — it references no `Camera` at all, which is why it stands alone.
- **`src/scrollbars.ts`** — scrollbar thumb sizing, positioning, and drag math. The one camera-side module that knows about the game model (`ContentBounds`), which is exactly why it's separate from `camera.ts`. Scrollbars represent the union of content bounds and current viewport, not content bounds alone (see comment on `computeAxisScrollbarMetrics`) — this keeps the thumb ratio/offset valid even when panned away from all live cells. **`computeThumbGeometry`'s `trackLengthPx` is the TRACK, never the viewport**, and the `scrollbar-thumb-overflows-its-track` slice is why that is written in capitals: `Scrollbar.tsx` passed the viewport length for it while its own Tailwind `right-2.5`/`bottom-2.5` inset each track by the perpendicular bar's 10px thickness, so every thumb was sized and positioned against a box 10px longer than the one it was drawn in (measured at rest, no content and no gesture: a 1280px horizontal thumb in a 1270px track, 900 in 890). The prop is now `viewportLengthPx` and `Scrollbar.tsx` does the subtraction itself, against its own `SCROLLBAR_THICKNESS_PX` — the CSS knowledge stays in the component and this module stays framework-free.

  **The lesson generalizes past scrollbars, and it is the one worth carrying: a property over a module cannot reach an argument's provenance.** `scrollbars.property.test.ts` already asserted "the thumb never extends past the track, in either length or offset" — and it was green, and correct, throughout the entire life of the defect, because it quantifies over the `trackLengthPx` it is _handed_. The bug lived in the gap between that parameter's name and the value one call site passed for it. No property, and no amount of mutation score, over `scrollbars.ts` can see that gap; the guards that can are the parameter's own name (which is why the rename is part of the fix, not cosmetics) and an observation of the rendered result. Before concluding a module is well covered because its invariants are quantified, ask what its callers actually pass.

  **The `SCROLLBAR_THICKNESS_PX` ↔ Tailwind-class coupling is guarded in two different places, in two different directions, and neither can be collapsed into the other.** The constant's _value_ is pinned by jsdom: `Scrollbar.test.tsx` and `GridScrollbars.test.tsx` deliberately restate `- 10` as a literal rather than importing the constant, so the subtraction carries its own mutants instead of trivially agreeing with the source. The constant's _agreement with the class_ is not visible there at all — jsdom has no stylesheet and no layout — and it is not visible to the generated bdd layer either, which reads `aria-valuenow` and the announced visible proportion, both derived from `computeScrollbarMetrics`, which never sees a track length: measured, all 73 e2e tests then in the suite passed both before and after a change that moves every rendered thumb by 10px. The sole channel is `grid-scrollbars.e2e.spec.ts`'s containment test, comparing the thumb's bounding box against its parent track's in a real browser. Read its guarantee as **one-directional**: it catches the constant _lagging_ the CSS inset (measured — that is exactly the deliberately-red step-1 commit, four failing sample points), and it structurally cannot catch the constant _leading_ it, since a track computed shorter than the painted one still satisfies `computeThumbGeometry`'s pinned containment and merely paints a slightly short thumb. **The leading direction is not unguarded, though — it is guarded by the other layer, and the two do not collapse into each other.** Measured, bumping `SCROLLBAR_THICKNESS_PX` to 20 against an unchanged `right-2.5`: `npm run test:e2e` stays at **74 passed**, the full suite, while exactly **4 of the 21 tests** in `Scrollbar.test.tsx` + `GridScrollbars.test.tsx` red — precisely the four carrying the `- 10` literal restatements, with the sub-thickness clamp test still green. So the coupling is guarded in both directions by two different layers: **lagging by the browser**, the only thing that can see paint; **leading by the jsdom restatements**, the only thing that pins the constant's value. That is also what makes "never import the constant into its own tests" a rule with a measured consequence rather than only a mutation-score rationale — importing it would make expected identical to actual and delete the leading-direction guard outright. The one cell of that matrix nothing covers is a _coordinated_ leading edit, constant and literals moved together, and nothing needs to: its worst case is the benign short thumb the derivation above already describes. Note also that a bare numeric constant is not a mutation site at all in this tree's enumeration (a scoped run over the two components produced 71 mutants, none of them on `SCROLLBAR_THICKNESS_PX`'s value) — the jsdom literal restatements are what stand in for the mutant Stryker will not generate. **No `ast-grep` rule is possible here**: the invariant relates a TypeScript number to a browser-computed layout box, and ast-grep can see neither side of that.

  One more measured fact, about `Scrollbar.tsx` rather than this module, since it reads as defensive code someone will want to delete: the `Math.max(0, …)` at that subtraction site has no mutant expressing its _removal_ (Stryker swaps `Math.max`→`Math.min` and `-`→`+`, both of which the ordinary geometry tests kill), so `Scrollbar.test.tsx`'s sub-thickness-viewport test is its only guard — deleting the clamp redded exactly **1 test** — that one — of the 663 across 54 files `scrollbar-thumb-overflows-its-track`'s tree held; the denominators move with the suite, the numerator is the claim. It pins the component's total contract over a `number` prop, not an app-reachable state: `GridScrollbars.tsx` returns `null` unless both dimensions are positive, so nothing in the app passes a viewport that small. Why that clamp carries no removal mutant at all — and why a bare `foo()` statement does — is in `mutation-testing.md`.

- **`src/patternPlacement.ts`** — the pattern-library interaction as one explicit three-state machine (`idle` / `browsing` / `placing`) rather than separate modal-open, armed-pattern, and preview-cell flags, so combinations like "library open with a pattern already armed" are unrepresentable. Exposes transitions (`toggleLibrary`, `armPattern`, `cancelPlacing`, `movePreviewTo`) and queries (`isLibraryOpen`, `armedPattern`, `previewPositions`); callers go through the queries rather than matching on `mode` themselves.
- **`src/liveCellStore.ts`** — the live-cell state itself, as a factory (`createLiveCellStore`) rather than module state: mutators (`advance`/`toggle`/`place`) and two `useSyncExternalStore` pairs — the whole live-cell set (`subscribeCells`/`getLiveCells`) and the content bounds (`subscribeBounds`/`getBoundsSnapshot`). **A third pair, `subscribeCell`/`getCellSnapshot` (plus `trackedCellCount`), was retired by `collapse-dead-cell-layer`, and with it the module's old headline invariant** — _a mutation notifies exactly the cells whose aliveness changed, each exactly once, and nobody else_ — which existed for the per-cell subscription every mounted `Cell` used to hold. Only live cells mount now, so the component that decides _which_ cells exist needs the whole set and per-cell precision buys nothing. The successor contract was written down in the same pass rather than merely lost (a deleted invariant with no successor is how a module quietly stops promising anything), and `liveCellStore.property.test.ts`'s header states its three clauses: **every whole-set subscriber is notified exactly once per mutation and never for a read; `getLiveCells()` is identity-stable between mutations and always hands back a new identity when membership really changed; published state is always frozen and always equals an independent brute-force oracle.** The named cost of the swap: every mutation notifies unconditionally, so a still-life tick re-renders every mounted cell where the retired channel would have re-rendered none. Two more contracts: every mutator funnels through a single private `publish()`, which re-freezes even though immer already auto-freezes (auto-freeze is a _global_ immer setting and can be defeated by a leaked scope — read the comment before removing it), so `getLiveCells()` is **always** frozen and typed `ReadonlyLiveCells`; and `getBoundsSnapshot()` keeps its object identity whenever the box hasn't moved, which is what stops `useSyncExternalStore` re-rendering the scrollbars every tick. `getLiveCells()` is paired with `subscribeCells` as a second `useSyncExternalStore` source (added by `collapse-dead-cell-layer`, read through `useLiveCells.ts`, and the input `liveCellWindow.ts` needs to decide which cells mount at all) — so it is a legitimate render source **only** with that subscription. Reading it during render _without_ subscribing is still the correctness bug this line used to warn against wholesale: the component then reads a value it is never notified about. Note the trade the whole-set subscriber makes against the per-cell one above — it re-renders on every mutation rather than only when one cell flips, which is exactly the accepted regression `collapse-dead-cell-layer` bought its mounting reduction with.
- **`src/liveCellWindow.ts`** — the live-cell rendering projection: which cells get a DOM element at all. `liveCellsInRange(cells, range, focus)` returns every live cell inside the mounted `TileRange`, row-major, **plus the keyboard focus cursor's own cell whenever that isn't already one of them** — the "+1" this module's header names, and the reason a dead cell can still be mounted. Sits above both `gameOfLife.ts` (the live-cell `Set`) and `cellTiles.ts` (the camera-derived tile range), the same two-sided position `scrollbars.ts` holds over `camera.ts` + `gameOfLife.ts`. **The +1 may leave the mounted set — the DOM is not a windowed view of the board**: the cursor's cell is included even when it sits _outside_ `range`, which is what keeps the grid reachable by Tab after a pan carries the cursor off screen, and is why a count of mounted live cells is not a count of live cells (see `features/screenplay/questions.ts`'s `aliveCellCount` and its precondition).
- **`src/gridFocus.ts`** — the keyboard focus-cursor model: one `(x, y)` world cell and the pure transitions that move it (`centerCell`, `stepFocus`, `jumpToRowEdge`, `panToRevealPx`). Imports `camera.ts` and `gridGeometry.ts` and nothing else; in particular it does **not** import `liveCellWindow.ts` and is not imported by it — the cursor and the mounting window are two independent projections of the same camera, and the focus coordinate reaches the window as a plain argument. `panToRevealPx`'s sign convention is derived against `camera.ts`'s `panCamera` in its own comment rather than by intuition; read that before touching it.

- **`src/liveCellSeed.ts`** — deterministic live-cell seeding for the render-performance harness (`perf/`): `parseSeedRequest` reads a `?cells=&spread=&seed=` query string, `buildSeededLiveCells` places exactly that many cells from a `Math.imul`-based LCG, and `seedFromSearch` is the two together. Only ever reached from `src/main.tsx` under `MODE=perf`, but deliberately a framework-free module rather than harness code: a seeder that silently produces the wrong population makes every perf number measured against it wrong too, and nothing downstream would notice — so it lives where mutation testing and property tests can see it. It takes the query string as an argument and never reads `location` or `import.meta.env` itself; `rules/no-dom-in-domain.yml` and `rules/no-build-env-in-domain.yml` enforce both.
- **`src/cache.ts`** — a keypath-trie cache (`createCache`, `CacheError`): entries are addressed by an arbitrary `unknown[]` key path, and the trie nodes are `PATH` or `ENTRY` (a node can be both a stored entry and a parent of deeper ones). Deliberately mutable rather than immutable, which its header comment argues at length and which is the reason to read that comment before "modernising" anything here — insert/update/remove mutate each node's `Map` in place so they stay O(keypath), where the clone-per-write immutable form (including immer's, whose `prepareMapCopy` shallow-clones the base Map on first write inside `produce()`) would be O(entries). Iteration is fenced: a mutation during a `for...of` over the cache invalidates the iterator and the next step throws, rather than silently yielding a torn view. The node representation stays private to the file — the exported surface is `createCache`, its two interfaces (`Cache`/`ReadonlyCache`), and `CacheError`.
- **`src/equality/`** — structural equality comparators, four files: `is-strict-equal.ts` (a typed `Object.is`), `container-equality.ts` (the walker: container-kind dispatch over Date/Set/Map/Array/plain object, taking the leaf comparison as an injected `compare` function), and the two one-line comparators that inject into it — `is-shallow-equal.ts` (leaves compare with `Object.is`) and `is-deep-equal.ts` (leaves compare with `isDeepEqual` itself, so it recurses). The injected comparator is the whole design: every branch that isn't a leaf comparison — kind dispatch, mismatch handling, size/key-count guards, Set multiset matching — exists exactly once, which is what stopped the two ported implementations from re-diverging (they were a near-verbatim duplicate of each other, and the mismatch bugs they carried were present in only one of the two directions). Read each comparator's scope contract before reaching for one: these are for small, known-shallow projections, and a Set of non-primitives costs O(n*m) per level.

Those twenty form a small acyclic graph, and keeping it acyclic is the point of the split: `appearance.ts`, `gameOfLife.ts`, `camera.ts`, `dragGesture.ts`, `cache.ts`, and `is-strict-equal.ts` import nothing; `patternLibrary.ts` → `gameOfLife.ts`; `gridGeometry.ts` → `camera.ts`; `zoomGlide.ts` → `camera.ts`; `cellTiles.ts` → `camera.ts`; `cellAnchor.ts` → `camera.ts` (neither imports the other — `spanCells` is a parameter both take rather than a shared import); `scrollbars.ts` → `camera.ts` + `gameOfLife.ts` (the single place the camera side touches the game model); `patternPlacement.ts` → `patternLibrary.ts`; `liveCellSeed.ts` → `gameOfLife.ts`; `liveCellStore.ts` → `gameOfLife.ts` + `patternLibrary.ts` + `equality/is-shallow-equal.ts`; `liveCellWindow.ts` → `gameOfLife.ts` + `cellTiles.ts`; `gridFocus.ts` → `camera.ts` + `gridGeometry.ts` (and deliberately neither imports the other — see both bullets above); `container-equality.ts` → `is-strict-equal.ts`; `is-shallow-equal.ts` → `container-equality.ts` + `is-strict-equal.ts`; `is-deep-equal.ts` → `container-equality.ts`. `cache.ts` and `src/equality/**` are the two general-purpose utilities imported wholesale by the `import-utilities` slice rather than grown from a feature. `is-shallow-equal.ts` acquired its first caller in the `live-cell-store` slice (the bounds-identity check above); `cache.ts` and `is-deep-equal.ts` still have none. They live here, inside every gate, rather than in a `src/catalyst/`-style exclusion, precisely because this repo now maintains them. A new domain module is covered by `rules/*.yml` with no rule edits whether it sits at `src/` root or in a subdirectory: ast-grep's `*` crosses `/`, so the domain rules' `files: src/*.ts` glob reaches `src/<dir>/*.ts`, **and their `ignores: src/*.test.ts` entry reaches `src/<dir>/*.test.ts` by the same rule** — a subdirectory's test files are excluded exactly like a root module's. `crap4ts.config.ts` and `stryker.config.json` scope by `src/**`, so they reach a subdirectory too. Prefer flat at `src/` root for a single cohesive module; a subdirectory is fine for a set of siblings that belong together (see `src/equality/`). (Measured twice against ast-grep 0.45.1 — once before `src/equality/` existed and again on the landed tree, both times with a throwaway probe module plus a `.test.ts` twin: the domain rules fired on the module and never on the twin. This paragraph previously claimed the opposite; it was wrong.) File naming follows the same split: `src/` root modules and `src/hooks/` are camelCase, `src/components/` is PascalCase, and `src/equality/` deliberately keeps the kebab-case names it was ported under — a decision, not drift, since the file names double as the identifiers a reader looks up when tracing these back to their source.

`src/catalyst/` sits apart from all of the above: it's vendored third-party Tailwind Catalyst UI primitives, dropped in as source rather than installed as a dependency. It isn't code this project authors, and it's deliberately outside every quality gate — `crap4ts.config.ts` and `stryker.config.json` each carry an explicit `src/catalyst/**` exclusion (`scripts/halstead4ts/run.ts` inherits it by resolving crap4ts's globs), and `.dry4tsrc.json` ignores `**/catalyst/**`. Note that's an exclusion rather than an omission: since both tools measure `src/**` by glob, anything dropped into `src/` is scored unless something says otherwise, so a second vendored directory would need the same three entries added. Components import from it as needed. Treat it as a library boundary: read it to learn a component's props, but don't refactor it to this repo's conventions or add it to a tool's include list.
