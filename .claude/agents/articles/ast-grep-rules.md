That is why no blur-side surgery could ever route Tab _into_ the grid from an element sitting after it. `remove` is deliberately absent from the enumerated method list: `classList.remove()` and a `Set`'s own `remove()` are ordinary, and a rule that noisy is one that gets weakened to clear a finding. `src/hooks/` is out of scope as a ruling — a hook is the sanctioned browser-API adapter layer and one that builds a detached node it owns outright is never fighting the reconciler. **No `-ts` twin, and unlike `no-unbraced-accessible-name`'s the argument is contingent rather than structural**: `src/components/` merely happens to hold only `.tsx` files, and a twin is not authorable today because `npm run ast-grep:rules` fails a `files:` glob resolving to nothing — so if a `.ts` module ever lands there, this rule goes blind to it and the twin becomes necessary and possible on the same day. Measured against ast-grep 0.45.1: the fixture's 8 valid cases produce no finding (including `classList.remove`, a ref `addEventListener` with an options object, and a prose mention) while all 9 invalid ones fire, a scan of the real tree is clean, and replanting the deleted `onBlur` into `src/components/Cell.tsx` produced exactly two findings, one per surgery call), and the two invariants the `features/screenplay/` decomposition rests on — a screenplay module importing the barrel back (`no-barrel-import-in-screenplay`, which is what keeps the layering underneath acyclic; ESM tolerates a cycle silently until an evaluation order puts a `const` in its temporal dead zone, and the failure then surfaces as `Cannot access 'CENTER' before initialization` from a module that never mentions `CENTER`) and `questions.ts` importing `expect` (`no-expect-in-screenplay-questions`, scoped to that one file on purpose — Playwright's retrying assertion is the sanctioned WAIT primitive and `interactions.ts` uses it as one, so a directory-wide "only expectations may assert" ban would report two correct functions and push the fix toward `page.waitForSelector`). Both were authored in that slice's DESIGN pass, ahead of the directory they scope, so each carried an `allow-unresolved-files` marker until the REVIEW pass deleted it — at which point each was live-probed against the real landed path (a planted `import { CENTER } from '../e2e-helpers'` in `viewport.ts`, and `expect` added to `questions.ts`'s existing `@playwright/test` import), one finding each and nothing else. That sequence is the standing bargain for authoring a rule ahead of its target: the fixture proves the matcher, the probe proves the `files:` glob, and the marker is what makes the debt visible in between (`npm run ast-grep:rules` reports it as stale the moment the glob resolves). Report-only like the four advisory `scripts/` programs in `quality-tooling.md` (but unlike `ast-grep:rules` and `agent-doc-check`, which gate) **for findings**: every rule is `severity: warning`, so a rule matching your code does not move the exit code -- read the output rather than `$?`. Promote one to a gate by changing it to `error`. The exit code is not meaningless though, it just answers a different question: measured against ast-grep 0.45.1, **8** means a rule file failed to parse and **1** means an `error`-severity rule matched, so a nonzero exit always warrants investigation.

**`no-dead-doc-on-annotated-return-literal` is documented here rather than inside that sentence, and the exception is deliberate.** Every other rule encodes a _layering_ invariant — who may import whom, what may appear in which file. This one encodes a fact about a _documentation channel_, it was authored a slice later than the enumeration, and folding it in would mean rewriting the connective grammar the paragraph above says not to touch. It is the only mechanical guard `doc-comments.md` has.

What it matches: a JSDoc block (`/**`, matched as a `comment` node, which is what tree-sitter makes it — a sibling of the object literal's properties, which is the whole reason this is expressible) standing inside a `return { ... }` object literal, or inside an arrow function's parenthesised expression-body literal, when the enclosing function annotates its return type. Unscoped by path and `language: TypeScript` — the invariant is a fact about TypeScript rather than about a layer, so it holds in `src/`, `scripts/` and `features/` alike, and leaving off a `files:` glob is also the one form that cannot be rotted by a rename in `src/` (the standing fragility named in CLAUDE.md, which nothing checks between `architect` passes). No `.tsx` twin: all sixteen hooks are `src/hooks/*.ts` and no annotated function in a `.tsx` file returns a documented literal; the `no-manual-memo-ts` / `-tsx` pair is the precedent if a hook ever lands in a component file.

Why it earns a rule: **the defect it catches is invisible to every other check in this repo and to the person committing it.** The code type-checks, lints, formats, and every test stays green; the doc simply never renders, at any call site, and a bare-signature hover is indistinguishable from no doc having been written. Measured on fresh files the language server had not read, hovering a **destructured** cross-file call site: an inline type-literal annotation (`(): { alpha: number }`) severs the property doc, an annotated arrow severs it, and an unannotated function's property doc **reaches**. That third row is the control rather than a bonus — all three hovers were taken from one file in one round, and an earlier round of the same probes returned `any` for all three because the server had not yet resolved the import, which is precisely the false negative a "severed" reading is exposed to. The measurement is what broadened the rule past the name the DESIGN pass proposed for it (`no-dead-doc-on-named-return-literal`, from `doc-comments.md` rule 8's `(): CellTilesView` row): the severing condition is _an_ annotation, not a _named_ one.

Two things it deliberately does not do. It never judges prose — a presence-only "every export carries a doc" rule was proposed in the same pass and **rejected**, because it cannot tell whether a summary says anything and is satisfied by an empty `/** */`. And every `inside` in its chain keeps the default `stopBy: neighbor`, so the chain object -> `return_statement` -> `statement_block` -> function is exact: a `return` inside an _unannotated inner_ arrow nested in an annotated outer function is a **live** doc, and a `stopBy: end` anywhere in the rule would walk past the inner function and report it. `rule-tests/` pins that case as valid for exactly that reason.

**Every rule ships with a fixture in `rule-tests/` and `npm run ast-grep:test` must pass.** This is not ceremony. A malformed ast-grep rule matches nothing and reports nothing — it looks exactly like a clean codebase — and two of these rules were silently inert when first written (metavariables don't interpolate inside string literals, so an import path needs `kind:` + `regex:`; and a `matches:` util is bound to one language, so it never applied to the `.tsx` files the rule existed to check). A rule with no failing fixture has not been shown to work. Note also that TypeScript and TSX use different parsers, which is why `no-manual-memo-ts` and `-tsx` are near-duplicates by necessity rather than by oversight.
