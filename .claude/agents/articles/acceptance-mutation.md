# Article: The acceptance-mutation Runner

**Audience:** product - **Read when:** before your first npm run acceptance-mutation in a slice.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 225-259. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

- `scripts/acceptance-mutation/` — **owned by `product`, not `hardener`** (it mutates the _spec_ and asks whether the scenario notices, so both sides of what it measures are `product`'s). Mutates individual values in `.feature` Examples tables (never source code) and reruns the target's generated Playwright spec to check the scenario actually notices (concept from unclebob's Acceptance-Pipeline-Specification). Every mutant and every baseline copy of a target is written as its own `.feature` file into one shared temp tree (`.features-gen/acceptance-mutation/`, in-tree — playwright-bdd's module resolution fails out-of-tree), and each of the run's two phases (baseline, then mutants) does exactly one `bddgen` generate + one `playwright test` run over the whole batch, rather than one process spawned per mutant — see `run.ts`'s own header comment for the two-phase design. `run.ts` itself is excluded from `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` by their `**/run.ts` globs, so it holds only I/O and composition: **which values are mutable, and how a mutant is located and rendered**, is `mutation-sites.ts`'s job (see the paragraph below), what a mutant _is_ (its ordinal, its mutated value, its mutated text) lives in `mutant-plan.ts`, what its filename _looks like_ lives in `mutant-tree.ts`, and how the report's Site column prints lives in `report-format.ts` — all inside the gates. That split is load-bearing rather than tidy — classification looks a result up by the mutant's filename, so a record whose name and text came from different sites would misattribute a kill or a survivor with nothing in the output to notice it by. `architect` ratified the batched form over a per-mutant-spawn alternative on cost (measured 215.3s against a >400s floor for the per-mutant form, an identical verdict either way). In practice this hardens the Gherkin layer against itself — the weaknesses it has surfaced so far were in step definitions absorbing a mutated value without noticing, not in the framework-free modules themselves — so treat it as acceptance-suite quality assurance, not as evidence the Gherkin layer is finding core-logic bugs unit tests miss.

  **The feature is read through one parser adapter, and the mutable surface is a registry rather than a hardcoded scan** (the `gherkin-ast-mutation` slice, which deleted the line-oriented `gherkin-examples.ts` — a scanner for `/^\s*Examples:\s*$/` that re-rendered a whole table row at a hardcoded 6-space indent). `gherkin-document.ts` is the **sole** `@cucumber/*` importer (`@cucumber/gherkin` + `@cucumber/messages`, both direct devDependencies added by that slice — no other new package; `rules/no-cucumber-parser-outside-adapter.yml` enforces the boundary from the other side), and it hands back real `Scenario` nodes **with their steps, examples and locations intact** rather than a cells-only projection, so the next mutator needs no second parse. `mutation-sites.ts` then holds two `Record<SiteKind, …>` registries, one finder and one renderer per kind: a `SiteKind` missing either half is a **type error in that file** under `npm run build` (whose `tsc -b` references `tsconfig.scripts.json`), never a silently-empty mutant set or a renderer that throws on the first mutant of its kind. `text-span.ts` is the parser-free other half — a `TextSpan` is a half-open, single-line column range and `spliceSpan` touches exactly those bytes, which is why a mutant differs from its original on **one line** where a full AST re-render would re-pad every cell in the table to the new widest value.

  **The registry exists because the mutable surface is meant to grow beyond Examples cells** — that scope, not any breakage of the old scanner, is why the slice ran. Mutating step text, scenario names or DocStrings was a _different program_ against a scanner keyed on `Examples:`; against this one it is one more registered file. Today there is exactly one kind, `examples-cell` (`examples-cell-sites.ts`), reproducing the old scanner's 55 mutants byte-for-byte. Measured at review with a throwaway `scenario-name` kind that ran end to end: **one** new `*-sites.ts`, plus one widened union line and two registry entries in `mutation-sites.ts`, and **zero** lines changed in `gherkin-document.ts`, `text-span.ts`, `mutant-plan.ts`, `mutation-rules.ts`, `report-format.ts` or `run.ts`. A kind needing a **new traversal root** widens the adapter too, additively: a `Background`-steps mutator wants a `listBackgrounds` beside `listScenarios`, because a `Background` nests under both `Feature` and `Rule` and a finder walking `doc.feature.children` itself would re-solve the Rule-nesting the adapter already owns. Widen the adapter rather than reaching around it; the rule's own `note:` says so.

  Three things it does before it will score anything, each of them closing a way the runner could report a confident number about nothing. **Targets are discovered from `features/`**, not from a hardcoded table (`discovery.ts`, over `scripts/feature-files.ts`) — every `.feature` file present is a target; discovery no longer pairs a target against a `*.steps.test.ts(x)` file at all, since the generated Playwright spec a mutant actually runs against doesn't exist yet at discovery time (it's produced later, by bddgen, from the mutant `.feature` files the runner writes) — see `discovery.ts`'s own comment for why that pairing check was dropped rather than adapted. **Every active target's unmutated feature runs once, batched with every other target's baseline, before any mutant is written**, and a baseline that isn't green (no matching spec in the report, zero specs collected, a failure, or a skipped spec) aborts the whole run naming the target — there is no trustworthy spec count to compare its mutants against, so proceeding would misreport them rather than merely under-report. **Each outcome is read from Playwright's JSON reporter** (`PLAYWRIGHT_JSON_OUTPUT_FILE`, written to a fresh path per phase so a crashed run can never be scored off a previous one's file), never a regex over console text: `killed` requires the same collected-spec count as the baseline, zero skipped specs, and at least one `unexpected` (failed) spec; a mismatched count or any skipped spec is `error` instead, and a matching, unskipped count with zero failures is `survived`. The error-on-mismatch half continues a repaired defect from this module's original vitest-based form, not a precaution reinvented for Playwright — the old classifier read a nonzero exit plus vitest's ordinary failure chrome as a kill, so a steps file broken at _import_ (0 tests collected, exit 1) scored as a kill on every mutant, and a wholly broken suite would have reported 100%.

  Separately from those three guards, and about the run's **output** rather than its preconditions: **a target with no Examples table contributes zero mutants and is reported as `0 mutants (no Examples table): <feature>` rather than silently dropped**, with the aggregate reading a defined `100.0%` — vacuously clean, nothing ran. That is a designed state, not a warning: since `prune-gherkin-to-domain-language`, **five of the ten features carry no Examples table at all** (`appearance-preference`, `camera-pan-and-zoom`, `grid-scrollbars`, `infinite-grid`, `keyboard-grid-reachability` — counted on the tree `dark-mode-following-system-appearance` was specified against), because a table-less scenario costing zero mutants is the lever that slice pulled — so `npm run acceptance-mutation -- --feature <one of those>` is a routine command, and it used to print `mutation score: NaN%` at exit 0. **A table-less target is not baselined either, so this runner says nothing whatever about whether its scenarios pass** — undocumented until `dark-mode-following-system-appearance`'s CONTRACT pass, and the reading to avoid is treating a `100.0%` beside a zero-mutant label as any kind of green. `run.ts` filters `activePlans` to plans with at least one mutation site _before_ `runBaselinePhase` ever sees them, so a table-less feature skips both phases; measured on that slice's contract, whose seven scenarios were **all red** under `npm run test:e2e`, `npm run acceptance-mutation -- --feature appearance-preference` still printed `0 mutants (no Examples table)` and `mutation score: 100.0%` at **exit 0**. The green that _does_ mean something for such a feature is its own bdd project run, nothing here. The label says only what it can actually observe: a target excluded by `--feature` is filtered before it becomes a plan, so it is never in that list.

  **The temp tree is flat, and two constraints follow from that.** One shared `features/` directory holds every target's baseline and mutants, so a nested target's path is flattened into a single filename (`/` → `__`, in `mutant-tree.ts`'s private `baseName`). First, **a feature path that reaches the temp tree may not contain `_`**: `/` → `__` alone is not injective (`a/_b.feature` and `a_/b.feature` both give `a___b.feature`), so rather than prove a cleverer encoding collision-free the deriver rejects the input that makes the flattening unsafe, exiting 1 and naming the file. Scope that to targets that reach the temp tree and **not** to `features/` as a whole — `baseName` runs only over _active_ plans, so a table-less feature under an underscored directory is reported as an ordinary zero-mutant target and never throws (measured both ways with a planted probe). Nothing enforces it at authoring time and nothing needs to: `product` runs this tool in both SPECIFY and VERIFY, so an underscore-named target with a table fails inside the slice that adds it. Second, and only until `intent-driven-layout` lands: **discovery is recursive but execution is not.** `playwright.config.ts`'s `bdd` project globs the non-crossing `features/*.feature`, and its generated-output guard reads `readdirSync(FEATURES_DIR)` non-recursively, so a nested `.feature` would be mutated by this runner and never run by `npm run test:e2e` at all — measured with a planted `features/probe-nested/probe-nested.feature`: `acceptance-mutation` discovered it, flattened it, and scored it 2/2, while `npm run test:e2e -- --list` stayed at **74 tests in 14 files**, the same total as the run without it (the totals line is what was compared, not the full listing). `npm run gherkin-lint` does recurse (same probe, reported against the nested path), so `product`'s lint gate is not part of the gap. `intent-driven-layout` owns `playwright.config.ts`; until it lands, keep `features/` flat.

  **Two structural mutation classes now, not one, and the count of mutants does not move when a class is added.** Every Examples data cell is exactly one mutation site and yields exactly one mutant — `buildMutantRecords` calls `mutateValue` once per site — so a new class **dilutes** the existing ones (each cell gets one mutant, class chosen by a draw) rather than multiplying them. 55 cells, 55 mutants, before and after `cells-column-has-two-parsers-and-neither-models-tuples`. A class count is only ever moved by changing the _site_ model, which `assertUniqueSeedKeys` forbids as written (two sites for one cell share a seedKey).

  **`tuple-list.ts` owns paren-delimited numeric tuple lists; `mutateCommaList` owns the flat rest.** `isTupleList` accepts a value that is **wholly** a comma-separated list of parenthesised, fixed-arity integer tuples — `(0, 0), (1, 0), (0, 1), (1, 1)`, the shape `pattern-library.feature`'s `cells` column uses — and its `VALUE_RULES` entry sits **ahead** of the comma-list rule. It emits two classes, chosen by a first draw that is taken unconditionally so the draw sequence never depends on data shape: **component-change** (mutate one component, the pre-existing behaviour) and **swap-x-y** (transpose a 2-tuple's two components, offered only for arity 2 and only for pairs whose components differ, since swapping `(2, 2)` would be a byte-identical no-op mutant). Measured over the current table: 6 component-change, 2 swap. `stripParenAffixes` — the flat splitter's paren-shaving patch, which shredded `(0, 0), (1, 0)` into unbalanced `(0` / ` 0)` fragments and shaved the punctuation back off — **is deleted**; `mutateCommaList` is a flat comma-list mutator again.

  **Swap is why the class was worth adding, and the reason is an assertion, not a shape.** A component-change is caught by "every cell the table names is on screen"; a **swap whose transpose is already a live cell of the pattern** passes that check vacuously and is caught only by the reverse one, "and nothing else is". Measured per pattern (swappable pairs whose transpose is already in the set): Pulsar 48 of 48, Beacon 4 of 4, Block 2, Beehive 2, Toad 2, Glider 2, LWSS 2, Blinker **0** — so 7 of 8 patterns can produce a mutant that only the reverse inclusion kills, and the landed dump contains one: Pulsar's `(12, 9)` → `(9, 12)`. **This is what makes `features/steps/pattern-library.ts`'s bidirectionality load-bearing rather than belt-and-braces**, and it is the class the flat splitter structurally could not express — it never sees a tuple's two components, so it could never propose transposing them.

  **The honest residual, which is narrower than "parens are handled" — that is the reading to avoid.** `isTupleList` is anchored and total: a value that is not _wholly_ a fixed-arity numeric tuple list is rejected and **falls through to `mutateCommaList`, where it may still syntax-break**. That reaches more shapes than it sounds like — an item delimited by anything else (`[x, y]`, `{a, b}`, `<x, y>`, bare `0 0`), a doubly-parenthesised `((0, 0))`, a list mixing arities (`(1, 2), (3, 4, 5)`), and a paren list whose items are not numeric. The last of those is not hypothetical and is pinned: `mutation-rules.test.ts`'s PINNED table keeps `(2026-05-13, P3D), (1, 2)` **as the boundary fixture**, re-pinned to its syntax-breaking mutant, so the grammar's edge is a test rather than a claim. So a step parsing a comma-list column still owes the bidirectional check plus an explicit count — the count is what reports a shortened expected list, with the reverse inclusion catching it if the count is removed.

  **For exactly one of those shapes "may still syntax-break" is too weak: a paren pair with decimal components is a measured REGRESSION against the pre-slice code.** `TUPLE_LIST_SHAPE` requires `-?\d+`, so `(-32, -22.5)` — the app's own default camera offset, half-cell because 900 / 20 = 45 is odd — is coordinate-shaped, paren-delimited and **rejected**, falling to a `mutateCommaList` that is no longer paren-aware. `stripParenAffixes` used to expose `-32` to the integer rule and `-22.5` to the decimal rule and produce same-length numeric mutants; the fall-through shatters the punctuation instead. Two independent runs mutated that value under N seed keys and counted mutants reducing a **decimal-tolerant** pair regex's (`/\((-?[\d.]+),\s*(-?[\d.]+)\)/g`) match count below its baseline of 1: pre-slice `e2d4a63` scored **0/40** and **0/400**; the slice tip scored **30/40** (`product`'s keys, at the tuple slice's VERIFY) and **28/40, 285/400** (this adjudication's). Read the rate, not either constant — the keys differ, the same way this section's `[x, y]` row already differs between two passes. The harm is the `comma-list-mutants-are-all-syntax-breaking` class reopening for this one shape: such a mutant still **dies**, but via the parser silently dropping an unparseable item rather than via the assertion noticing a wrong coordinate.

  **Three things narrow that finding, and together they are why `tuple-grammar-rejects-decimal-components` was closed without code rather than actioned.** First, **the regex the count is taken under is part of the claim**. Under the repo's own pair grammar — `-?\d+`, in `features/steps/pattern-library.ts` and byte-identically in both PAIR oracles — `(-32, -22.5)` matches **zero pairs at baseline**, so that count is **0/40 on both trees** and the regression is invisible to every consumer that exists today. It is the same degeneracy that scores `[0, 0], [1, 1]` at 0/40 on both trees (a paren regex sees nothing to shorten), and reading either row as a pass is the error the split exists to prevent. Second, **the clean-to-broken claim does not extend to the other near-miss filed beside it**: `(0, 0)-(12, 12)` measures **6/40 pre-slice** against 27/40 at the tip, so the slice worsened a shape already partly broken rather than breaking a clean one — `stripParenAffixes` shaved one paren per fragment side and the interior fragment `0)-(12` matched neither, which is also why its pre-slice cleanliness on the decimal pair was incidental to a function never designed for decimals. Third, **no gate reports any of this in either direction**: a syntax-broken mutant still dies, so `npm run acceptance-mutation`'s score does not move when the class reopens or closes.

  **Re-open trigger, stated from both sides, because two roles can independently build the world where this bites and nothing mechanical will say so.** From `product`'s side: **an Examples cell that is paren-delimited and carries a non-integer numeric component.** Today all of `features/` holds four Examples headers — `coordinate`; `pattern | category | cells`; `state | neighbors | next state`; `x | y | expected center x | expected center y` — and **zero decimal values in any cell**; `cells` cannot legitimately go fractional since `CellKey` is integer, and `expected center x/y` is the blinker's centre _cell_, not a viewport centre. Note `ideas/candidates/decimal-mutant-magnitude-is-precision-independent.md`'s last open question proposes adding a decimal column, and the two are **disjoint** rather than coupled — this sentence claimed the opposite until `correct-decimal-coupling-claim`, and the inversion is the more dangerous direction because it reads as a warning while licensing the one column shape that measures nothing. Measured against the landed `VALUE_RULES` by tracing which entry fires: **`mutateDecimal` is reached exactly when a cell, or one of its trimmed comma-split fragments, is _wholly_ `-?\d+\.\d+`** — so `1.5` reaches it directly and `0.25, 0.5` reaches it through `mutateCommaList`'s recursion, while `(1.5, 2.5)` and `(-32, -22.5)` reach it **not at all**: `isTupleList` rejects the non-integer component, the comma-list rule claims the value instead, and each fragment carries a paren (`(1.5`, `2.5)`) that fails the decimal pattern and lands in `mutateString`. A tuple component cannot reach it either, `TUPLE_LIST_SHAPE`'s components being integer-only. So a column that trips this trigger is a column that **cannot** exercise `mutateDecimal`, and a column that exercises it cannot trip this trigger; adding the decimal column costs no tuple work in either direction. What it does still cost is a fractional _domain_ quantity for the column to be about, which is the altitude question the closing argument below turns on rather than anything in `scripts/`. From `scripts/`' side: **any widening of `TUPLE_LIST_SHAPE`'s `-?\d+`, or of the step's PAIR regex** — the three deliberately-mirrored copies must move in one slice or silently disagree, and widening also makes `mutateDecimal`'s filed `KNOWN DEFECT` reachable **through a tuple component**, which nothing does today (measured on a widened copy of the grammar: `(1.5, 2.5)` then dispatches `tupleList` and recurses to `decimal` on `2.5`). Read that as the mechanism and not as exclusivity — a bare `1.5` cell reaches `mutateDecimal` through the route that already exists, with no widening at all, which is the correction the sentence above records. Neither remedy the closed candidate weighed was free: widening the grammar drags `product`'s step regex with it into a two-role slice, and restoring paren-awareness in the fall-through reinstates the two-theories-of-a-coordinate-list problem `cells-column-has-two-parsers-and-neither-models-tuples` existed to remove. **What made closing right is not that the regression is small — it is that `.gherkin-lintrc`'s `no-restricted-patterns` bans `\boffset ?[xy]\b`, so the one genuinely fractional quantity this app has is precluded from the contract by the altitude linter rather than merely absent from it.** That is a claim about today's contract and not about the code, which is why the trigger is stated from both sides rather than left as "no column has this shape".

  **Three copies of the coordinate grammar exist, deliberately, and nothing mechanical checks they agree.** `tuple-list.ts` parses it structurally; `features/steps/pattern-library.ts` scans it with a lenient `matchAll` regex; and `tuple-list.test.ts` + `tuple-list.property.test.ts` each carry a **byte-identical mirror of the step's regex** as their oracle — deliberately mirroring the step rather than reusing `tuple-list.ts`'s own parser, since a mutator checked against its own parser is self-agreeing and proves nothing. No `ast-grep` rule is possible (matching is within one file; this is cross-file regex agreement) and an import-based test is out (`parseCellList` is not exported, and importing the step module executes `createBdd()` registration). The tether is comments naming each other, and system-level agreement is checked by `npm run acceptance-mutation` itself — which is the tool whose entire job that is.

  **`tuple-list.ts` never imports `mutation-rules.ts`; the component mutator is injected.** `mutation-rules.ts`'s `VALUE_RULES` entry imports `isTupleList`/`mutateTupleList`, so an import back would close a cycle — oxlint's `import/no-cycle` is an **error** here. The entry therefore passes `mutateValue` in as a `ValueMutator` parameter, on `src/equality/container-equality.ts`'s injected-comparator precedent. That is not merely cycle avoidance: it makes a component's mutation **defined as** recursion through `VALUE_RULES` (exactly what `mutateCommaList` does with its fragments) rather than a direct `mutateInteger` call that merely agrees with it today, so a rule later inserted ahead of the integer rule is picked up instead of silently diverging. `seeded-random.ts` is the shared leaf both files import (`RandomFn`, `seededRandom`, `nonzeroDelta`) and holds no mutation rule.

  Measured twice, independently, by mutating a four-item column of each shape under 40 seed keys and asking whether the mutant still parses as four well-formed items: the paren control is **40/40 preserved** and `((x, y))` is **0/40** in both runs — those two rows are the finding. The other-delimiter shapes come out at 0–3/40 depending on which 40 keys are drawn (`product`'s pass read `[x, y]` as 0/40, the architect review's as 1/40, same sample size and different keys), and the residual is incidental rather than arming: it is the free-text mutator happening to land outside the delimiters. **Read the two decisive rows, not the residuals** — a column that preserves its shape 39 times in 40 is not safe, it is a column whose next mutant is the old class again. The class is closed for the cell shape this repo currently writes, and for that shape only.

  **Which assertion actually reports which class was measured, in three runs, and the answer is asymmetric.** Each run hand-applied one mutant of the `Block` row to `features/pattern-library.feature` and ran `npm run test:e2e -- --project bdd --grep "Each pattern in the library has a category"` — 8 tests, 1 failed / 7 passed every time. (1) The old-class mutant (`…, a1, 1)`) is reported at the `toHaveCount` in `features/steps/pattern-library.ts`: `parseCellList` collects pairs with `matchAll`, so an unparseable fragment is silently dropped, `expected` is short by exactly one, and the count is reached first. (2) The new-class mutant (`…, (4, 1)`) is reported at the **first direction of the set equality**, naming the expected-but-absent `(4, 1)` — the count passes on the way through, because the list length never changed. (3) "Reported first" is not "the only thing that catches it", so the count was neutralised for that row and run (1) repeated: the old-class mutant is then caught by the **second** direction. (Those three assertions were that file's lines 107, 115 and 116 when this was run and are 123, 131 and 132 after `product` rewrote the step's comment block later in the same slice. They are cited by role rather than by line here for that reason: a line number in this paragraph is invalidated by an edit to a comment, which is the cheapest possible way for a measured claim to go stale.) So the set equality is the **sole** detector of the new, same-length class, and the count is the sole detector of nothing. Keep the count regardless, for the reason its own comment gives rather than for detection: it is the only **auto-retrying** assertion in the step, and every non-retrying read after it depends on it having settled the render. Deleting it trades a race for nothing — `previewCellPositions` and both `filter` reads are non-retrying, so the `toHaveCount` is what settles React's hover render before any of them happen.

  **The headline acceptance-mutation figure does not move across this change, and cannot — that is the single most misreadable thing here.** Both classes are lethal, so the run scores 100% on either side of the slice, and anyone comparing a before-and-after figure will conclude nothing happened. Measured: the old class is 8/8 short by exactly one item, which the count catches; the new class is 8/8 same-length carrying exactly one coordinate the table never named, which the first inclusion direction catches. What the slice bought is **which assertion earns the score** — the named-but-absent direction went from exercised by zero `cells` mutants to all eight — and a mutation score is a ratio over the mutants that die, not a record of what killed them. Expecting the split to move here was a framing error made twice while the slice was in flight; it is recorded so the next reader doesn't make it a third time, and it generalises: **when a fix changes the _kind_ of mutant a generator emits rather than how many die, no mutation score can see it.**
