**ARCHIVE — everything below describes a layer that no longer exists, and is kept for its method.** The vitest step layer was first removed from `npm run test:mutation` by `stryker-excludes-gherkin` (`ignorePatterns` keeping `features/` out of the sandbox) on the strength of the measurement below, and then deleted outright by `delete-step-test-layer`. So this is now doubly historical: the exclusion it argues for is belt-and-braces, and the layer it measures is gone. It stays because the reasoning is transferable — it is the only written account of _why_ a `killedBy` naming a step test never meant what it looked like, and that failure recurs the moment any runner compiles one logical case into several `test`s. Read it as method, never as a description of what the gate runs.

**The removal experiment below can no longer be run at all — there is nothing left to remove, since `features/` holds no vitest test.** It is recorded for its shape. When you need to know whether some layer is the sole killer of a mutant, a removal experiment names _candidates_ and nothing more; the verdict is hand-applying the mutant and running the whole unfiltered suite. Never trust Stryker's `killedBy` when it names a `features/**` test — against a step-per-test runner it is a false positive whenever a scenario's setup steps fall outside the covering set, which is the normal case rather than the exception.** Measured against Stryker 10.0.0 / vitest 4.1.10 / `@amiceli/vitest-cucumber` 7.0.0.

- **The removal experiment is still the right screen**, and a `coveredBy` screen is still wrong every time: all six `src/scrollbars.ts` mutants that survive once `features/**` is removed are `coveredBy` `scrollbars.test.ts` and `scrollbars.property.test.ts` and killed by neither, so `coveredBy` answers "covered, therefore fine" about mutants nothing kills. **The recipe inverted when the exclusion landed, and then went inert when the layer was deleted**: the arm that needed constructing became the one that puts the layer _back_, and a `"ignorePatterns": []` arm now readmits **zero tests**, so both arms collect the same set and the experiment has no signal left to give. It is two `--mutate`-scoped Stryker runs — the ordinary `stryker.config.json` against a copy of it carrying `"ignorePatterns": []` (and its own `tempDirName`, so the two sandboxes can't collide) — neither passing `--incremental`, for the reason the mutation-testing note in Commands gives. It used to be the reverse: a copy of `vite.config.ts` with `'features/**'` prepended to `sharedExclude`, selected via `{ "vitest": { "configFile": "vite.config.probe.ts" } }`. Don't reach for that form now; `ignorePatterns` is the one lever, and a `sharedExclude` probe would be subtracting a layer the sandbox no longer contains. What the experiment cannot do, in either direction, is separate real Gherkin coverage from a spurious Gherkin kill — **removing the layer removes the false kill along with the true one, so both present identically as "survives without `features/**`".**

- **`killedBy` naming a step test proved nothing, and can no longer happen at all** — the sandbox has no `features/` in it, and since `delete-step-test-layer` there is no vitest step test anywhere to name. The mechanism is kept because it is general: it is a property of a step-per-test runner meeting Stryker's covering-test filter, and it will recur the moment any layer compiles one logical case into several `test`s. A mutant run set `project.config.testNamePattern` to a regex built from the covering test names only (`node_modules/@stryker-mutator/vitest-runner/dist/src/vitest-test-runner.js`), and vitest-cucumber compiles every _step_ into its own `test`. A scenario's `Given`/`And` steps usually touch a different module than its `When`, so they are not in the covering set, get filtered out, and the `When` then runs on empty closure state and throws. That failure is scored as a kill. Reproduce it on **unmutated** source in one command — `npx vitest run features/grid-scrollbars.steps.test.ts -t "the scrollbars are drawn for an 800 by 600 pixel viewport"` gives 5 failed / 33 skipped with `TypeError: Cannot read properties of undefined (reading 'size')`, and `npx vitest run features/cell-life-and-death.steps.test.tsx -t "I toggle the cell at"` fails the same way on an unrendered `board`. Those "killer" tests fail whether or not a mutant is active. **Both `-t` patterns quote live step text, so `product` rewording a step silently retires the command** — which is what happened to the first one (`prune-gherkin-to-domain-language` renamed that `When`), and the failure mode is the dangerous direction: a `-t` matching nothing exits **0** with every test skipped (measured: 38 skipped, 0 run), so a stale repro reads as "the mechanism has been fixed" rather than as a broken command. Check the run actually collected tests before concluding anything from it.

- **The verdict is a direct measurement**: apply the mutation to `src/` by hand, run `npx vitest run` with no filter at all, and read which files fail. Done for all ten mutants the Gherkin layer has ever been credited with killing (6 in `scrollbars.ts`, 2 in `gameOfLife.ts`, 1 each in `camera.ts` and `liveCellStore.ts` — the full table is in the `prune-gherkin-to-domain-language` adjudication commit): **all ten leave the suite green.** Five are equivalent mutants, five were simply untested and now carry unit tests. **The Gherkin layer's contribution to the Stryker score is zero mutants** — the measured form of what this layer's purpose paragraph already says in prose, and the finding the `ignorePatterns` exclusion acts on: **the counterfactual is now the default**, so a full-tree run no longer has `features/**` to remove. The removal-experiment run scored **98.70%** against `break: 85` on the tree it was measured on; no figure for the current tree is written here, because `hardener`'s `npm run test:mutation:full` on the landed change is what produces one, and a literal copied forward here would be stale before the next slice lands. (Two correct numbers already went stale inside this one slice — 98.70% and 99.00%, each right about a different tree.) **That is not a licence to delete scenarios.** Unit coverage is what makes a deletion _safe_; what makes one _permissible_ is that the promise survives in `features/**` at domain altitude — already stated by a sibling scenario, or restated in the feature it actually belongs to. "A unit test covers it" discriminates nothing, since by this measurement it is true of every scenario in the directory. (Ruled in `prune-gherkin-to-domain-language`'s review, over the two whole outlines that slice deleted rather than merely un-tabled: one named a browser event field no user can observe, the other moved to `camera-pan-and-zoom` and is asserted there.)

**The black-box step form: three facts a conversion had to be built around — ARCHIVE.** The layer they describe was deleted by `delete-step-test-layer` and **no further conversion will ever happen**, so none of the three is a constraint on anything today. Facts one and three are kept because their subject is not the layer: one is a measured property of a third-party runner and the standing warning against reasoning about a lifecycle instead of measuring it (`architect.md`'s CONTRACT-mode question 4 leans on it), and three is a fact about `src/` that is still exactly true. Fact two is kept because its principle outlived its subject — see its own note.

_First, `@amiceli/vitest-cucumber` compiled every Gherkin **step** into its own vitest `test`, not every scenario._ Measured on 7.0.0, on a tree where that layer still existed: `cell-life-and-death.feature` collected **48 tests, not 13**, with `ancestorTitles` naming the scenario and the test itself named for the step. `src/test-setup.ts` installs a global `afterEach(cleanup)`, so **that cleanup fires _between_ a scenario's `Given` and its `When`** — an RTL-`render`ed tree cannot survive one scenario, and the failure reads as a bare `expected null not to be null` in the `Then`, which looks nothing like a lifecycle problem. `features/harness/board.tsx`, the shared harness core, works around it by owning its own `createRoot` container (`cleanup()` is then a no-op for the board, and `mountBoardRequiring()` unmounts the previous one), which is why it does not call `render()`. There is no future conversion to inherit it, and the `acceptance` project the count was read off no longer exists. **What generalises is the method, not the number**: when a contract will be executed through someone else's runner, read the collected-test count off an actual run rather than reasoning about what the runner probably does. A DESIGN pass asserted the opposite of the fact above from plausible reasoning and was wrong.
