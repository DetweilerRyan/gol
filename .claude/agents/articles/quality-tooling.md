# Article: Quality Tooling: crap4ts, gherkin-lint, and the scripts/ programs

**Audience:** cleaner, architect, hardener - **Read when:** on an unexpected crap4ts number, when touching .gherkin-lintrc or `.oxlintrc.json`, on a `jsdoc/*` lint finding, or at hardener stages 6-8.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 101-104, 221-223, 261-263, 269-270, 275-282. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

**crap4ts is patched locally (`patches/crap4ts+1.0.1.patch`) and `crap4ts` is pinned to an exact version because of it.** Upstream, crap4ts pairs an AST function span to an Istanbul coverage span only when they overlap by ≥80% of the AST span's lines (`OVERLAP_THRESHOLD = 0.8`), and Istanbul records `fnMap[k].loc` as the function _body_ — starting at the opening brace, never consulting `fnMap[k].decl`. A signature Prettier had to break across lines therefore pushes the two spans apart far enough that no candidate matches, and the function is reported at 0% coverage with an inflated CRAP score even though it is fully exercised. The patch mirrors upstream PR [breezy-bays-labs/crap4ts#37](https://github.com/breezy-bays-labs/crap4ts/pull/37) (open and unmerged since 2026-04-07; `crap4ts@1.x` is in maintenance mode pending a Rust-backed v2 rebuild, so it may never land): `findCandidates` now also accepts a candidate when either span fully contains the other, bypassing the ratio gate in that case. Ranking (`contains` → `ratio` → `nameMatch`) is unchanged.

Three consequences follow. First, the patch targets a **content-hashed tsup chunk** (`dist/chunk-W6RIPRFD.js` plus its CJS twin `dist/chunk-OHOZMDXW.cjs`), so any crap4ts release renames the file and the patch stops applying — which is why `package.json` pins `"crap4ts": "1.0.1"` with no caret, and why **upgrading crap4ts means regenerating the patch by hand**, not just bumping the range. Second, `patch-package` runs from `postinstall`, so the patch is only in effect after a normal `npm install`/`npm ci`. Third, `src/patternLibrary.ts`'s `patternCellPositions` keeps its four-line signature deliberately: it is the live regression fixture for this patch. If the patch ever stops applying, that row drops back to 0.0% in `npm run crap4ts` — don't "tidy" the signature onto one line, and don't chase the 0% as a coverage gap if it reappears. `npm run crap4ts -- --verbose` distinguishes the two cases: an `[unmatched-no-coverage]` warning naming the function means the matcher missed it (patch not applied), whereas a genuine gap shows as a matched row with a low percentage. There is a third cause of the identical `[unmatched-no-coverage]` warning, unrelated to the patch, and it is the one that has actually bitten repeatedly: **`crap4ts` reads `coverage/coverage-final.json` off disk and never regenerates it**, so any source edit since the last `npm run test:coverage` is scored against stale line spans. This is broader than a missing entry for a newly-landed file — _any_ line-shifting edit, including a pure comment change, moves a function's AST span away from the recorded coverage span, and the two failure modes look nothing alike: some functions orphan at 0.0% (indistinguishable from the patch-not-applied case above), while others match an old, shifted entry and read a spurious 100%. The remedy is the same either way, and it is a precondition rather than a fix: **run `npm run test:coverage` (or `npm run test:coverage:scripts` before `npm run crap4ts:scripts`) whenever source has changed since the last coverage run** — which, in a role's pass, is essentially always. (The many `[unmatched-no-ast]` warnings under `--verbose` are unrelated and expected — they are coverage entries in files outside crap4ts's `include` list, plus nested functions crap4ts does not score.)

`scripts/` is TypeScript, not JavaScript, and is its own project — separate `tsconfig.scripts.json`, `vitest.scripts.config.ts`, `crap4ts.scripts.config.ts`, and `stryker.scripts.config.json` from the ones covering `src/`/`features/` above. It's the tooling every other role's quality gate runs on, so it's held to the same CRAP threshold (6) as `src/`, via its own parallel commands (`npm run test:scripts`, `npm run test:coverage:scripts`, `npm run crap4ts:scripts`, `npm run dry4ts:scripts`, `npm run test:mutation:scripts`) — see `.claude/agents/articles/engineering.md`'s "Working inside scripts/" section for exactly which command each pipeline role substitutes for its usual `src/`-scoped one.

Its layout is two levels and no more: **`scripts/<program>/` holds one program's own modules** (its `run.ts` shell plus the pure modules that shell delegates to), and **a file at `scripts/` root is shared by two or more programs**. `scripts/feature-files.ts` is the current example — `listFeatureFiles` is the one place that answers "which `.feature` files exist", used by both `acceptance-mutation` and `gherkin-dry-checker`, which previously carried two independent hardcoded copies of that list that went stale separately. `listFeatureFiles` globs `**/*.feature` **recursively** and returns paths relative to the features directory — bare basenames while the tree is flat, `sub/name.feature` once it isn't — which is why every call site's `path.join(FEATURES_DIR, file)` needed no change when discovery went recursive. It throws in two deliberately distinguishable ways rather than returning an empty array, and both throws are load-bearing rather than tidy: `globSync` returns `[]` for a missing `cwd` exactly as it does for a real but empty directory, so without the `existsSync` guard a wrong path misroutes into the `No .feature files found in <path>` message instead of naming the actual problem — and without the empty-list throw at all, a features directory that resolved to nothing would run zero targets, summarize to a defined `100.0%`, and exit 0 reporting a perfect score about nothing. Shared root modules are ordinary product code and sit inside the gates exactly like a program's own modules; the one exception is `scripts/test-support.ts`, which is test infrastructure and is excluded by the same `**/test-support.ts` glob in `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` that already excludes `scripts/perf-report/test-support.ts`. `gate-report.ts` is the second product one: it exports `checkNonEmpty` and nothing else — the "this program found nothing to check, and that is itself a failure" guard that `ast-grep-rule-check`'s `checkAnyRulesFound` and `reference-check`'s `checkAnyFilesScanned` each carried an independent, byte-identical copy of until `dry4ts:scripts` flagged the pair. Each call site still supplies its own check id and message, so the shared file holds the shape of the guard and none of the vocabulary. **Imports run program → shared and never the reverse**, which is what keeps the shared file safe to change: a root module that reached back into a program directory would couple every other program to that program's internals. **That direction is now checked mechanically**, on this sentence's own trigger — the third shared root module rather than a first violation, since there has never been one. `rules/no-downward-import-in-scripts.yml` fires on any relative import under `scripts/` that descends through a directory segment. The prediction above held: a `files:` glob can't express "`scripts/` root only", because ast-grep's `*` crosses `/`, so the rule's measured reach is root -> program _and_ a program growing a third level, both of which are invariants this paragraph states. The throwaway probe was run in each of those two positions; that measurement, and the program -> program shape the rule deliberately leaves to prose, are in `.claude/agents/articles/ast-grep-rules.md`.

- `scripts/gherkin-dry-checker/` — advisory-only; scans all `.feature` files for step-text vocabulary duplication/drift, discovering them through `scripts/feature-files.ts` (see above) rather than the hardcoded list it used to carry. Always exits 0 on a successful run (report-only), writes to `reports/gherkin-dry/report.json`.
- `scripts/halstead4ts/` — runs `fta-cli` against the same files as `crap4ts.config.ts`'s `include` list and prints a Halstead (volume/difficulty/effort/bugs) + FTA Score table alongside crap4ts's per-function CRAP table. FTA only reports at file granularity (no per-function breakdown), so this is a second, coarser report rather than something merged into crap4ts's output — and since FTA's own score formula isn't published, it's report-only like `gherkin-dry-checker`, never a CI gate. `run.ts` resolves `crap4ts.config.ts`'s own `include`/`exclude` globs rather than keeping a copy of the file list — the two used to be hand-synchronized arrays of the same 21 paths, and a list like that goes stale silently: a module missing from it is simply never reported on, and nothing fails. fta-cli returns no analysis at all (an empty array, not a zeroed-out one) for any file at or under its own size floor — measured at ≤6 code lines, comments not counted — so a file that small renders as an explicit `not scored (under FTA size floor)` row rather than crashing the tool or, worse, vanishing from the report; `src/equality/is-strict-equal.ts` is the first file to hit it.
- `scripts/perf-report/` — turns the raw `RawScenarioSample` JSON files `perf/` writes under `reports/perf/raw/` into `reports/perf/latest.md`/`latest.json`/`history.jsonl`. Report-only, no thresholds. This is where **every** median, percentile, ratio, and unit conversion in the perf harness lives — `perf/` itself computes none, because `perf/` is outside the gates and a wrong statistic there would be silent and plausible-looking. The boundary between the two is a file on disk, not a module import: `import type` crosses it (erased at compile time), a value import never may, in either direction, and `rules/no-value-import-across-perf-boundary.yml` checks that mechanically. It's also a real compiler boundary — `perf/` is in `tsconfig.app.json` (`moduleResolution: "bundler"`, `lib: DOM`) and `scripts/` in `tsconfig.scripts.json` (`nodenext`, no DOM).

**Before proposing a new program here, search for an existing tool first.** A bespoke checker in this directory pays every gate this section's opening paragraph lists, and becomes permanent maintenance, so the bar is whether anything off the shelf already does the job. `orchestration.md` states the habit and why a search that turns nothing up is still worth its cost.

**`scripts/` has exactly one vitest config and therefore exactly one project, which makes the `*.property.test.ts` suffix mean something different here than it does in `src/`.** `scripts/acceptance-mutation/tuple-list.property.test.ts` (added by `comma-list-mutants-are-all-syntax-breaking` as `mutation-rules.property.test.ts`, renamed when `cells-column-has-two-parsers-and-neither-models-tuples` moved its subject into `tuple-list.ts`, and the first of its kind here) is collected by `vitest.scripts.config.ts`'s ordinary `scripts/**/*.test.ts` include and runs inside `npm run test:scripts` alongside every unit test — measured. In `src/` that suffix selects the separate `property` vitest project; in `scripts/` it is a naming convention only, and the src-side project cannot reach it because `sharedExclude` subtracts `scripts/**`. Two consequences. There is **no** `test:property:scripts` command and no role gains an obligation — see `.claude/agents/articles/engineering.md`'s "Working inside `scripts/`". And do **not** "fix" the apparent inconsistency by widening the src-side `property` project to reach `scripts/`: that project runs under `vite.config.ts` — jsdom-adjacent settings, the React plugin chain, `src/`'s coverage directory — which is the whole reason `vitest.scripts.config.ts` exists, and the `sharedExclude` entry for `scripts/**` is what keeps the two suites out of one process. (That entry is **not** one of the two the merge protocol's mutation-invariant predicate leans on — those are `ideas/**` and `.claude/**`, the two `vite.config.ts`'s own "Both entries below" comment scopes itself to. `scripts/**` is absent from the predicate's allowlist, so a `scripts/`-only diff never earns the exemption and always runs the full gate.)

`.gherkin-lintrc` is a ninth checker, over `features/*.feature` rather than over TypeScript, and it **gates** (`npm run gherkin-lint`, nonzero on any finding) for `product`, the only role that runs it. Twenty-one of `gherkin-lint-plus`'s registered rules are on. Four facts about it that are easy to get wrong, all measured against the installed copy:

- **The package ships a `duplicate-state` rule file that is not in its registry** (`dist/rules/registry.js`), so naming it in the config aborts the run with `Rule "duplicate-state" does not exist`. The registered set is 31 rules, not the ~35 the `dist/rules/` listing suggests.
- **`name-length`'s and `max-scenarios-per-file`'s library defaults do not fit this repo — and note only the first of those two caps is derived the way the next sentence describes** — at defaults they report 21 findings against features nobody considers wrong. The caps here are derived from Prettier's 120-char print width (a step line is indented 4 plus its keyword, leaving ~110 for the text; a scenario line is indented 2 plus `Scenario Outline: `, leaving ~100), not fitted to the current text. `max-scenarios-per-file` runs with `countOutlineExamples: false`, because the quantity this repo actually budgets — acceptance mutants — is measured exactly by `npm run acceptance-mutation` and a blunter proxy for it would only ever be tuned.
- **`no-restricted-patterns` compiles every pattern with `new RegExp(pattern, 'i')`, unconditionally.** Case is therefore not available as a signal: a camelCase-identifier detector like `\b[a-z][a-z0-9]*[A-Z]` matches every ordinary word and reported 184 findings when trialled. The list has to be an enumerated vocabulary, not a shape.
- It reads **feature/rule/background/scenario names and descriptions and step text**, and never Examples headers or cells. That is not a hole in practice, because `no-unused-variables` forces every header to appear in some step's `<placeholder>`; the two rules together reach the whole table.

**`no-restricted-patterns`' pattern list belongs to `architect`, in the same sense `rules/*.yml` does**, even though it lives in a config file `product` otherwise owns. It mechanises the domain-altitude judgment — implementation vocabulary must not leak into the contract — and its failure mode is someone widening the list to clear a finding, which is the same move as narrowing a fast-check arbitrary or weakening an ast-grep rule. A role that hits a pattern it believes is wrong routes it back to `architect` rather than editing the list. The list has **two categories**. Most entries name a field, type, or function of a `src/` module (`offsetX`/`offsetY`, `cellSize`, `ScrollbarMetrics`' `thumbRatio`/`thumbOffsetRatio`, `ScrollbarMetrics` itself, `ContentBounds`, `VisibleRange`'s `minX`/`maxX`/`minY`/`maxY`, world-space coordinates, `cellKey`, and `should return`). Three more joined that category in `wheel-zoom-ignores-magnitude-and-pinch`'s CONTRACT pass: `delta` — deliberately unanchored at its end, so one pattern reaches `deltaX`, `deltaY`, `deltaMode` and the bare noun — plus `wheel event` and `zoom factor`, the latter for `camera.ts`'s `ZOOM_FACTOR`. They were added for the same reason as the ARIA four in `ast-grep-rules.md`, one input channel over: that slice is the first to make the contract talk about **how far** a wheel was rolled, and the natural phrasing for that reaches straight for the `WheelEvent` field names. `ctrl key` and `shift key` were considered alongside them and deliberately **rejected** — they name physical keys a user presses, and `no-restricted-patterns` compiles every pattern case-insensitively, so the list cannot tell `shiftKey` from "holding the shift key"; restricting them would ban the plainest English available for the gesture. Four name **markup and ARIA vocabulary instead** — `aria-`, `role=`, `tab index`/`tabindex`, `gridcell` — which belong to no `src/` module at all and are implementation vocabulary all the same; they were added in `collapse-dead-cell-layer`'s CONTRACT pass, ahead of the first `.feature` about keyboard and screen-reader behaviour, because that is the feature whose natural phrasing reaches for them. Adding to this list is the **safe** direction (it narrows what a contract may say); widening it to clear a finding is the move the paragraph above forbids. All four — and all three of the wheel entries above — were shown to fire against a planted probe feature before landing, each reported **by its own pattern name** rather than merely turning the run red, and each first checked against the seven existing `.feature` files for a clean baseline (a pattern that fires on the contract as it stands is a dirty baseline, and the fix is narrowing the pattern, never editing `product`'s text). The probe feature is deleted in the same command that runs the lint: a `.feature` with no step definitions makes `bddgen` exit 1 having generated **nothing at all**, so a probe left behind takes down every feature's generated spec rather than its own. Same obligation an `ast-grep` rule's fixture carries — a pattern that matches nothing is indistinguishable from a clean `features/`. Verbs are deliberately **not** restricted: `computed` reads as implementation but "the next generation is computed" is a statement about the game, and restricting it would drag the one already-converted feature into every prune's scope for no altitude gain. Neither is `live cells`, which is a type name (`LiveCells`) and simultaneously Conway's own ubiquitous language — the clearest example of why this list is enumerated by hand rather than derived.

## The oxlint JSDoc tier — `.oxlintrc.json`'s `jsdoc/*` rules

**Ratified by `architect` in `oxlint-native-jsdoc-tier` (2026-09-07), and owned by it thereafter, in the same sense `no-restricted-patterns`' list above is** — the rule set mechanises `doc-comments.md`'s authoring conventions, so widening or relaxing it to clear a finding is the same move as narrowing a fast-check arbitrary. A role that hits one of these and believes it is wrong routes it to `architect` rather than editing the config. oxlint 1.78.0 ships **23** native `jsdoc` rules; **six** are on, all at `error`, and the other seventeen are declined on the record below.

**Two ways this tier can be silently inert, both measured, both exiting 0.** They are the same failure shape this repo already documents for a Stryker `ignorePatterns` glob, a vitest `include` and a `-t` pattern that match nothing — the command reports success and the thing you asked about never ran.

- **The `plugins` entry.** With all six rules present at `error` and the `settings` block intact but `"jsdoc"` removed from `plugins`: **exit 0, zero findings, no warning.** The rules are read, accepted, and never run. `.oxlintrc.json` carries a comment saying so at the site, which is measured safe — oxlint parses the JSONC, `npx prettier --write` preserves the comment, and nothing else in the repo reads that file.
- **Severity.** An oxlint `warn` **exits 0** (measured: the same planted `/** */` scores `warning` + exit 0 at `warn`, `error` + exit 1 at `error`). Every role reads `npm run lint` by its exit code, so a jsdoc rule at `warn` is a finding nobody will ever act on. That, not the `rules/*.yml` convention, is why these are `error`: `npm run ast-grep` is report-only and read by its output, while `npm run lint` is a gate read by `$?`, so the two configs are answering different questions. The baseline was clean when this landed, so `error` cost no migration — a one-time window that is now spent.

**Enabling the plugin also activates a default rule set at `warn`** — measured, `check-tag-names`, `no-defaults` and `require-property` fire without being named in `rules` — and since `warn` exits 0 that set gates nothing. So the explicit severities are what make this tier real, not decoration. `require-property` is declined below yet remains default-on; if it ever appears it is advisory noise on a block that `check-tag-names` is already erroring about, and the response is to turn it off rather than to write an `@property`.

### The six, and what each catches

Every one was shown firing **through `npm run lint` itself** against a planted fault, in `src/`, and two of them additionally in `scripts/` and `features/` — a rule that matches nothing reports nothing and is indistinguishable from clean prose, exactly as an ast-grep rule without a failing fixture has not been shown to work. The battery: exit 1, all six named.

| rule                          | catches                                                                                                                                                  |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check-tag-names`             | a misspelled or non-JSDoc tag, plus the closed table's banned vocabulary — below                                                                         |
| `no-blank-blocks`             | `/** */` — the degenerate block a presence-only "every export is documented" rule would accept, which is why that rule was rejected when it was proposed |
| `no-defaults`                 | `@param [a=1]` — a default value restates the signature and fails rule 5's information test                                                              |
| `require-param-description`   | `@param a` naming a parameter and saying nothing — rule 5's named defect, the one `Cache.insert` actually carried                                        |
| `require-returns-description` | a bare `@returns`                                                                                                                                        |
| `require-throws-description`  | a bare `@throws`                                                                                                                                         |

**`check-tag-names` runs with `typed: true` plus three `tagNamePreference` bans, and both halves were measured rather than assumed.** At defaults it enforced only **2 of the 5** tags `doc-comments.md` rule 5 names as not written here — `@remarks` and `@defaultValue` fail because they are not JSDoc vocabulary at all, while `@deprecated`, `@internal` and `@todo` are standard JSDoc and passed. `settings.jsdoc.tagNamePreference` accepts `false` as a ban (schema `TagNamePreference` admits a boolean), and banning those three takes it to **5 of 5**. `typed: true` bans the TypeScript-redundant family wholesale — measured on `@abstract` ("redundant outside ambient contexts") and `@typedef` ("redundant when using a type system") — and is silent on all five sanctioned tags, which was checked directly rather than inferred.

**Read the result at its actual scope: the closed table is _not_ mechanically enforced, and it cannot be.** `definedTags` is an **additive** allowlist, so there is no restrictive form; the bans are a blocklist over a ~65-tag vocabulary, closing the three tags a writer is actually tempted by and leaving the rest of standard JSDoc permitted. What is now mechanised is misspellings, non-JSDoc tags, the TS-redundant family, and the article's own named five. The table itself remains an `architect` ruling enforced by review. Admitting a tag means editing both `doc-comments.md`'s table and this config — `@deprecated` is the article's named likeliest candidate, and banning it here is deliberately the thing that makes a future admission a ruling rather than a drift.

**The `scripts/**` override does not shield any of this, and neither does `features/`.** That override declares its own `plugins` array omitting `jsdoc`, but a top-level plugin plus a top-level rule fires inside it anyway — and so does the top-level `settings` block, measured with a planted `@internal` in `scripts/feature-files.ts` that `tagNamePreference` correctly reported. A planted `@bogustag` in `features/screenplay/viewport.ts` fires too, so this tier binds `product`'s TypeScript exactly as it binds `src/`.

### The limit that matters most: oxlint sees only line-leading tags

**`doc-comments.md` rule 9's whitespace-`@` hazard is only half closed, and the closed half is the half that was never the surprising one.** Measured with a planted `@bogustag`: oxlint's JSDoc parser recognises a tag **only at the start of a JSDoc line** (leading whitespace tolerated) and is **blind to a mid-line one**, while TypeScript's hover parser recognises a tag wherever `@` is whitespace-preceded, anywhere in the block. So `* Uses the @fast-check/vitest package` — prose that TS splits into a `@fast-check` tag, the exact class that cost `jsdoc-in-scripts` three hand-rewording commits — passes `npm run lint` silently. The line-leading form, including one inside an `@example` fence, is caught.

**A clean `npm run lint` is therefore not evidence that a JSDoc block hovers as written.** Backticking every `@`-prefixed token remains the only guard on the mid-line half, and it stays a human discipline. Closing it needs `escape-inline-tags`, which is not native — see the alpha-tier note below.

### The seventeen declined, and why

The three groups below partition the seventeen exactly — 5 + 8 + 4 — against the 6 enabled, and the arithmetic is stated because a count that does not add up is the first thing to rot. The selection principle is mechanical rather than taste, and it has one clause: **a rule earns its line when it can fire on a fault the other five cannot, and when its trigger vocabulary is either tag-agnostic or inside `doc-comments.md`'s closed table.** Three groups fall out of it.

- **Five red the tree, and each contradicts a written convention.** `require-param` (155 findings) and `require-returns` (148) are coverage mandates, which rule 5 forbids outright — a tag that restates the signature is deleted, not required — and `doc-comments.md` says in as many words that documenting every undocumented export is not this convention. `require-param-type` (5), `require-returns-type` (10) and `require-throws-type` (20) mandate a JSDoc `{Type}` slot that duplicates the signature, and `require-throws-type` mandates the exact `@throws {CacheError}` form rule 9 measured as **broken** — `@throws` and `@see` print a braced type verbatim, braces and all. Enabling it would require the repo to write the one form its own measurement forbids.
- **Eight are conditional on a tag the table excludes**, so enabling them would police the well-formedness of vocabulary that must never appear — legitimising it rather than banning it: `check-access` (`@access`), `implements-on-classes` (`@implements`), `check-property-names`, `require-property`, `require-property-description`, `require-yields`, `require-yields-description`, and `empty-tags`. Two of them, `require-property` and `require-yields`, are coverage mandates that would demand a tag the table forbids — a documented generator would be told to add `@yields`. `empty-tags` is the odd one: its void-tag vocabulary (`@abstract` and kin) is entirely outside the table, and its remedy direction is "empty the tag" where the convention says delete it.
- **Four are strictly subsumed or inert.** `require-param-name` fires **only** on a completely bare `@param`, which `require-param-description` also catches — measured, and structurally so, because the parser takes the first token after `@param` as the name, so `@param must be positive` yields the name `must` and neither rule fires. There is no fault it uniquely reports. `require-property-name`, `require-property-type` and `require-yields-type` are inert by the same vocabulary argument as the group above — listed here rather than there because each is conditional on a tag that is itself already conditional on one the table excludes, so nothing would reach them even if `@property`/`@yields` were admitted. Reopen `require-param-name` if a parser change ever admits a nameless `@param` carrying text.

**The alpha tier is deliberately not here.** `escape-inline-tags`, `informative-docs`, `no-undefined-types`, `normalize-see-links`, `match-description` and `no-bad-blocks` are `eslint-plugin-jsdoc` rules with no native oxlint port; reaching them means oxlint's alpha JS-plugin API plus an alias, since the `jsdoc` name collides with the native plugin. That is a separate evaluation with a real dependency cost, and none of it is needed to hold what this tier holds.

**What no lint rule here reaches at all:** the dead file, symbol and test-title references in `//` comments that motivated this work. Every rule above operates **inside a JSDoc block**, and those references are overwhelmingly in `//` comments — which is why this tier is complementary to `scripts/reference-check/` (`npm run reference-check`, CLAUDE.md's programs section) rather than a substitute for it. That checker covers the file and symbol halves of the motivating problem; the test-title half was scoped out at design time (`checkCitedSymbolExists` does not scan a quoted test title) and remains a gap this tier does not close either.
