# Article: Quality Tooling: crap4ts, gherkin-lint, and the scripts/ programs

**Audience:** cleaner, architect, hardener - **Read when:** on an unexpected crap4ts number, when touching .gherkin-lintrc, or at hardener stages 5-7.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 101-104, 221-223, 261-263, 269-270, 275-282. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

**crap4ts is patched locally (`patches/crap4ts+1.0.1.patch`) and `crap4ts` is pinned to an exact version because of it.** Upstream, crap4ts pairs an AST function span to an Istanbul coverage span only when they overlap by ≥80% of the AST span's lines (`OVERLAP_THRESHOLD = 0.8`), and Istanbul records `fnMap[k].loc` as the function _body_ — starting at the opening brace, never consulting `fnMap[k].decl`. A signature Prettier had to break across lines therefore pushes the two spans apart far enough that no candidate matches, and the function is reported at 0% coverage with an inflated CRAP score even though it is fully exercised. The patch mirrors upstream PR [breezy-bays-labs/crap4ts#37](https://github.com/breezy-bays-labs/crap4ts/pull/37) (open and unmerged since 2026-04-07; `crap4ts@1.x` is in maintenance mode pending a Rust-backed v2 rebuild, so it may never land): `findCandidates` now also accepts a candidate when either span fully contains the other, bypassing the ratio gate in that case. Ranking (`contains` → `ratio` → `nameMatch`) is unchanged.

Three consequences follow. First, the patch targets a **content-hashed tsup chunk** (`dist/chunk-W6RIPRFD.js` plus its CJS twin `dist/chunk-OHOZMDXW.cjs`), so any crap4ts release renames the file and the patch stops applying — which is why `package.json` pins `"crap4ts": "1.0.1"` with no caret, and why **upgrading crap4ts means regenerating the patch by hand**, not just bumping the range. Second, `patch-package` runs from `postinstall`, so the patch is only in effect after a normal `npm install`/`npm ci`. Third, `src/patternLibrary.ts`'s `patternCellPositions` keeps its four-line signature deliberately: it is the live regression fixture for this patch. If the patch ever stops applying, that row drops back to 0.0% in `npm run crap4ts` — don't "tidy" the signature onto one line, and don't chase the 0% as a coverage gap if it reappears. `npm run crap4ts -- --verbose` distinguishes the two cases: an `[unmatched-no-coverage]` warning naming the function means the matcher missed it (patch not applied), whereas a genuine gap shows as a matched row with a low percentage. There is a third cause of the identical `[unmatched-no-coverage]` warning, unrelated to the patch, and it is the one that has actually bitten repeatedly: **`crap4ts` reads `coverage/coverage-final.json` off disk and never regenerates it**, so any source edit since the last `npm run test:coverage` is scored against stale line spans. This is broader than a missing entry for a newly-landed file — _any_ line-shifting edit, including a pure comment change, moves a function's AST span away from the recorded coverage span, and the two failure modes look nothing alike: some functions orphan at 0.0% (indistinguishable from the patch-not-applied case above), while others match an old, shifted entry and read a spurious 100%. The remedy is the same either way, and it is a precondition rather than a fix: **run `npm run test:coverage` (or `npm run test:coverage:scripts` before `npm run crap4ts:scripts`) whenever source has changed since the last coverage run** — which, in a role's pass, is essentially always. (The many `[unmatched-no-ast]` warnings under `--verbose` are unrelated and expected — they are coverage entries in files outside crap4ts's `include` list, plus nested functions crap4ts does not score.)

`scripts/` is TypeScript, not JavaScript, and is its own project — separate `tsconfig.scripts.json`, `vitest.scripts.config.ts`, `crap4ts.scripts.config.ts`, and `stryker.scripts.config.json` from the ones covering `src/`/`features/` above. It's the tooling every other role's quality gate runs on, so it's held to the same CRAP threshold (6) as `src/`, via its own parallel commands (`npm run test:scripts`, `npm run test:coverage:scripts`, `npm run crap4ts:scripts`, `npm run dry4ts:scripts`, `npm run test:mutation:scripts`) — see `.claude/agents/articles/engineering.md`'s "Working inside scripts/" section for exactly which command each pipeline role substitutes for its usual `src/`-scoped one.

Its layout is two levels and no more: **`scripts/<program>/` holds one program's own modules** (its `run.ts` shell plus the pure modules that shell delegates to), and **a file at `scripts/` root is shared by two or more programs**. `scripts/feature-files.ts` is the current example — `listFeatureFiles` is the one place that answers "which `.feature` files exist", used by both `acceptance-mutation` and `gherkin-dry-checker`, which previously carried two independent hardcoded copies of that list that went stale separately. `listFeatureFiles` globs `**/*.feature` **recursively** and returns paths relative to the features directory — bare basenames while the tree is flat, `sub/name.feature` once it isn't — which is why every call site's `path.join(FEATURES_DIR, file)` needed no change when discovery went recursive. It throws in two deliberately distinguishable ways rather than returning an empty array, and both throws are load-bearing rather than tidy: `globSync` returns `[]` for a missing `cwd` exactly as it does for a real but empty directory, so without the `existsSync` guard a wrong path misroutes into the `No .feature files found in <path>` message instead of naming the actual problem — and without the empty-list throw at all, a features directory that resolved to nothing would run zero targets, summarize to a defined `100.0%`, and exit 0 reporting a perfect score about nothing. Shared root modules are ordinary product code and sit inside the gates exactly like a program's own modules; the one exception is `scripts/test-support.ts`, which is test infrastructure and is excluded by the same `**/test-support.ts` glob in `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` that already excludes `scripts/perf-report/test-support.ts`. **Imports run program → shared and never the reverse**, which is what keeps the shared file safe to change: a root module that reached back into a program directory would couple every other program to that program's internals. Nothing checks that direction mechanically yet — with two shared files it's prose, and `architect` should encode it as an ast-grep rule at the first violation or the third shared module, whichever comes first (a `files:` glob can't express "`scripts/` root only", since ast-grep's `*` crosses `/`, so that rule needs the throwaway-probe measurement this file describes for the domain rules).

- `scripts/gherkin-dry-checker/` — advisory-only; scans all `.feature` files for step-text vocabulary duplication/drift, discovering them through `scripts/feature-files.ts` (see above) rather than the hardcoded list it used to carry. Always exits 0 on a successful run (report-only), writes to `reports/gherkin-dry/report.json`.
- `scripts/halstead4ts/` — runs `fta-cli` against the same files as `crap4ts.config.ts`'s `include` list and prints a Halstead (volume/difficulty/effort/bugs) + FTA Score table alongside crap4ts's per-function CRAP table. FTA only reports at file granularity (no per-function breakdown), so this is a second, coarser report rather than something merged into crap4ts's output — and since FTA's own score formula isn't published, it's report-only like `gherkin-dry-checker`, never a CI gate. `run.ts` resolves `crap4ts.config.ts`'s own `include`/`exclude` globs rather than keeping a copy of the file list — the two used to be hand-synchronized arrays of the same 21 paths, and a list like that goes stale silently: a module missing from it is simply never reported on, and nothing fails. fta-cli returns no analysis at all (an empty array, not a zeroed-out one) for any file at or under its own size floor — measured at ≤6 code lines, comments not counted — so a file that small renders as an explicit `not scored (under FTA size floor)` row rather than crashing the tool or, worse, vanishing from the report; `src/equality/is-strict-equal.ts` is the first file to hit it.
- `scripts/perf-report/` — turns the raw `RawScenarioSample` JSON files `perf/` writes under `reports/perf/raw/` into `reports/perf/latest.md`/`latest.json`/`history.jsonl`. Report-only, no thresholds. This is where **every** median, percentile, ratio, and unit conversion in the perf harness lives — `perf/` itself computes none, because `perf/` is outside the gates and a wrong statistic there would be silent and plausible-looking. The boundary between the two is a file on disk, not a module import: `import type` crosses it (erased at compile time), a value import never may, in either direction, and `rules/no-value-import-across-perf-boundary.yml` checks that mechanically. It's also a real compiler boundary — `perf/` is in `tsconfig.app.json` (`moduleResolution: "bundler"`, `lib: DOM`) and `scripts/` in `tsconfig.scripts.json` (`nodenext`, no DOM).

**`scripts/` has exactly one vitest config and therefore exactly one project, which makes the `*.property.test.ts` suffix mean something different here than it does in `src/`.** `scripts/acceptance-mutation/tuple-list.property.test.ts` (added by `comma-list-mutants-are-all-syntax-breaking` as `mutation-rules.property.test.ts`, renamed when `cells-column-has-two-parsers-and-neither-models-tuples` moved its subject into `tuple-list.ts`, and the first of its kind here) is collected by `vitest.scripts.config.ts`'s ordinary `scripts/**/*.test.ts` include and runs inside `npm run test:scripts` alongside every unit test — measured. In `src/` that suffix selects the separate `property` vitest project; in `scripts/` it is a naming convention only, and the src-side project cannot reach it because `sharedExclude` subtracts `scripts/**`. Two consequences. There is **no** `test:property:scripts` command and no role gains an obligation — see `.claude/agents/articles/engineering.md`'s "Working inside `scripts/`". And do **not** "fix" the apparent inconsistency by widening the src-side `property` project to reach `scripts/`: that project runs under `vite.config.ts` — jsdom-adjacent settings, the React plugin chain, `src/`'s coverage directory — which is the whole reason `vitest.scripts.config.ts` exists, and the `sharedExclude` entry for `scripts/**` is what keeps the two suites out of one process. (That entry is **not** one of the two the merge protocol's mutation-invariant predicate leans on — those are `ideas/**` and `.claude/**`, the two `vite.config.ts`'s own "Both entries below" comment scopes itself to. `scripts/**` is absent from the predicate's allowlist, so a `scripts/`-only diff never earns the exemption and always runs the full gate.)

`.gherkin-lintrc` is an eighth checker, over `features/*.feature` rather than over TypeScript, and it **gates** (`npm run gherkin-lint`, nonzero on any finding) for `product`, the only role that runs it. Twenty-one of `gherkin-lint-plus`'s registered rules are on. Four facts about it that are easy to get wrong, all measured against the installed copy:

- **The package ships a `duplicate-state` rule file that is not in its registry** (`dist/rules/registry.js`), so naming it in the config aborts the run with `Rule "duplicate-state" does not exist`. The registered set is 31 rules, not the ~35 the `dist/rules/` listing suggests.
- **`name-length`'s and `max-scenarios-per-file`'s library defaults do not fit this repo — and note only the first of those two caps is derived the way the next sentence describes** — at defaults they report 21 findings against features nobody considers wrong. The caps here are derived from Prettier's 120-char print width (a step line is indented 4 plus its keyword, leaving ~110 for the text; a scenario line is indented 2 plus `Scenario Outline: `, leaving ~100), not fitted to the current text. `max-scenarios-per-file` runs with `countOutlineExamples: false`, because the quantity this repo actually budgets — acceptance mutants — is measured exactly by `npm run acceptance-mutation` and a blunter proxy for it would only ever be tuned.
- **`no-restricted-patterns` compiles every pattern with `new RegExp(pattern, 'i')`, unconditionally.** Case is therefore not available as a signal: a camelCase-identifier detector like `\b[a-z][a-z0-9]*[A-Z]` matches every ordinary word and reported 184 findings when trialled. The list has to be an enumerated vocabulary, not a shape.
- It reads **feature/rule/background/scenario names and descriptions and step text**, and never Examples headers or cells. That is not a hole in practice, because `no-unused-variables` forces every header to appear in some step's `<placeholder>`; the two rules together reach the whole table.

**`no-restricted-patterns`' pattern list belongs to `architect`, in the same sense `rules/*.yml` does**, even though it lives in a config file `product` otherwise owns. It mechanises the domain-altitude judgment — implementation vocabulary must not leak into the contract — and its failure mode is someone widening the list to clear a finding, which is the same move as narrowing a fast-check arbitrary or weakening an ast-grep rule. A role that hits a pattern it believes is wrong routes it back to `architect` rather than editing the list. The list has **two categories**. Most entries name a field, type, or function of a `src/` module (`offsetX`/`offsetY`, `cellSize`, `ScrollbarMetrics`' `thumbRatio`/`thumbOffsetRatio`, `ScrollbarMetrics` itself, `ContentBounds`, `VisibleRange`'s `minX`/`maxX`/`minY`/`maxY`, world-space coordinates, `cellKey`, and `should return`). Three more joined that category in `wheel-zoom-ignores-magnitude-and-pinch`'s CONTRACT pass: `delta` — deliberately unanchored at its end, so one pattern reaches `deltaX`, `deltaY`, `deltaMode` and the bare noun — plus `wheel event` and `zoom factor`, the latter for `camera.ts`'s `ZOOM_FACTOR`. They were added for the same reason as the ARIA four in `ast-grep-rules.md`, one input channel over: that slice is the first to make the contract talk about **how far** a wheel was rolled, and the natural phrasing for that reaches straight for the `WheelEvent` field names. `ctrl key` and `shift key` were considered alongside them and deliberately **rejected** — they name physical keys a user presses, and `no-restricted-patterns` compiles every pattern case-insensitively, so the list cannot tell `shiftKey` from "holding the shift key"; restricting them would ban the plainest English available for the gesture. Four name **markup and ARIA vocabulary instead** — `aria-`, `role=`, `tab index`/`tabindex`, `gridcell` — which belong to no `src/` module at all and are implementation vocabulary all the same; they were added in `collapse-dead-cell-layer`'s CONTRACT pass, ahead of the first `.feature` about keyboard and screen-reader behaviour, because that is the feature whose natural phrasing reaches for them. Adding to this list is the **safe** direction (it narrows what a contract may say); widening it to clear a finding is the move the paragraph above forbids. All four — and all three of the wheel entries above — were shown to fire against a planted probe feature before landing, each reported **by its own pattern name** rather than merely turning the run red, and each first checked against the seven existing `.feature` files for a clean baseline (a pattern that fires on the contract as it stands is a dirty baseline, and the fix is narrowing the pattern, never editing `product`'s text). The probe feature is deleted in the same command that runs the lint: a `.feature` with no step definitions makes `bddgen` exit 1 having generated **nothing at all**, so a probe left behind takes down every feature's generated spec rather than its own. Same obligation an `ast-grep` rule's fixture carries — a pattern that matches nothing is indistinguishable from a clean `features/`. Verbs are deliberately **not** restricted: `computed` reads as implementation but "the next generation is computed" is a statement about the game, and restricting it would drag the one already-converted feature into every prune's scope for no altitude gain. Neither is `live cells`, which is a type name (`LiveCells`) and simultaneously Conway's own ubiquitous language — the clearest example of why this list is enumerated by hand rather than derived.
