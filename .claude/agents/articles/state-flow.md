# Article: State Flow: hooks, stores, and composition roots

**Audience:** coder, cleaner, architect - **Read when:** before touching a hook or a composition root, before relocating state, and at the start of every architect REVIEW or DESIGN pass.

> Extracted verbatim from CLAUDE.md @ b5e333e, lines 143-166. No prose was edited in the extracting commit; only the common leading indent of a fragment lifted out of a nested list was removed.

### State flow

- **Live-cell state does not live in React at all.** `src/App.tsx` holds one `useState(() => createLiveCellStore(initialLiveCells))` — a stable handle, never a value that changes — and passes the store down as an opaque handle. `LifeBoard` accepts `store` and reads nothing out of it, so a generation tick never re-renders it. Two components subscribe, at two different granularities: `GridScrollbars` to the bounding box, and — since `collapse-dead-cell-layer` — `Grid` to the whole live-cell set (`useLiveCells`), because deciding which cells have a DOM element at all requires seeing all of them (`liveCellWindow.ts`). **That second subscription is a deliberate, named regression**: a tick now re-renders `Grid`, `GridCells` and every mounted `Cell`, where the retired per-cell `useLiveCell` subscription re-rendered only the cells that actually flipped. It is paid for by there being far fewer mounted cells — only the live ones, plus the focus cursor — instead of one per tile slot in range. This replaced `use-immer`'s `useImmer` (now removed from `package.json`): a producer hands back a new `Set` identity every tick, which defeats React Compiler's memoization however deep the prop drilling goes, so every visible cell re-rendered on every tick. `App.tsx`'s one optional prop, `initialLiveCells`, exists solely for the perf harness; `undefined` (every normal boot) means the ordinary empty grid.
- `src/components/GenerationHud.tsx` owns the `generation` count and the Next Generation button, advancing only via that button's own click/keyboard handling — there is no global keyboard shortcut for it. It takes `onAdvance` (wired to `store.advance`) and holds no live-cell data, so a tick re-renders the counter and nothing else above the grid.
- `src/main.tsx` is bootstrap, not a composition root: it reads `import.meta.env.MODE` and passes the _result_ down. That check has to be at the entry module for Rolldown to constant-fold it and tree-shake `liveCellSeed.ts` out of a normal production bundle, which is why `rules/no-logic-in-composition-root.yml` deliberately doesn't scope it and `rules/no-build-env-in-domain.yml` guards the same invariant from the other side. The file holds exactly one ternary and no other decision.
- Each hook in `src/hooks/` owns exactly one piece of state or one browser API, and delegates the actual rules to a framework-free module: `useCamera.ts` owns the `Camera` as local `useState` and exposes pan/zoom/wheel/center/scrollbar-drag actions that delegate to `camera.ts` and `scrollbars.ts` — every one of them through a single private `commit()` that **cancels any in-flight zoom glide first**, which is the whole reason that funnel exists: reset is only one of five external writers (wheel zoom, drag-pan, scrollbar drag and the arrow-key reveal-pan are the others), and one cancel site is what stops the fifth being forgotten. The glide's own frames call `setCamera` directly and deliberately bypass `commit()`; `usePatternPlacement.ts` owns the `PlacementState` and its Escape-to-cancel listener, delegating every transition to `patternPlacement.ts`, and takes the place-a-pattern commit callback so that single-shot stamping (read the armed pattern, commit it, disarm) is one action here rather than a two-call sequence a caller could get wrong; `useElementSize.ts` isolates `ResizeObserver`; `useWheelInput.ts` isolates the native, non-passive `wheel` listener and hands callers a `WheelInput` instead of a DOM event; `useGridPointerGestures.ts` isolates pointer capture and drag-vs-tap resolution (delegating the threshold math to `dragGesture.ts`), reporting rect-relative pixels and never touching a `Camera`; `useInitialCentering.ts` isolates the one-shot first-non-zero-measurement latch (`useLayoutEffect` + a ref, so no frame paints uncentered); `useCellTiles.ts` holds two independent sticky values as two `useState`s — a `TileRange` (mounting coverage) and an `Anchor` (precision bounding) — returning the range as an object (reference-stable by `nextTileRange`'s own contract, so this is not a regression of the old hook's scalar-flattening discipline) alongside the anchor's pixel offset as scalars, delegating the keep-or-rebase decision for each to `cellTiles.ts`'s `nextTileRange` and `cellAnchor.ts`'s `nextAnchor` independently (read the hook's comment on why both coverage checks run during render rather than in a `useEffect`); `useRafCoalescedPan.ts` isolates `requestAnimationFrame`, summing however many pan deltas arrive within one frame into a single `onPan` call and exposing `flush()` so a pointerup settles the camera synchronously instead of waiting on a queued frame; `useZoomGlide.ts` is this repo's other animation-frame owner and mirrors that lifecycle with one deliberate difference — an unfinished glide at unmount is **cancelled, never flushed**, because a coalesced pan owes its caller an already-accumulated delta while a half-arrived-at cellSize is owed to nobody — and holds the one state that makes the whole design exact: every frame recomputes `zoomCameraToCellSize` from the camera the glide STARTED at, never from the previous frame's result, so the completion frame is bit-identical to an instantaneous zoom (chaining frame-over-frame is algebraically exact and float-inexact, measured at up to ~1 ULP by fuzzing, which reds an exact-equality assertion though not any pixel one); `useMatchMedia.ts` is the shared `useSyncExternalStore` subscribe/getSnapshot plumbing for a boolean `matchMedia` query — note **jsdom does not implement `matchMedia` at all** (measured: `undefined` in this repo's `dom` project, while `requestAnimationFrame` and `performance.now` both exist), so any test mounting a tree that reaches it (directly or through one of its two composers) must call `src/test-support/domStubs.ts`'s `stubMatchMedia`, and it carries no defensive fallback on purpose — an unstubbed test throwing loudly beats shipping a branch no gate can exercise. Its `subscribe`/`getSnapshot` are **inline closures over `query`**, not the module-level named functions `useReducedMotion.ts` held before the extraction, so their identity stability — and therefore `useSyncExternalStore`'s resubscribe avoidance — is **provided by React Compiler rather than structural**. Measured at this slice's REVIEW pass, on the shipped config: **1 `addEventListener` call and 0 `removeEventListener` calls across three re-renders**, for `useMatchMedia` directly and through both composers. With the `babel({ presets: [reactCompilerPreset()] })` entry removed from an otherwise identical jsdom config: **4 adds and 3 removes** — one resubscribe per render, on the hook `useZoomGlide.ts` reads once per pointermove of a drag-pan. That is the `stable-hook-identities` class exactly, so it is pinned rather than assumed: `useMatchMedia.test.ts` carries an `it.skipIf(underStryker)` no-resubscribe assertion plus an **unskipped companion built on a changing query**, which resubscribes in both configs. The companion is deliberately not built from a fresh-closure construction — measured, the compiler flattens those too, so such a companion would red the shipped config. Note `listenerCount()` structurally cannot serve here: a resubscribe removes and re-adds, leaving the net count at 1 either way, which is why `MatchMediaController` grew `addCallCount`/`removeCallCount` beside it; `useReducedMotion.ts` composes it with `'(prefers-reduced-motion: reduce)'` and returns the raw boolean unchanged; `useSystemAppearance.ts` composes it with `'(prefers-color-scheme: dark)'` and maps the boolean onto `'dark'`/`'light'` — this pair used to each carry an identical private `subscribe`/`getSnapshot`, extracted into `useMatchMedia.ts` once the duplication became cross-file rather than hypothetical; `useLiveCells.ts` is a `useSyncExternalStore` adapter over the store's whole live-cell set, the exact shape `useContentBounds.ts` already had over the bounds snapshot; `useGridFocus.ts` owns the keyboard focus cursor, delegating every transition to `gridFocus.ts` and keeping for itself only the two things that are genuinely React's — synchronizing real DOM focus onto whichever cell is current (both the keyboard route and, since this slice's step-4 adjudication, the pointer route, which the browser used to handle for free while every cell had a button) and the one-shot initial centering; `useAppearance.ts` owns the one `AppearancePreference` as local `useState` (seeded from `localStorage` via `appearance.ts`'s `parseAppearancePreference`), resolves it against `useSystemAppearance.ts`'s live value through `resolveAppearance`, and is the one `useEffect` that pushes the result onto `<html>`'s `dark` class for Tailwind's `dark:` variant and `src/index.css`'s `@custom-variant` override to key off — called exactly once, from `App.tsx`, since a second call site would hold a second `useState` the two could desync against. That split is what keeps the rules testable without a jsdom environment — put new logic in the pure module and let the hook stay a thin adapter.

  **`useZoomGlide.ts`'s returned controller is identity-stable across renders, and that is a contract with named guards rather than an incidental property of how the hook is written.** `useCamera`'s private `commit()` closes over the controller, and every one of its seven returned actions closes over `commit()` (or, for the two centered-zoom actions, over the controller directly) — so a controller rebuilt per render churns all seven, measured both ways: pre-slice all seven were stable, and with the churn none were. What keeps it stable is that the controller closes over nothing that varies per render — `onCamera` and the reduced-motion preference are both read through refs reassigned in the hook's single dependency-array-free effect, which is what lets React Compiler memoize it. **Declaration order is load-bearing**: placing that effect above `const prefersReducedMotion = useReducedMotion()` compiles, type-checks and passes every other test in the repo while leaving the controller unmemoized and the change inert.

  Three guards pin it, each `it.skipIf(underStryker)` — Stryker's per-expression instrumentation defeats React Compiler's memoization, so an ungated identity assertion reds the **dry run** and `npm run test:mutation` never starts — with an unskipped companion proving the instrument non-vacuous: `useZoomGlide.test.ts` (controller identity across a re-render), `useCamera.test.ts` (the whole returned surface across a no-op re-render, plus **all seven** returned actions across a pan — that test asserted only the five `commit()`-routed writers until `stable-hook-identities`, which superseded the ruling that `zoomInCentered`/`zoomOutCentered` legitimately churn because they capture `camera`, by making them read it through a ref at call time instead; see the contract paragraph below), and `LifeBoard.test.tsx` (no `wheel` re-registration during a six-frame drag pan). All three were verified red against **both** fault arms — the unfixed tree, and the misordered variant above — and `useZoomGlide.test.ts`'s companion, "reads prefers-reduced-motion at click time", was separately verified to be the **only** test in the repo that reds when the ref assignment is dropped, which is what guards that path under Stryker, where the skipped three do not run at all.

  **The cost this removes is measured; the perf attribution it was chased down for is not.** In jsdom the churn tore down and re-added `#grid-content`'s non-passive `wheel` listener on every camera commit (`useWheelInput`'s effect is keyed `[ref, onWheelInput]`, and `onWheelInput` is `applyWheel`) — 4 registrations at mount and 10 after a six-frame paced pan before the fix, 4 and 4 after it. **Whether that explains `pan-min-zoom-50k`'s ~8ms regression at 1280×900 was left as a hypothesis jsdom cannot test**, having no compositor — and the orchestrator's post-merge run then **closed it**: with the fix landed that scenario reads **41.80 / 47.53 / 41.70ms** at 1280×900 and **58.30 / 58.33 / 58.40ms** at 1920×1080, against a regressed 50.00 / 50.00 / 49.91 / 50.00 and 66.70 / 66.60 / 66.07 / 66.60, and a pre-`smooth-zoom-transitions` baseline of 42.70 / 41.81 / 41.91 and 58.45 / 58.33 / 60.02. Fully recovered at 1920 and recovered in two of three runs at 1280. Read that as **the identity churn being the cost**, not as proof the listener re-registration is the whole of the mechanism — the perf harness cannot separate them, and two earlier explanations of this same 8ms were confidently stated and refuted. Note also it inverts an assumption made during the investigation: 1280 was treated as the stable viewport and 1920 the noisy one, and this run is the other way round, so **neither viewport should be trusted from a single sample**. The mechanism originally proposed — that memoization bailing re-renders every mounted cell — was **refuted**: `Cell` and `GridCells` render counts are byte-identical in both arms, those renders being driven by the tile-range rebuild that `perf/pan.perf.spec.ts`'s 400px-per-move pan forces on every move at `MIN_CELL_SIZE` regardless. So acceptance for the fix was identity stability plus its guards, deliberately independent of the perf number — which is why the recovery above is corroboration rather than the thing that made the slice correct.

  **The general contract that generalizes from it, established by `stable-hook-identities`: a hook-returned function must not capture render-varying state it only needs at call time, and where such a function crosses a component boundary as a prop, its identity is asserted by a test.** The sanctioned mechanism is a **ref synced in a dependency-array-free `useEffect`** — never `useCallback`, which `rules/no-manual-memo-ts`/`-tsx` forbid under React Compiler, and never a write during render, which the compiler forbids outright (`useRafCoalescedPan.ts` carries that trap's explanation). Five such refs across four hooks: `useZoomGlide.ts` (`onCameraRef`, `prefersReducedMotionRef`), `useRafCoalescedPan.ts` (`onPanRef`), `useCamera.ts` (`cameraRef`, for the two centered zooms) and `usePatternPlacement.ts` (`placementRef`, for `stampArmedPattern`). **The call-time read is semantically better, not merely a memoization trick**: `stampArmedPattern` reading the placement when the click happens, rather than when the render happened, is what makes it impossible to stamp a pattern `Escape` cancelled in between — same for the camera a zoom click zooms from.

  **It is a scoped contract, not a blanket rule, and the exemptions carry their reasons at the site.** A blanket "everything a hook returns is identity-stable" is unachievable for projections (`useCellTiles`'s view object _must_ change when the camera moves) and would spend real complexity on churn that provably costs nothing. Three exemptions, each measured: `useGridFocus.moveFocus`/`jumpToEdge` churn on `focus` and `camera` but reach only `Grid`'s local `handleKeyDown` and from there `#grid-content`'s `onKeyDown` prop — a DOM property assignment with **no memoized subtree behind it** — so stabilising them buys nothing (the comment at their declaration site says so, and names the condition that reopens it: either becoming a prop of a memoized child); `useGridPointerGestures`' `handlers` _container_ churns when any member does, but `Grid` spreads it rather than passing it down, so React diffs the four members individually and each is memoized against its own dependencies; and `useCellTiles`'s view object is a projection whose change is the point. **What decides an exemption is where the churn LANDS, not whether it happens** — which is why each one is a measurement rather than a judgement call.

  **Guarded in two layers, and no `ast-grep` rule is possible.** Layer A is the durable one: composition-level render-count guards, currently `Grid.test.tsx`'s "a pan that stays within the current tile range re-renders zero cells" and `LifeBoard.test.tsx`'s "armed hover does not re-render mounted cells", both counting `Cell` render calls through `vi.mock('./Cell', { spy: true })`. Layer B is per-hook identity assertions, added only where capture risk exists (`useCamera.test.ts`, `usePatternPlacement.test.ts`, `useZoomGlide.test.ts`). Both layers use the `it.skipIf(underStryker)`-plus-unskipped-companion idiom described above. **The tempting structural proxy — "no inline arrow functions in a hook's returned object literal" — is exactly backwards on this codebase and was tested rather than assumed**: `usePatternPlacement`'s four inline arrows are all identity-stable, and the one function that churned, `stampArmedPattern`, was a hoisted declaration. The real discriminator is **forward reference** — a declaration referenced from a closure appearing above it, measured by moving `Grid.tsx`'s `activateCell` back to that form, which reds exactly one `Grid.test.tsx` test — and that is scope analysis, not a syntax pattern. Identity is a property of _compiled output_; tests are the only instrument that can see it.

  **A shared `useLatestRef(value)` helper was proposed at the fourth site and declined** (`cleaner`, ratified at `stable-hook-identities`' REVIEW): the load-bearing content at each site is the why-**this**-value comment, which any extraction leaves in place, so the mechanical saving is ~2 lines per site; `useZoomGlide.ts`'s two-refs-in-one-effect shape does not fit a single-value API without either splitting that effect — the exact declaration-ordering hazard measured above, where a plausible reordering passes and fixes nothing — or generalizing the API for one caller; and a fourteenth hook would enter this section's enumerated list and every gate for that saving. **`dry4ts`'s silence here is a `minNodes: 20` floor artifact, not evidence against duplication** — each occurrence's effect body is one or two statements — so don't cite a clean run as a finding either way. Reopen on a **shape** change rather than a count (the count trigger has already fired once and returned the same answer): a site where the one-effect-flush lag is not acceptable and wants a module to argue the timing in, or a single-value site whose why-comment turns out to be boilerplate.

- `src/components/LifeBoard.tsx` is the composition root for the camera and placement state: it calls `useCamera` and `usePatternPlacement`, derives `previewPositions`/`armedPattern` from already-tested pure functions, and supplies `Grid`'s `renderOverlays` render prop with the ruler, zoom-%, scrollbars, toolbar, and pattern-library modal — in that stacking order, since all of them are `position: absolute` with auto z-index and a later sibling wins hit-testing (`GridToolbar` at `top-2 right-2` must render after `GridScrollbars`' track, or it can't be clicked where it overlaps). It deliberately touches **no** live-cell data — it only forwards the `store` handle and `store.toggle` — so a generation tick never re-renders it; the content-bounds subscription that used to sit here was pushed down into `GridScrollbars`, the one overlay that needs it. `LifeBoard.tsx` is deliberately outside every quality gate, like `App.tsx` — kept wiring-only mechanically by `rules/no-logic-in-composition-root.yml` (ast-grep, report-only) rather than by unit-test coverage; its own small `LifeBoard.test.tsx` exists only to recover the two behaviors no unit below it can prove alone (that a pointer tap on the grid actually reaches `usePatternPlacement`'s single-shot `stampArmedPattern`, and the Patterns-button-while-placing cancel path) that would otherwise be e2e-only.
- `src/components/Grid.tsx` owns the measurement (`useElementSize`), the pointer/wheel listeners (`useGridPointerGestures`, `useWheelInput`), the one-shot initial centering (`useInitialCentering`), and the DOM sibling-not-ancestor layering between `#grid-content` and whatever `renderOverlays` returns — but it imports none of `GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, or `Scrollbar.tsx` directly. Those four are inverted: `Grid` takes a `renderOverlays(context)` render prop (`context` carries only what `Grid` measures and its caller can't — viewport `size` and the computed `visibleRange`) instead of importing and rendering them itself, so `LifeBoard` supplies the actual overlay components rather than `Grid` hardcoding them. The deliberate exceptions are `Grid → GridCells → Cell`, `Grid → GridLines`, `Grid → HoverIndicator` and `Grid → PatternPreview`: cells must render _inside_ `#grid-content`, and owning that containment is exactly why `Grid` exists as its own component rather than folding into `LifeBoard`. Inside `#grid-content`, `Grid` renders four siblings in DOM order — `GridLines`, then a transformed layer div wrapping `GridCells`, then `HoverIndicator`, then `PatternPreview` (later-in-DOM wins among same-level absolutely-positioned siblings, so lines paint furthest back and are occluded by every opaque live cell, and the preview paints over both the cell buttons and the hover indicator). **The pan transform sits on that inner layer div and never on `#grid-content` itself**, which is load-bearing rather than stylistic: `useGridPointerGestures` and `useWheelInput` both call `getBoundingClientRect()` on `#grid-content`, so a transform there would shift that rect and silently resolve every tap and hover to the wrong world cell. `Grid.test.tsx` asserts `#grid-content` carries no transform (and, in its own comment next to that assertion, that the layer div's own transform is a pure `translate(...)` with no `scale` — this app re-lays-out on zoom instead of scaling, which keeps `getBoundingClientRect()` and layout units from disagreeing the way a scaled scroll container's would), for exactly that reason. `GridCells` no longer decides which cells exist: `Grid` calls `liveCellsInRange(liveCells, tiles.range, gridFocus.focus)` (see `liveCellWindow.ts`) once per render and hands the finished array down, and `GridCells` only lays it out — one `Cell` per entry, keyed by that cell's own `CellKey`, a stable identity for as long as the cell stays alive. **`CellTile.tsx` is deleted**, along with the "`TILE_SPAN_CELLS²` cells per mounted tile, dead or alive" loop it wrapped; `useCellTiles`'s world-anchored `TileRange` survives as the _bound_ on that projection rather than as a set of things to render, and the intra-tile pixel math (`cellOffsetPx`) moved down into `GridCells`. `Cell.tsx` takes its own aliveness as a plain `isAlive` prop instead of holding the per-cell store subscription it used to (`useLiveCell.ts`, retired with `subscribeCell` itself) — the one `liveCellsInRange` call that decided to mount it already knows — and takes a finished CSS `transform` string rather than pixel numbers, so it holds neither a `Camera` nor any pixel geometry. It paints solid when alive and **nothing at all** when dead: `GridLines.tsx`'s own white base fill and gridlines show through, which is why a dead-but-focused cell must stay transparent rather than white. `PatternPreview.tsx` is the one place that stays camera-exact — it sits outside the transformed layer and recomputes `worldToScreen` per position, which is affordable because it is bounded by the armed pattern's own size, not by the viewport. That split is the point of the layer, and `collapse-dead-cell-layer` changed which half of it does the work: a tick now re-renders every mounted `Cell` rather than only the flipped ones (`Grid`'s whole-set subscription — see the state-flow bullet above), but the mounted set is the live cells in range plus the cursor rather than the ~34,000 tile slots at min zoom, so an empty board costs nothing to render at all. A pan that stays within the tile range's eviction hysteresis still re-renders no cell — `liveCellsInRange`'s three inputs (the store's set identity, `nextTileRange`'s by-reference range, the focus cursor) are all unchanged, so React Compiler bails on the call. `Grid.tsx` has its own unit tests (`Grid.test.tsx`), now scoped to that composition — the DOM layering contract, the place-vs-toggle dispatch, and one thin wiring test per hook — rather than the ~1,575-button, ~500ms-per-test renders it used to pay for when it rendered the whole tree itself; the hooks and pure modules it composes, and the four inverted overlay components, are each tested on their own.
