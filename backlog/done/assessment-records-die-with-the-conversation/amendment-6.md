## Item 17 — a role reads its own spec by path, and the truncation class ends

**Supersedes nothing in the spec or the earlier amendments. It replaces item 17 as I first drafted

### The ruling, stated so one sentence can overturn it

**Ruled: the narrow carve-out. A role reads its own item's `spec.md` and `amendment-*.md`, at
paths the prompt names, and nothing else under `backlog/`.** The seat names paths instead of
pasting bytes.

**The alternative I rejected is the blanket rule as it stands today**, in CLAUDE.md — "no role
reads it, and an item reaches a role as prompt content rather than as a file path" — and in
`pipelines.md` — "No spec in the prompt, no authority to edit."

**My first draft kept that rule and made truncation merely detectable. The user asked why it
should be possible.** They are right, and the seat that raised it was right to send it back.

### What the blanket rule protects, and what the carve-out costs

Four protections. Three survive; one is genuinely lost and is replaced.

1. **Navigation — a role cannot wander the lanes.** **Survives.** The carve-out names two
   basenames in one folder. Sibling items, lane counts and other slices' work stay unreadable.
2. **Authority — the pasted bytes are the grant.** **Survives in kind, and the argument is
   already signed.** `pipelines.md` rules the spec and every signed amendment immutable once the
   slice starts. So the bytes at the path are the bytes the seat vouched for. The path form is
   equivalent to the paste form because of a rule in force, not because of a guarantee invented
   here.
3. **Pass scoping by omission — a role cannot execute an item it was never shown.** **Lost.**
   Replaced by half two below, and that replacement is what makes the carve-out safe.
4. **Simplicity — a rule with no exceptions cannot be misread into one.** **Genuinely lost, and
   this is the real cost.** A carve-out can be read wider than it is written. So it carries a
   glance test in the next section, and every home states the same two sentences.

### The pass-scoping risk, weighed rather than asserted

**The record: six `writer` passes in this slice, each scoped by instruction, none executing an
item outside its pass.**

**That is evidence about instruction-scoping, and no evidence at all about omission.** Every one
of the six carried the item numbers in its prompt. So the sample shows the instruction works. It
cannot show how often omission saves a pass, because omission was never the operative constraint
— instruction fired first, every time.

**The two defects are not symmetrical in what has been observed.** Truncation has fired once, at
step 4, and was caught by luck rather than by design. Executing a future item has fired zero
times. **Ruling on the observed defect over the hypothesised one, with an explicit guard for the
hypothesised one, is the trade.**

**And omission degrades as the chain grows.** Six amendments produced a 350-line prompt. The
truncation risk scaled with that length; the protection did not scale with anything. The blanket
rule got weaker exactly where the risk got stronger.

**Half two gets stronger under the carve-out, which is the answer to the risk.** Today the seat's
scoping is implicit — it pastes some items — and `writer` cannot check it. Under the carve-out the
prompt names item numbers and `writer` reads the file holding all of them, so `writer` can compare
the named set against the file and report both. **Pass scoping becomes auditable for the first
time.**

### How a reader tells the two cases apart at a glance

**A path you were handed, versus a path you worked out.** Read a board path the prompt names.
Never derive one — no globbing, no directory listing, no path built from the slice name.
