# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Conway's Game of Life, built as an infinite, pannable/zoomable grid (React 19 + TypeScript + Vite + Tailwind v4). Cells are toggled by click; generations advance manually via the Next Generation button.

There is no separate typecheck script — `npm run build` runs `tsc -b` as its first step. Lint (oxlint) has type-aware rules disabled by default; see README.md if enabling `oxlint-tsgolint`.

**Mutation testing runs incrementally.** `npm run test:mutation` still covers the whole `mutate` list, but Stryker caches results and re-tests only the mutants whose source _or covering tests_ changed — a full run over `src/` took ~10 minutes when that was measured — with `features/` still in the sandbox, which it no longer is (see the sandbox paragraph below); no replacement figure is recorded here, since `hardener`'s next `npm run test:mutation:full` is the thing that produces a current one. An incremental run tracks the size of the diff **above a floor described in the next paragraph**. This matters because Stryker kills a mutant when _any_ test fails, so a mutant in one module is often killed by a test in another; scoping a run to changed source files alone would be blind to "a test moved, and now a mutant in an untouched file survives," whereas incremental mode accounts for it. Reach for `npm run test:mutation:full` whenever the cache's file-level assumptions break — `stryker.config.json` changed in either of the two keys that decide what the run sees (`mutate`, which picks the files to mutate, **or `ignorePatterns`, which picks the files that reach the sandbox at all** and therefore which tests exist to kill anything), a module was split or renamed, or test files were moved/deleted rather than edited in place — and prefer it when genuinely unsure, since a false-clean score is worse than a slow one.

**That floor is `@fast-check/vitest`, and it is structural: ~10% of the mutants and ~3m45s of wall clock get re-tested even when nothing changed at all.** The plugin interpolates the run's seed into the test _title_ (`… (with seed=2041793899)`), unconditionally and with no option to suppress it (measured in `node_modules/@fast-check/vitest/lib/vitest-fast-check.js` — the only way to stabilize the title is to pin the seed), while Stryker's `IncrementalDiffer` matches cached results _by test name_. So every property test looks brand-new on every run and invalidates the ~135 mutants they cover regardless of the diff: measured, 310 of 383 invalidated cached tests carried a `with seed=` marker, and the run reported `1171 of 1306 mutant result(s) are reused`. **Those three test-side figures were measured with `features/` still in the sandbox and have not been remeasured since it was excluded** — the mutant totals are unaffected (`mutate` never covered `features/`, and 1,306 is still the count on the current tree), but the run's test population dropped by the 151 tests in 7 files that Stryker collected from `features/` (its scope, not vitest's — see the sandbox paragraph), so the 310/383 denominators are pre-exclusion and are left as-is rather than quietly adjusted to a number nobody ran. The mechanism the paragraph describes is unchanged either way: property tests live in `src/`, so nothing about the seed-in-the-title problem moved. It fails **safe** — it re-tests more than needed and never falsely reuses a stale result, and three runs on an identical tree gave byte-identical totals — so this is a cost, not a correctness problem, and no reported score has ever been wrong because of it. Don't buy the floor back by pinning the seed globally: the exploration is the whole point of that layer, and this repo separately requires repeated property runs when a slice edits a property file. Pinning a seed only under Stryker, leaving `npm run test:property` exploratory, is the one variant that isn't self-defeating — and it is a slice of its own, since it changes what the mutation gate measures.

**`features/` is not in Stryker's sandbox.** `stryker.config.json` carries `"ignorePatterns": ["/features"]`, so the whole Gherkin layer — all 7 step files — is never copied into `.stryker-tmp/` and cannot run, kill, or be attributed a kill. **Size that layer at the scope you mean, because the two scopes genuinely differ**: `npx vitest run features/` collects **180** tests from those 7 files (of 837 across 61 files on `ebba2f5`), while the `bd7c388` baseline shows Stryker itself collected only **151** from the same 7 (of 805 across the same 61 files). Same tree, same files, 32 fewer tests seen by Stryker — its runner drops any test that finishes without a result (`vitest-test-runner.js` filters on exactly that, with `bail: 1` set). So quote 151/805 when the sentence is about the mutation run, and 180/837 when it is about `npm test`. The justification is in the testing-layer note below: that layer's measured contribution to the score is zero mutants, while its `killedBy` attributions were routinely phantom. **Excluded from Stryker is not unmutated, and that second half is the whole argument** — `features/` keeps its own mutation signal in `npm run acceptance-mutation`, which mutates the Examples tables and asks whether the steps notice. That runner never touches any of this machinery: it spawns a plain `vitest run <steps file>` with **no `--config`** (`scripts/acceptance-mutation/vitest-runner.ts`), against the real tree, so Stryker's sandbox and its `ignorePatterns` are not in the picture at all. What this slice removed was a duplicate measurement that was also wrong, not a gate — read it as de-duplication, never as the Gherkin layer being ungated. Three things follow that are easy to trip over. **The leading `/` is load-bearing** — it anchors the pattern to the project root (gitignore semantics, per the option's own schema description), so it matches `features/` and not some nested `src/features/`. **`ignorePatterns` has no effect whatsoever under `--inPlace`**, which the schema states outright ("with `true` the `ignorePatterns` has no effect any more") because in-place mode mutates the real tree instead of a sandbox copy; no npm script passes that flag today, and adding one would silently readmit the entire Gherkin layer to the run. **A rename of `features/` breaks this entry silently and in the dangerous direction** — an `ignorePatterns` glob that matches nothing is not an error, the layer comes back, and the score moves _up_, which no threshold catches. That silence is measured, not assumed: a probe config carrying `ignorePatterns: ["/no-such-dir-xyz"]` emits no warning of any kind and collects the identical test count as `ignorePatterns: []` (267, scoped to `is-strict-equal.ts`). `npm run gherkin-lint`, `playwright.config.ts`'s `testDir`, and `vite.config.ts`'s `acceptanceTests` glob all hardcode that directory name too; see the `acceptance` project's comment in `vite.config.ts`.

**This is also the repo's first split between what `crap4ts` sees and what Stryker sees, and it is intended.** `npm run test:coverage` runs through `vite.config.ts` and so runs all four projects, both step-file forms included, which means a line reachable _only_ from a step test still reads as covered in `npm run crap4ts`. Its mutants, though, are now killable only by a non-`features/` test. So the two tools can legitimately disagree about the same line, and the remedy when they do is the same as for the browser-required layer: close the gap with a jsdom or unit test under `src/`, never by reaching back into `features/`. Don't rediscover this as a bug.

The two Stryker configs keep **separate** caches (`incrementalFile`: `reports/stryker-incremental.json` for `src/`, `reports/stryker-incremental-scripts.json` for `scripts/`), the same way they already separate `tempDirName` and their HTML reports — one shared cache across two different `mutate` lists would corrupt both. For the same reason, a `--mutate`-scoped run (as in `cleaner`'s workflow step 3) must never pass `--incremental`: it would record that subset as if it were the whole project and make the next full-scope run report a false-clean score. Both cache paths are gitignored, so a fresh clone or CI pays full cost on the first run — that's the safe default, not a misconfiguration. Note the `scripts/` cache is currently declared rather than used: `npm run test:mutation:scripts` runs `stryker run stryker.scripts.config.json` with **no** `--incremental` flag, so that side always pays full cost and never writes `reports/stryker-incremental-scripts.json` at all. The separate path still earns its line in the config — it is what makes adding the flag safe — but don't read the merge protocol's `rm -f` of both files as evidence the second one exists.

**crap4ts is patched locally (`patches/crap4ts+1.0.1.patch`) and `crap4ts` is pinned to an exact version because of it.** Upstream, crap4ts pairs an AST function span to an Istanbul coverage span only when they overlap by ≥80% of the AST span's lines (`OVERLAP_THRESHOLD = 0.8`), and Istanbul records `fnMap[k].loc` as the function _body_ — starting at the opening brace, never consulting `fnMap[k].decl`. A signature Prettier had to break across lines therefore pushes the two spans apart far enough that no candidate matches, and the function is reported at 0% coverage with an inflated CRAP score even though it is fully exercised. The patch mirrors upstream PR [breezy-bays-labs/crap4ts#37](https://github.com/breezy-bays-labs/crap4ts/pull/37) (open and unmerged since 2026-04-07; `crap4ts@1.x` is in maintenance mode pending a Rust-backed v2 rebuild, so it may never land): `findCandidates` now also accepts a candidate when either span fully contains the other, bypassing the ratio gate in that case. Ranking (`contains` → `ratio` → `nameMatch`) is unchanged.

Three consequences follow. First, the patch targets a **content-hashed tsup chunk** (`dist/chunk-W6RIPRFD.js` plus its CJS twin `dist/chunk-OHOZMDXW.cjs`), so any crap4ts release renames the file and the patch stops applying — which is why `package.json` pins `"crap4ts": "1.0.1"` with no caret, and why **upgrading crap4ts means regenerating the patch by hand**, not just bumping the range. Second, `patch-package` runs from `postinstall`, so the patch is only in effect after a normal `npm install`/`npm ci`. Third, `src/patternLibrary.ts`'s `patternCellPositions` keeps its four-line signature deliberately: it is the live regression fixture for this patch. If the patch ever stops applying, that row drops back to 0.0% in `npm run crap4ts` — don't "tidy" the signature onto one line, and don't chase the 0% as a coverage gap if it reappears. `npm run crap4ts -- --verbose` distinguishes the two cases: an `[unmatched-no-coverage]` warning naming the function means the matcher missed it (patch not applied), whereas a genuine gap shows as a matched row with a low percentage. There is a third cause of the identical `[unmatched-no-coverage]` warning, unrelated to the patch, and it is the one that has actually bitten repeatedly: **`crap4ts` reads `coverage/coverage-final.json` off disk and never regenerates it**, so any source edit since the last `npm run test:coverage` is scored against stale line spans. This is broader than a missing entry for a newly-landed file — _any_ line-shifting edit, including a pure comment change, moves a function's AST span away from the recorded coverage span, and the two failure modes look nothing alike: some functions orphan at 0.0% (indistinguishable from the patch-not-applied case above), while others match an old, shifted entry and read a spurious 100%. The remedy is the same either way, and it is a precondition rather than a fix: **run `npm run test:coverage` (or `npm run test:coverage:scripts` before `npm run crap4ts:scripts`) whenever source has changed since the last coverage run** — which, in a role's pass, is essentially always. (The many `[unmatched-no-ast]` warnings under `--verbose` are unrelated and expected — they are coverage entries in files outside crap4ts's `include` list, plus nested functions crap4ts does not score.)

## Architecture

### Core logic: sixteen framework-free modules, ten hooks, twelve unit-tested components

Sixteen framework-free modules — twelve at `src/` root (`gameOfLife.ts`, `patternLibrary.ts`, `camera.ts`, `gridGeometry.ts`, `cellTiles.ts`, `cellAnchor.ts`, `dragGesture.ts`, `scrollbars.ts`, `patternPlacement.ts`, `liveCellStore.ts`, `liveCellSeed.ts`, and `cache.ts`) and four in `src/equality/` (`container-equality.ts`, `is-shallow-equal.ts`, `is-deep-equal.ts`, `is-strict-equal.ts`) — hold every non-UI rule in the repo, and together with ten hooks in `src/hooks/` (`useCamera.ts`, `useElementSize.ts`, `usePatternPlacement.ts`, `useWheelInput.ts`, `useGridPointerGestures.ts`, `useInitialCentering.ts`, `useLiveCell.ts`, `useContentBounds.ts`, `useCellTiles.ts`, `useRafCoalescedPan.ts`) and twelve components in `src/components/` (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `CellTile.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`) are the modules covered by unit tests and mutation testing (see `stryker.config.json` / `crap4ts.config.ts` — both scope by glob-minus-exclusions rather than by an enumerated list, and `scripts/halstead4ts/run.ts` resolves `crap4ts.config.ts`'s globs rather than restating them, so a new module at `src/` root, `src/hooks/`, or `src/components/` is covered the day it lands with no config edit). Every framework-free module is additionally covered by property tests (the `property` vitest project's `include` is `**/*.property.test.ts`, so a new file with that suffix is picked up automatically) with two deliberate exceptions in `src/equality/`: `is-strict-equal.ts` is a three-line `Object.is` wrapper with no invariant to quantify over, and `container-equality.ts` has no contract of its own to state — it is the shared walker both comparators inject into, so their property tests (reflexivity, symmetry, clone round-trip, Set-member order-independence) are what cover it, from both sides. `src/App.tsx`, `src/main.tsx`, and `src/components/LifeBoard.tsx` remain excluded — still composition-root/bootstrap code exercised by browser testing rather than unit tests, specifically `features/hud-layout-and-shortcuts.e2e.spec.ts`, which drives the HUD and App's own state wiring (including that a stamped pattern really does come to life) through the real app — as does `src/test-support/`, which is shared test infrastructure (jsdom stubs for `ResizeObserver`, `getBoundingClientRect`, and pointer capture in `domStubs.ts`, the fast-check arbitraries the camera-side property tests share in `arbitraries.ts`, the brute-force Life oracle `gameOfLife`'s and `liveCellStore`'s property tests both check against in `lifeReference.ts`, the `#grid-content` DOM query both `Grid.test.tsx` and `LifeBoard.test.tsx` need in `gridDom.ts`, and the single encoding of how a cell's aliveness is expressed in the DOM (the `aria-pressed` attribute/value constants and the `Cell x, y` label format, shared by `src/components/*.test.tsx`, `features/*.e2e.spec.ts`, and `perf/`) in `cellQuery.ts`) rather than product code. Nothing in `src/` outside a test file may import from `src/test-support/` — the directory sits outside every gate, so such an import silently moves what it pulled in out of mutation testing and coverage scoring; `rules/no-test-support-in-product-ts.yml` and `rules/no-test-support-in-product-tsx.yml` check that mechanically. Keep new domain logic in a framework-free module rather than in a component whenever it can be expressed as pure logic, so it stays covered by property tests and mutation testing, not just unit tests.

- **`src/gameOfLife.ts`** — the actual Game of Life model. Live cells are stored as a sparse `Set<CellKey>` (`CellKey` = `"x,y"` string), not a bounded 2D array — the grid is conceptually infinite. Core functions: `toggleCell` (mutates an Immer draft), `advanceGeneration` (one generation **plus** the exact set of cells whose aliveness flipped, computed in the same pass that decides survival — the delta is never recovered afterwards by diffing two finished sets, and `countNeighbors` seeds each live cell at zero precisely so the isolated cell that dies of underpopulation is a candidate that single pass can see), `getNextGeneration` (a projection of `advanceGeneration` for callers with no use for the delta — the Gherkin step definitions; deliberately not a second implementation of the rules), `computeContentBounds` (bounding box of live cells, used to size scrollbars). Neighbor counting is done only around currently-live cells, never by scanning a bounded region.
- **`src/patternLibrary.ts`** — the catalog of the 8 known Life patterns and the queries over it (`getPatternByName`, `patternsByCategory`), plus the anchor convention shared by `patternCellPositions` and `placePattern`: a `Pattern`'s cells are stored relative to its own bounding-box top-left corner, so stamping and previewing can't drift apart. Split out of `gameOfLife.ts` so the Life rules aren't fused with a data table; the dependency runs catalog → model, never the reverse. Distinct from `patternPlacement.ts` below, which owns the _interaction_, not the data.
- **`src/camera.ts`** — the camera and every transform that produces a new one, independent of both the game rules and what's on screen. `Camera` = `{ offsetX, offsetY, cellSize }` in world-space coordinates. Key conversions: `worldToScreen` / `screenToWorld`, with `rectRelativePixels` as the single translation point from a DOM event's client coordinates into the viewport-relative pixel space every pixel-taking function here (and in `scrollbars.ts`) expects. Handles pan, zoom-at-point (keeps the world point under the cursor fixed), and wheel input (shift+wheel = zoom, plain wheel = pan, with a Firefox/Windows axis-swap workaround — see comment in `applyWheelInput`). Note the deliberate sign asymmetry: wheel-pan and scrollbar-drag follow the "document scroll" convention, drag-to-pan doesn't.
- **`src/gridGeometry.ts`** — which part of the infinite grid is on screen and which coordinates are reference lines: `computeVisibleRange` (viewport plus a small buffer) and major-gridline computation every 10 cells. Takes a `Camera` but never returns one.
- **`src/cellTiles.ts`** — the tile-virtualized mounting policy: which world tiles are mounted, and when that set changes, replacing `cellLattice.ts`'s coverage half. Tiles are fixed `TILE_SPAN_CELLS` (4) cells square, world-anchored rather than viewport-relative, so a retained tile's own cells never change coordinates while it stays mounted — a pan re-renders only the entering/exiting strip of tiles at a boundary, not the whole mounted set. `coveringTileRange` computes the exact minimal `TileRange` a camera/viewport needs; `tileRangeHolds`/`nextTileRange` are eviction hysteresis (`EVICT_LAG_TILES` = 1): keep the previous range while it still contains the required one and exceeds it by at most one tile per side, and otherwise rebuild onto the **eviction-lag-clamped union of the previous range and the required one** — not onto the required range exactly, which is what the `fix-tile-hysteresis` slice changed and what makes a sub-cell wobble at a tile boundary cost one rebuild instead of one per pointermove. That retention is deliberately not admission overscan, and the distinction is the whole design: per axis the clamp can only ever keep a bound the previous range already held, so it defers an eviction rather than admitting a tile (see the module header, which also records the two costs it does add — a monotone pan can rebuild twice per tile span instead of once, eviction-only, and a zoom-**in** rebuild retains a four-sided ring where a zoom-out one does not). `nextTileRange` returns its input **by reference** when it holds and is idempotent on its own result, the same no-infinite-loop guarantee `cellLattice.ts`'s `nextLattice` used to carry alone. Stores no `cellSize` — zoom needs no special case, since zooming out fails containment and zooming in fails the lag test, both already covered by the hold/rebuild rule.
- **`src/cellAnchor.ts`** — precision bounding, and nothing else: keeps `(worldCoordinate − anchor) × cellSize` small enough that the compositor's float32 transform matrix stays exact, which is the only half of `cellLattice.ts`'s old origin this module inherits (coverage moved to `cellTiles.ts`, and the two are independent — `cellAnchor.ts` takes `spanCells` as a parameter rather than importing `cellTiles.ts`). `ANCHOR_DRIFT_CELLS` (4096) is how far the camera's offset may drift from the anchor before `nextAnchor` re-quantises, chosen against the float32 integer-exactness cliff at 2²⁴ px. `anchorOffsetPx` is `cellLattice.ts`'s old `latticeOffsetPx`, deliberately just `worldToScreen`: `screenToWorld` resolves taps and hover, and the two must stay exact inverses or a click lands on a different cell than the one under the cursor — `cellAnchor.property.test.ts` pins that identity. `nextAnchor` carries the same by-reference/idempotent contract as `cellTiles.ts`'s `nextTileRange`, applied independently. Because coverage no longer forces a re-anchor, this re-quantises roughly once per 4,096 cells of camera travel instead of on nearly every rebase — rare enough that the cost of that full re-render (~180–200 ms) is an accepted trade rather than a per-pan concern.
- **`src/dragGesture.ts`** — the pointer-drag gesture: `beginDrag`/`advanceDrag` decide when a drag has crossed `DRAG_THRESHOLD_PX` and become a pan rather than a click (the flag latches, so a drag returning near its origin doesn't fall back to a click), and report the incremental pan delta. Deals only in client pixels — it references no `Camera` at all, which is why it stands alone.
- **`src/scrollbars.ts`** — scrollbar thumb sizing, positioning, and drag math. The one camera-side module that knows about the game model (`ContentBounds`), which is exactly why it's separate from `camera.ts`. Scrollbars represent the union of content bounds and current viewport, not content bounds alone (see comment on `computeAxisScrollbarMetrics`) — this keeps the thumb ratio/offset valid even when panned away from all live cells.
- **`src/patternPlacement.ts`** — the pattern-library interaction as one explicit three-state machine (`idle` / `browsing` / `placing`) rather than separate modal-open, armed-pattern, and preview-cell flags, so combinations like "library open with a pattern already armed" are unrepresentable. Exposes transitions (`toggleLibrary`, `armPattern`, `cancelPlacing`, `movePreviewTo`) and queries (`isLibraryOpen`, `armedPattern`, `previewPositions`); callers go through the queries rather than matching on `mode` themselves.
- **`src/liveCellStore.ts`** — the live-cell state itself, as a factory (`createLiveCellStore`) rather than module state: mutators (`advance`/`toggle`/`place`), per-cell subscriptions (`subscribeCell`/`getCellSnapshot`), and one content-bounds subscription (`subscribeBounds`/`getBoundsSnapshot`). The design is one invariant: **a mutation notifies exactly the cells whose aliveness changed, each exactly once, and nobody else.** That is the whole value of the module — a store notifying every subscriber would render identical pixels and pass every rendering, Gherkin and e2e test — so it is pinned by `liveCellStore.property.test.ts` as per-listener call counts, not by set equality. Two more contracts: every mutator funnels through a single private `publish()`, which re-freezes even though immer already auto-freezes (auto-freeze is a _global_ immer setting and can be defeated by a leaked scope — read the comment before removing it), so `getLiveCells()` is **always** frozen and typed `ReadonlyLiveCells`; and `getBoundsSnapshot()` keeps its object identity whenever the box hasn't moved, which is what stops `useSyncExternalStore` re-rendering the scrollbars every tick. `getLiveCells()` is inspection/export only and **never** a render source — a component reading it during render reads a value it never subscribed to, which is a correctness bug, not a missed optimization.
- **`src/liveCellSeed.ts`** — deterministic live-cell seeding for the render-performance harness (`perf/`): `parseSeedRequest` reads a `?cells=&spread=&seed=` query string, `buildSeededLiveCells` places exactly that many cells from a `Math.imul`-based LCG, and `seedFromSearch` is the two together. Only ever reached from `src/main.tsx` under `MODE=perf`, but deliberately a framework-free module rather than harness code: a seeder that silently produces the wrong population makes every perf number measured against it wrong too, and nothing downstream would notice — so it lives where mutation testing and property tests can see it. It takes the query string as an argument and never reads `location` or `import.meta.env` itself; `rules/no-dom-in-domain.yml` and `rules/no-build-env-in-domain.yml` enforce both.
- **`src/cache.ts`** — a keypath-trie cache (`createCache`, `CacheError`): entries are addressed by an arbitrary `unknown[]` key path, and the trie nodes are `PATH` or `ENTRY` (a node can be both a stored entry and a parent of deeper ones). Deliberately mutable rather than immutable, which its header comment argues at length and which is the reason to read that comment before "modernising" anything here — insert/update/remove mutate each node's `Map` in place so they stay O(keypath), where the clone-per-write immutable form (including immer's, whose `prepareMapCopy` shallow-clones the base Map on first write inside `produce()`) would be O(entries). Iteration is fenced: a mutation during a `for...of` over the cache invalidates the iterator and the next step throws, rather than silently yielding a torn view. The node representation stays private to the file — the exported surface is `createCache`, its two interfaces (`Cache`/`ReadonlyCache`), and `CacheError`.
- **`src/equality/`** — structural equality comparators, four files: `is-strict-equal.ts` (a typed `Object.is`), `container-equality.ts` (the walker: container-kind dispatch over Date/Set/Map/Array/plain object, taking the leaf comparison as an injected `compare` function), and the two one-line comparators that inject into it — `is-shallow-equal.ts` (leaves compare with `Object.is`) and `is-deep-equal.ts` (leaves compare with `isDeepEqual` itself, so it recurses). The injected comparator is the whole design: every branch that isn't a leaf comparison — kind dispatch, mismatch handling, size/key-count guards, Set multiset matching — exists exactly once, which is what stopped the two ported implementations from re-diverging (they were a near-verbatim duplicate of each other, and the mismatch bugs they carried were present in only one of the two directions). Read each comparator's scope contract before reaching for one: these are for small, known-shallow projections, and a Set of non-primitives costs O(n*m) per level.

Those sixteen form a small acyclic graph, and keeping it acyclic is the point of the split: `gameOfLife.ts`, `camera.ts`, `dragGesture.ts`, `cache.ts`, and `is-strict-equal.ts` import nothing; `patternLibrary.ts` → `gameOfLife.ts`; `gridGeometry.ts` → `camera.ts`; `cellTiles.ts` → `camera.ts`; `cellAnchor.ts` → `camera.ts` (neither imports the other — `spanCells` is a parameter both take rather than a shared import); `scrollbars.ts` → `camera.ts` + `gameOfLife.ts` (the single place the camera side touches the game model); `patternPlacement.ts` → `patternLibrary.ts`; `liveCellSeed.ts` → `gameOfLife.ts`; `liveCellStore.ts` → `gameOfLife.ts` + `patternLibrary.ts` + `equality/is-shallow-equal.ts`; `container-equality.ts` → `is-strict-equal.ts`; `is-shallow-equal.ts` → `container-equality.ts` + `is-strict-equal.ts`; `is-deep-equal.ts` → `container-equality.ts`. `cache.ts` and `src/equality/**` are the two general-purpose utilities imported wholesale by the `import-utilities` slice rather than grown from a feature. `is-shallow-equal.ts` acquired its first caller in the `live-cell-store` slice (the bounds-identity check above); `cache.ts` and `is-deep-equal.ts` still have none. They live here, inside every gate, rather than in a `src/catalyst/`-style exclusion, precisely because this repo now maintains them. A new domain module is covered by `rules/*.yml` with no rule edits whether it sits at `src/` root or in a subdirectory: ast-grep's `*` crosses `/`, so the domain rules' `files: src/*.ts` glob reaches `src/<dir>/*.ts`, **and their `ignores: src/*.test.ts` entry reaches `src/<dir>/*.test.ts` by the same rule** — a subdirectory's test files are excluded exactly like a root module's. `crap4ts.config.ts` and `stryker.config.json` scope by `src/**`, so they reach a subdirectory too. Prefer flat at `src/` root for a single cohesive module; a subdirectory is fine for a set of siblings that belong together (see `src/equality/`). (Measured twice against ast-grep 0.45.1 — once before `src/equality/` existed and again on the landed tree, both times with a throwaway probe module plus a `.test.ts` twin: the domain rules fired on the module and never on the twin. This paragraph previously claimed the opposite; it was wrong.) File naming follows the same split: `src/` root modules and `src/hooks/` are camelCase, `src/components/` is PascalCase, and `src/equality/` deliberately keeps the kebab-case names it was ported under — a decision, not drift, since the file names double as the identifiers a reader looks up when tracing these back to their source.

`src/catalyst/` sits apart from all of the above: it's vendored third-party Tailwind Catalyst UI primitives, dropped in as source rather than installed as a dependency. It isn't code this project authors, and it's deliberately outside every quality gate — `crap4ts.config.ts` and `stryker.config.json` each carry an explicit `src/catalyst/**` exclusion (`scripts/halstead4ts/run.ts` inherits it by resolving crap4ts's globs), and `.dry4tsrc.json` ignores `**/catalyst/**`. Note that's an exclusion rather than an omission: since both tools measure `src/**` by glob, anything dropped into `src/` is scored unless something says otherwise, so a second vendored directory would need the same three entries added. Components import from it as needed. Treat it as a library boundary: read it to learn a component's props, but don't refactor it to this repo's conventions or add it to a tool's include list.

### State flow

- **Live-cell state does not live in React at all.** `src/App.tsx` holds one `useState(() => createLiveCellStore(initialLiveCells))` — a stable handle, never a value that changes — and passes the store down as an opaque handle. Nothing between `App` and the leaves re-renders on a generation tick: `LifeBoard`, `Grid` and `GridCells` accept `store` and read nothing out of it, and only the components that actually subscribe (`Cell`, one per visible cell, and `GridScrollbars` for the bounding box) re-render, and only when their own subscription fires. This replaced `use-immer`'s `useImmer` (now removed from `package.json`): a producer hands back a new `Set` identity every tick, which defeats React Compiler's memoization however deep the prop drilling goes, so every visible cell re-rendered on every tick. `App.tsx`'s one optional prop, `initialLiveCells`, exists solely for the perf harness; `undefined` (every normal boot) means the ordinary empty grid.
- `src/components/GenerationHud.tsx` owns the `generation` count and the Next Generation button, advancing only via that button's own click/keyboard handling — there is no global keyboard shortcut for it. It takes `onAdvance` (wired to `store.advance`) and holds no live-cell data, so a tick re-renders the counter and nothing else above the grid.
- `src/main.tsx` is bootstrap, not a composition root: it reads `import.meta.env.MODE` and passes the _result_ down. That check has to be at the entry module for Rolldown to constant-fold it and tree-shake `liveCellSeed.ts` out of a normal production bundle, which is why `rules/no-logic-in-composition-root.yml` deliberately doesn't scope it and `rules/no-build-env-in-domain.yml` guards the same invariant from the other side. The file holds exactly one ternary and no other decision.
- Each hook in `src/hooks/` owns exactly one piece of state or one browser API, and delegates the actual rules to a framework-free module: `useCamera.ts` owns the `Camera` as local `useState` and exposes pan/zoom/wheel/center/scrollbar-drag actions that delegate to `camera.ts` and `scrollbars.ts`; `usePatternPlacement.ts` owns the `PlacementState` and its Escape-to-cancel listener, delegating every transition to `patternPlacement.ts`, and takes the place-a-pattern commit callback so that single-shot stamping (read the armed pattern, commit it, disarm) is one action here rather than a two-call sequence a caller could get wrong; `useElementSize.ts` isolates `ResizeObserver`; `useWheelInput.ts` isolates the native, non-passive `wheel` listener and hands callers a `WheelInput` instead of a DOM event; `useGridPointerGestures.ts` isolates pointer capture and drag-vs-tap resolution (delegating the threshold math to `dragGesture.ts`), reporting rect-relative pixels and never touching a `Camera`; `useInitialCentering.ts` isolates the one-shot first-non-zero-measurement latch (`useLayoutEffect` + a ref, so no frame paints uncentered); `useCellTiles.ts` holds two independent sticky values as two `useState`s — a `TileRange` (mounting coverage) and an `Anchor` (precision bounding) — returning the range as an object (reference-stable by `nextTileRange`'s own contract, so this is not a regression of the old hook's scalar-flattening discipline) alongside the anchor's pixel offset as scalars, delegating the keep-or-rebase decision for each to `cellTiles.ts`'s `nextTileRange` and `cellAnchor.ts`'s `nextAnchor` independently (read the hook's comment on why both coverage checks run during render rather than in a `useEffect`); `useRafCoalescedPan.ts` isolates `requestAnimationFrame`, summing however many pan deltas arrive within one frame into a single `onPan` call and exposing `flush()` so a pointerup settles the camera synchronously instead of waiting on a queued frame. That split is what keeps the rules testable without a jsdom environment — put new logic in the pure module and let the hook stay a thin adapter.
- `src/components/LifeBoard.tsx` is the composition root for the camera and placement state: it calls `useCamera` and `usePatternPlacement`, derives `previewPositions`/`armedPattern` from already-tested pure functions, and supplies `Grid`'s `renderOverlays` render prop with the ruler, zoom-%, scrollbars, toolbar, and pattern-library modal — in that stacking order, since all of them are `position: absolute` with auto z-index and a later sibling wins hit-testing (`GridToolbar` at `top-2 right-2` must render after `GridScrollbars`' track, or it can't be clicked where it overlaps). It deliberately touches **no** live-cell data — it only forwards the `store` handle and `store.toggle` — so a generation tick never re-renders it; the content-bounds subscription that used to sit here was pushed down into `GridScrollbars`, the one overlay that needs it. `LifeBoard.tsx` is deliberately outside every quality gate, like `App.tsx` — kept wiring-only mechanically by `rules/no-logic-in-composition-root.yml` (ast-grep, report-only) rather than by unit-test coverage; its own small `LifeBoard.test.tsx` exists only to recover the two behaviors no unit below it can prove alone (that a pointer tap on the grid actually reaches `usePatternPlacement`'s single-shot `stampArmedPattern`, and the Patterns-button-while-placing cancel path) that would otherwise be e2e-only.
- `src/components/Grid.tsx` owns the measurement (`useElementSize`), the pointer/wheel listeners (`useGridPointerGestures`, `useWheelInput`), the one-shot initial centering (`useInitialCentering`), and the DOM sibling-not-ancestor layering between `#grid-content` and whatever `renderOverlays` returns — but it imports none of `GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, or `Scrollbar.tsx` directly. Those four are inverted: `Grid` takes a `renderOverlays(context)` render prop (`context` carries only what `Grid` measures and its caller can't — viewport `size` and the computed `visibleRange`) instead of importing and rendering them itself, so `LifeBoard` supplies the actual overlay components rather than `Grid` hardcoding them. The deliberate exceptions are `Grid → GridCells → CellTile → Cell` and `Grid → PatternPreview`: cells must render _inside_ `#grid-content`, and owning that containment is exactly why `Grid` exists as its own component rather than folding into `LifeBoard`. Inside `#grid-content`, `Grid` renders two siblings in DOM order — a transformed layer div wrapping `GridCells`, then `PatternPreview` (later-in-DOM wins, and the preview must paint over the cell buttons rather than behind them). **The pan transform sits on that inner layer div and never on `#grid-content` itself**, which is load-bearing rather than stylistic: `useGridPointerGestures` and `useWheelInput` both call `getBoundingClientRect()` on `#grid-content`, so a transform there would shift that rect and silently resolve every tap and hover to the wrong world cell. `Grid.test.tsx` asserts `#grid-content` carries no transform (and, in its own comment next to that assertion, that the layer div's own transform is a pure `translate(...)` with no `scale` — this app re-lays-out on zoom instead of scaling, which keeps `getBoundingClientRect()` and layout units from disagreeing the way a scaled scroll container's would), for exactly that reason. `GridCells` consumes nothing that changes per tick _or per pan_: it iterates `useCellTiles`'s world-anchored `TileRange` (see `cellTiles.ts`), rendering one `CellTile` per mounted tile keyed by `tileKey(tx, ty)` — the tile's own world coordinates, not a lattice-style linear slot index — rather than a camera-derived cells array, and every prop it receives is pan-stable. `CellTile` renders `TILE_SPAN_CELLS²` `Cell`s as a fragment (no DOM node of its own, so the flat button-list DOM shape is unchanged from before tiling); keying by world coordinate is the load-bearing inversion from the lattice design this replaced, where a rebase reused DOM nodes at a new origin under a linear slot index instead — here, a retained tile's `tileX`/`tileY`/`spanCells`/`store`/`onActivate`/`cellSize`/`anchorX`/`anchorY` props never change while it stays mounted, so React's reconciler bails on it entirely and only the entering strip of tiles at a crossed boundary re-renders. `Cell.tsx` owns the `useLiveCell(store, key)` subscription for its own coordinate and takes a finished CSS `transform` string rather than pixel numbers, so it holds neither a `Camera` nor any pixel geometry. `PatternPreview.tsx` is the one place that stays camera-exact — it sits outside the transformed layer and recomputes `worldToScreen` per position, which is affordable because it is bounded by the armed pattern's own size, not by the viewport. That split is the point of the layer: a tick re-renders only the handful of `Cell`s whose membership flipped, not the ~34,000 mounted at min zoom, and a pan that stays within the current tile range's eviction hysteresis re-renders none of them — only a pan that crosses a tile boundary re-renders the entering strip, a small fraction of the mounted set (`cellTiles.ts`'s `enteringStripCellCount`), which is what replaced the old lattice's all-or-nothing rebase. `Grid.tsx` has its own unit tests (`Grid.test.tsx`), now scoped to that composition — the DOM layering contract, the place-vs-toggle dispatch, and one thin wiring test per hook — rather than the ~1,575-button, ~500ms-per-test renders it used to pay for when it rendered the whole tree itself; the hooks and pure modules it composes, and the four inverted overlay components, are each tested on their own.

### Testing structure (four layers, deliberately separate)

1. **Unit/property tests** — `src/*.test.ts` and `src/*.property.test.ts` (fast-check via `@fast-check/vitest`) for each of the framework-free modules (`src/equality/`'s own tests are one directory deeper, but land in the same two projects), plus `src/hooks/*.test.ts` (`@testing-library/react`'s `renderHook`) and `src/components/*.test.tsx` (`@testing-library/react`'s `render`/`screen`/`fireEvent`, jest-dom matchers via `src/test-setup.ts`) for the twelve unit-tested components (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `CellTile.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`). These run across four vitest projects, not one (see `vite.config.ts`'s `test.projects`): the framework-free-module tests run under the `unit` and `property` projects in plain Node — no `document`, no jsdom cost — while the hook and component tests run under the `dom` project in jsdom, since only those actually render. The fourth, `acceptance`, is jsdom too and belongs to layer 3 below rather than to this one. A new test file lands in `unit` by default (it's the project that subtracts rather than includes) and fails loudly if it needed jsdom after all. One consequence worth knowing before writing a property test: `property`'s `include` is the bare `**/*.property.test.ts`, which is _not_ rooted at `src/` root, so a `*.property.test.ts` placed under `src/hooks/` or `src/components/` would be collected by both `property` (Node, no React plugin, no jsdom) and `dom`, and fail in the first. That is a feature, not a gap — property tests belong in the framework-free layer, and a hook-resident invariant worth quantifying over is a signal to extract the rule into a module rather than to reach for a config exception. This is where implementation correctness lives — edge cases, invariants, and the numeric precision (`-0` handling, clamp boundaries, same-reference no-ops) that a Gherkin Examples table can't express.
2. **Browser-required unit tests** — `src/**/*.browser.test.ts` (co-located with the module they cover, run by `npm run test:browser` via `vitest.browser.config.ts` — Vitest Browser Mode driving real Chromium, reusing the Playwright binary `npm run test:e2e` already installs). Same kind of test as layer 1, and owned by the same roles (`coder`/`cleaner`/`architect` — never `product`): it imports one module directly and never boots the app. It exists only for contracts jsdom has no faithful equivalent for, currently just `useElementSize.browser.test.ts`, which pins down that the real `ResizeObserver` fires an initial callback from `observe()` itself and delivers an update on a real size change — neither of which the jsdom stub in `src/test-support/domStubs.ts` reproduces (it fires only when a test calls `.resize()`). This layer is **additive only**: `vite.config.ts` excludes the `*.browser.test.ts` suffix, and since `crap4ts`/`npm run test:mutation` both run through that config, neither can see these files. Moving an assertion out of a jsdom test into one of these silently drops coverage and mutation score on the module — always leave the jsdom test in place. See `.claude/agents/articles/engineering.md` for which layer a given test belongs in.
3. **Gherkin acceptance tests** — `features/*.feature` (plain-English specs) paired 1:1 with `features/*.steps.test.ts(x)` (step definitions using `@amiceli/vitest-cucumber`, run by vitest — these are _not_ Playwright and don't need a browser). `features/` is `product`'s entire manifest — the directory is the user-facing contract, end to end, and the **suffix** is what separates the layers inside it: `.feature` (the contract), `.steps.test.tsx` (its black-box executable form), `.steps.test.ts` (not yet migrated — see `vite.config.ts`), and `.e2e.spec.ts` plus `e2e-helpers.ts` (the Playwright layer, item 4 below). **The two step-file extensions are two different kinds of test, and the extension is the only discriminator** — a project `include` glob cannot split one extension by content. A `.steps.test.ts` file exercises the framework-free modules directly and never touches the DOM; a `.steps.test.tsx` file boots the real `<App />` in jsdom and drives it through ARIA, naming no `src/` module at all. `cell-life-and-death` is the first converted (the `black-box-acceptance-pilot` slice); the other six are still direct-call, which is what the overlap note below is about. Their assertions often overlap substantially with the unit tests covering the same functions (an architect review confirmed this for `grid-reference-lines`, `mouse-wheel-controls`, `infinite-grid`, `grid-scrollbars`, `camera-pan-and-zoom`, and `cell-life-and-death` — same functions, frequently the same literal inputs) — that overlap is expected and not a bug to fix. This layer's purpose is the stakeholder-readable, accepted-behavior contract and the `product`→`coder` handoff (see Subagent pipeline below), not incremental defect detection beyond the unit tests; don't chase assertion parity or treat the overlap as duplication to eliminate. The one feature that isn't overlap-redundant is `pattern-library.feature`, whose Examples table is the only place the exact cell geometry of all 8 patterns is pinned down — the unit and property tests check names, categories, and the bounding-box anchor convention, but never the shapes themselves.

   **This layer is no longer part of `npm run test:mutation` at all** — `stryker.config.json`'s `ignorePatterns` keeps `features/` out of the sandbox, landed by the `stryker-excludes-gherkin` slice on the strength of the measurement below. The measurement is kept because it is the argument for that exclusion, and because it is the only written account of _why_ a `killedBy` naming a step test never meant what it looked like. Read it as history plus method, not as a description of what the gate currently runs.

   **When you need to know whether the Gherkin layer is the sole killer of a mutant, the removal experiment names _candidates_ and nothing more; the verdict is hand-applying the mutant and running the whole unfiltered suite. Never trust Stryker's `killedBy` when it names a `features/**` test — against a step-per-test runner it is a false positive whenever a scenario's setup steps fall outside the covering set, which is the normal case rather than the exception.** Measured against Stryker 10.0.0 / vitest 4.1.10 / `@amiceli/vitest-cucumber` 7.0.0.

   - **The removal experiment is still the right screen**, and a `coveredBy` screen is still wrong every time: all six `src/scrollbars.ts` mutants that survive once `features/**` is removed are `coveredBy` `scrollbars.test.ts` and `scrollbars.property.test.ts` and killed by neither, so `coveredBy` answers "covered, therefore fine" about mutants nothing kills. **The recipe inverted when the exclusion landed**: the arm that needs constructing is now the one that puts the layer _back_. It is two `--mutate`-scoped Stryker runs — the ordinary `stryker.config.json` against a copy of it carrying `"ignorePatterns": []` (and its own `tempDirName`, so the two sandboxes can't collide) — neither passing `--incremental`, for the reason the mutation-testing note in Commands gives. It used to be the reverse: a copy of `vite.config.ts` with `'features/**'` prepended to `sharedExclude`, selected via `{ "vitest": { "configFile": "vite.config.probe.ts" } }`. Don't reach for that form now; `ignorePatterns` is the one lever, and a `sharedExclude` probe would be subtracting a layer the sandbox no longer contains. What the experiment cannot do, in either direction, is separate real Gherkin coverage from a spurious Gherkin kill — **removing the layer removes the false kill along with the true one, so both present identically as "survives without `features/**`".**
   - **A `--mutate`-scoped probe's dry run does not collect the whole suite, and its test counts are not the full run's.** `@stryker-mutator/vitest-runner`'s `vitest.related` option defaults to **true** (its own `dist/schema/vitest-runner-options.json`), so `dryRun` hands the mutated files to vitest's `--related` and only test files importing them are collected. Measured on 10.0.0 / vitest 4.1.10, scoped to `src/equality/is-strict-equal.ts`: 267 tests collected with `ignorePatterns: []` against 219 with the landed `["/features"]` — a 48-test delta that is exactly `cell-life-and-death.steps.test.tsx` (it boots `<App />`, so it is related to almost everything), while the six direct-call `.steps.test.ts` files never entered either arm because they don't import `equality/`. Read those numbers as related-scoped to one file. A full-scope run passes every mutated `src/` file as related, which is why the whole layer is in it.
   - **`killedBy` naming a step test proved nothing, and can no longer happen at all** — the sandbox has no `features/` in it, so no Stryker attribution can name a test from that layer. The mechanism is kept because it is general: it is a property of a step-per-test runner meeting Stryker's covering-test filter, and it will recur the moment any layer compiles one logical case into several `test`s. A mutant run set `project.config.testNamePattern` to a regex built from the covering test names only (`node_modules/@stryker-mutator/vitest-runner/dist/src/vitest-test-runner.js`), and vitest-cucumber compiles every _step_ into its own `test`. A scenario's `Given`/`And` steps usually touch a different module than its `When`, so they are not in the covering set, get filtered out, and the `When` then runs on empty closure state and throws. That failure is scored as a kill. Reproduce it on **unmutated** source in one command — `npx vitest run features/grid-scrollbars.steps.test.ts -t "the scrollbars are drawn for an 800 by 600 pixel viewport"` gives 5 failed / 33 skipped with `TypeError: Cannot read properties of undefined (reading 'size')`, and `npx vitest run features/cell-life-and-death.steps.test.tsx -t "I toggle the cell at"` fails the same way on an unrendered `board`. Those "killer" tests fail whether or not a mutant is active. **Both `-t` patterns quote live step text, so `product` rewording a step silently retires the command** — which is what happened to the first one (`prune-gherkin-to-domain-language` renamed that `When`), and the failure mode is the dangerous direction: a `-t` matching nothing exits **0** with every test skipped (measured: 38 skipped, 0 run), so a stale repro reads as "the mechanism has been fixed" rather than as a broken command. Check the run actually collected tests before concluding anything from it.
   - **`killedBy` is first-kill-wins, so an attribution count is not a coverage count.** The runner sets `bail: this.options.disableBail ? 0 : 1` (`vitest-test-runner.js:81`), so vitest stops at the first failing test and Stryker records that one — measured on the `bd7c388` baseline, all 1,278 killed mutants carry **exactly one** `killedBy` entry, never more. So "324 of 1,278 kills were attributed to a `features/**` test" means _a Gherkin step got there first_, not _only a Gherkin step could kill it_. That is the whole reason removing all 324 attributions cost so few real kills: the other tests that would have killed those mutants were simply never reached. **The fact that no mutant was killed by a mix of Gherkin and non-Gherkin tests is an artifact of first-kill-wins, not corroborating evidence** — under `bail: 1` a mixed attribution is unrepresentable. The baseline's attribution table, for the record: 292 of the 324 went to `cell-life-and-death.steps.test.tsx` alone; the largest non-`features/` attributions were `src/cache.test.ts` (173), `src/hooks/useCamera.test.ts` (62), `src/liveCellSeed.test.ts` (57), and `src/components/LifeBoard.test.tsx` (55), with 104 kills carrying an id that resolves to no test file in the report.
   - **The verdict is a direct measurement**: apply the mutation to `src/` by hand, run `npx vitest run` with no filter at all, and read which files fail. Done for all ten mutants the Gherkin layer has ever been credited with killing (6 in `scrollbars.ts`, 2 in `gameOfLife.ts`, 1 each in `camera.ts` and `liveCellStore.ts` — the full table is in the `prune-gherkin-to-domain-language` adjudication commit): **all ten leave the suite green.** Five are equivalent mutants, five were simply untested and now carry unit tests. **The Gherkin layer's contribution to the Stryker score is zero mutants** — the measured form of what this layer's purpose paragraph already says in prose, and the finding the `ignorePatterns` exclusion acts on: **the counterfactual is now the default**, so a full-tree run no longer has `features/**` to remove. The removal-experiment run scored **98.70%** against `break: 85` on the tree it was measured on; no figure for the current tree is written here, because `hardener`'s `npm run test:mutation:full` on the landed change is what produces one, and a literal copied forward here would be stale before the next slice lands. (Two correct numbers already went stale inside this one slice — 98.70% and 99.00%, each right about a different tree.) **That is not a licence to delete scenarios.** Unit coverage is what makes a deletion _safe_; what makes one _permissible_ is that the promise survives in `features/**` at domain altitude — already stated by a sibling scenario, or restated in the feature it actually belongs to. "A unit test covers it" discriminates nothing, since by this measurement it is true of every scenario in the directory. (Ruled in `prune-gherkin-to-domain-language`'s review, over the two whole outlines that slice deleted rather than merely un-tabled: one named a browser event field no user can observe, the other moved to `camera-pan-and-zoom` and is asserted there.)
   - Per-test attribution is unreliable in the other direction too, and that was recorded first: see the mutation-scan note above `getBoundsSnapshot` in `src/liveCellStore.ts`, where a non-equivalent mutant is reported `Survived` with its actual killers listed as having run.
   - One caution from the same measurement: a kill reported as `Timeout` rather than an assertion failure is a wall-clock artifact of a component test and not coverage anyone should rely on, and the survivor set at the margin moves between runs because of it.

4. **Black-box e2e tests** — `features/*.e2e.spec.ts` (Playwright, real Chromium, run against `npm run dev` on a fixed 1280×900 viewport), alongside the Gherkin layer in `product`'s one directory. `features/e2e-helpers.ts` has shared helpers; many pixel-math assertions are derived from the exact default camera (`offsetX: -32, offsetY: -22.5, cellSize: 20`) that results from that fixed viewport — read the comments in that file before changing default camera values or the viewport size. A spec whose name matches a `.feature` file is the browser-level counterpart of that same feature; an unpaired spec (currently `hud-layout-and-shortcuts` and `modal-inertness`) covers behavior with no pure-logic layer to specify in Gherkin — layout, hit-testing, stacking, App-level wiring — and is specified by `product`'s plain-English outline instead, which it records in the spec's own header comment so the accepted behavior stays written down.

**The black-box step form: three facts a conversion must be built around.**

_First, `@amiceli/vitest-cucumber` compiles every Gherkin **step** into its own vitest `test`, not every scenario._ Measured on 7.0.0: `cell-life-and-death.feature` collects **48 tests, not 13**, with `ancestorTitles` naming the scenario and the test itself named for the step. `src/test-setup.ts` installs a global `afterEach(cleanup)`, so **that cleanup fires _between_ a scenario's `Given` and its `When`** — an RTL-`render`ed tree cannot survive one scenario, and the failure reads as a bare `expected null not to be null` in the `Then`, which looks nothing like a lifecycle problem. `features/acceptance-harness.tsx` works around it by owning its own `createRoot` container (`cleanup()` is then a no-op for the board, and `mountBoard()` unmounts the previous one), which is why it does not call `render()`. **Every future conversion inherits this.** Verify it the same way rather than assuming: read the collected-test count off `npx vitest run --project acceptance`.

_Second, the harness is test infrastructure and is **not** expected to carry its own unit tests._ It is the `features/`-side peer of `src/test-support/`, which is already excluded from `crap4ts.config.ts` and `stryker.config.json` for exactly this reason, and requiring coverage of it would gate a category this repo has deliberately decided not to gate. (An ad-hoc `--mutate` run over `acceptance-harness.tsx`, outside every configured gate, scores 60.63% with 33 survivors; the `[NoCoverage]` rows are throw paths a passing suite never enters, and the two teardown survivors are individually near-equivalent.) That is not the same as unverified — three things check a harness, and a conversion should be able to point at all three: the steps suite going green end to end (which exercises every mount, query and teardown path a scenario uses), `npm run acceptance-mutation`'s per-mutant collected-test-count discipline, and the harness's own `assertRequiredWindowMounted()`, which fails loudly if the mounted world rectangle ever stops containing what the feature and its mutants need.

_Third, a `fireEvent.click` on a cell in this layer is **not** the route a mouse user takes, and the difference is not a jsdom artifact._ `useGridPointerGestures` takes pointer capture on `#grid-content`, which retargets the subsequent native `click` to the container — so `Cell`'s own `onClick` never fires for pointer-driven interaction, and `Grid`'s `onTap` resolves the cell from pointerup pixels through `screenToWorld` instead. `Cell.onClick` is therefore the **keyboard-activation** route (Enter/Space), and jsdom's `fireEvent.click` dispatches a bare `click` with no pointer sequence — so this layer drives that keyboard route and never exercises hit-testing at all. **Read the two black-box layers as nested, not complementary.** The e2e layer drives _both_ routes: Playwright's `.click()` for the pointer route, and `page.keyboard.press('Enter')` on a focused cell button for the keyboard one (`features/hud-layout-and-shortcuts.e2e.spec.ts:102`). The acceptance layer therefore sees a strict subset of the routes the browser layer sees, plus no hit-testing — it is not reaching anything Playwright structurally cannot. Measured on this tree by injecting `Cell`'s `onActivate(x, y)` → `(y, x)`: the acceptance project fails (5 of its 48 step-tests), the full Playwright run is **58 passed / 1 failed** — the failure being that keyboard test, on `aria-pressed` — and all **14 tests** in the paired `cell-life-and-death.e2e.spec.ts` pass, every activation there being a `.click()`. What survives of this is the narrow half only: **a green acceptance run is not evidence about hit-testing**, which is exactly what it cannot see. (Commit `4f6e14d`, "record why the e2e layer cannot see `Cell.onClick`", concluded the opposite — "disjoint activation routes", "passes all 14 e2e specs" — from a Playwright column pre-registered as that one paired spec file, and generalized to the layer; `product`'s VERIFY pass refuted it by running the whole layer. Its subject line and body cannot be rewritten, so this paragraph is the correction.)

There is no single default jsdom run any more — `vite.config.ts`'s `test.projects` splits the main vitest config into `unit`/`property` (Node) and `dom`/`acceptance` (jsdom) projects (see Architecture above) — but all four projects still exclude `**/*.e2e.spec.ts`, `**/*.browser.test.ts`, and `**/*.perf.spec.ts` via the shared `exclude` list, so the three runners (this config, `vitest.browser.config.ts`, and Playwright) never collide.

`npm test`/`npx vitest run` with no `--project` flag runs all four (`unit`, `property`, `dom`, `acceptance`); `npm run test:unit` and `npm run test:property` narrow to a subset via `--project`, which is the only way to filter which project(s) run once `test.projects` is set — a plain `--exclude` on the CLI has no effect there. `--project` matches by the project's `name`, so `npx vitest run --project dom <path>` (or the bare `name`, or a `!name` negation as `test:unit` uses) is how to run just one project's slice of the suite. Be aware a vitest project whose `include` glob matches nothing simply reports 0 files and exits 0 — there is no warning — so if `dom`'s globs (`src/components/**` and `src/hooks/**`) ever stop matching anything (e.g. one of those directories gets renamed), `npm test` stays green while quietly running 15 fewer files; see the comment in `vite.config.ts` for the other files that same rename would need to update.

`perf/` is a fifth top-level directory of Playwright specs, and deliberately **not** a fifth test layer: it measures render cost and asserts nothing about performance (see `perf/README.md`). It is outside every quality gate on purpose, which is why the split described under "Custom quality tooling" below matters — the numbers themselves are computed in `scripts/perf-report/`, which is gated.

### Custom quality tooling in `scripts/`

`scripts/` is TypeScript, not JavaScript, and is its own project — separate `tsconfig.scripts.json`, `vitest.scripts.config.ts`, `crap4ts.scripts.config.ts`, and `stryker.scripts.config.json` from the ones covering `src/`/`features/` above. It's the tooling every other role's quality gate runs on, so it's held to the same CRAP threshold (6) as `src/`, via its own parallel commands (`npm run test:scripts`, `npm run test:coverage:scripts`, `npm run crap4ts:scripts`, `npm run dry4ts:scripts`, `npm run test:mutation:scripts`) — see `.claude/agents/articles/engineering.md`'s "Working inside scripts/" section for exactly which command each pipeline role substitutes for its usual `src/`-scoped one.

Its layout is two levels and no more: **`scripts/<program>/` holds one program's own modules** (its `run.ts` shell plus the pure modules that shell delegates to), and **a file at `scripts/` root is shared by two or more programs**. `scripts/feature-files.ts` is the current example — `listFeatureFiles` is the one place that answers "which `.feature` files exist", used by both `acceptance-mutation` and `gherkin-dry-checker`, which previously carried two independent hardcoded copies of that list that went stale separately. Shared root modules are ordinary product code and sit inside the gates exactly like a program's own modules; the one exception is `scripts/test-support.ts`, which is test infrastructure and is excluded by the same `**/test-support.ts` glob in `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` that already excludes `scripts/perf-report/test-support.ts`. **Imports run program → shared and never the reverse**, which is what keeps the shared file safe to change: a root module that reached back into a program directory would couple every other program to that program's internals. Nothing checks that direction mechanically yet — with two shared files it's prose, and `architect` should encode it as an ast-grep rule at the first violation or the third shared module, whichever comes first (a `files:` glob can't express "`scripts/` root only", since ast-grep's `*` crosses `/`, so that rule needs the throwaway-probe measurement this file describes for the domain rules).

- `scripts/acceptance-mutation/` — **owned by `product`, not `hardener`** (it mutates the _spec_ and asks whether the _steps_ notice, so both sides of what it measures are `product`'s). Mutates individual values in `.feature` Examples tables (never source code) and reruns the corresponding steps file to check the scenario actually notices (concept from unclebob's Acceptance-Pipeline-Specification). Each mutant runs the _entire_ steps file, not a filtered subset, since Given/When/Then steps share closure state within a scenario. In practice this hardens the Gherkin layer against itself — the weaknesses it has surfaced so far were in step definitions absorbing a mutated value without noticing, not in the framework-free modules themselves — so treat it as acceptance-suite quality assurance, not as evidence the Gherkin layer is finding core-logic bugs unit tests miss.

  Three things it does before it will score anything, each of them closing a way the runner could report a confident number about nothing. **Targets are discovered from `features/`**, not from a hardcoded table (`discovery.ts`, over `scripts/feature-files.ts`) — a `.feature` with no partner, a partner claimed twice, or a steps file with no `.feature` all abort by name; `.steps.test.ts` and `.steps.test.tsx` are both accepted, since that extension is the only discriminator between the node and jsdom step-definition forms. **Every target's steps file runs once against its unmutated feature first**, and a baseline that isn't green (nonzero exit, unreadable summary, or zero tests collected) aborts the whole run naming the target — there is no trustworthy test count to compare its mutants against, so proceeding would misreport them rather than merely under-report. **Each outcome is read from vitest's JSON reporter** (`--reporter=json --outputFile=`, written to a fresh path per mutant so a crashed run can never be scored off a previous one's file), never a regex over console text: `killed` requires the same collected-test count as the baseline _plus_ at least one failure, and any other count is `error`. That last one is a repaired defect, not a precaution — the old classifier read a nonzero exit plus vitest's ordinary failure chrome as a kill, so a steps file broken at _import_ (0 tests collected, exit 1) scored as a kill on every mutant, and a wholly broken suite would have reported 100%.

- `scripts/gherkin-dry-checker/` — advisory-only; scans all `.feature` files for step-text vocabulary duplication/drift, discovering them through `scripts/feature-files.ts` (see above) rather than the hardcoded list it used to carry. Always exits 0 on a successful run (report-only), writes to `reports/gherkin-dry/report.json`.
- `scripts/halstead4ts/` — runs `fta-cli` against the same files as `crap4ts.config.ts`'s `include` list and prints a Halstead (volume/difficulty/effort/bugs) + FTA Score table alongside crap4ts's per-function CRAP table. FTA only reports at file granularity (no per-function breakdown), so this is a second, coarser report rather than something merged into crap4ts's output — and since FTA's own score formula isn't published, it's report-only like `gherkin-dry-checker`, never a CI gate. `run.ts` resolves `crap4ts.config.ts`'s own `include`/`exclude` globs rather than keeping a copy of the file list — the two used to be hand-synchronized arrays of the same 21 paths, and a list like that goes stale silently: a module missing from it is simply never reported on, and nothing fails. fta-cli returns no analysis at all (an empty array, not a zeroed-out one) for any file at or under its own size floor — measured at ≤6 code lines, comments not counted — so a file that small renders as an explicit `not scored (under FTA size floor)` row rather than crashing the tool or, worse, vanishing from the report; `src/equality/is-strict-equal.ts` is the first file to hit it.
- `scripts/perf-report/` — turns the raw `RawScenarioSample` JSON files `perf/` writes under `reports/perf/raw/` into `reports/perf/latest.md`/`latest.json`/`history.jsonl`. Report-only, no thresholds. This is where **every** median, percentile, ratio, and unit conversion in the perf harness lives — `perf/` itself computes none, because `perf/` is outside the gates and a wrong statistic there would be silent and plausible-looking. The boundary between the two is a file on disk, not a module import: `import type` crosses it (erased at compile time), a value import never may, in either direction, and `rules/no-value-import-across-perf-boundary.yml` checks that mechanically. It's also a real compiler boundary — `perf/` is in `tsconfig.app.json` (`moduleResolution: "bundler"`, `lib: DOM`) and `scripts/` in `tsconfig.scripts.json` (`nodenext`, no DOM).
- `scripts/ast-grep-rule-check/` (`npm run ast-grep:rules`) — **this is the first of two checks in this list that gate.** Every other check in this list needs judgment to act on; this one is a set of binary facts about `rules/*.yml` + `rule-tests/*.yml`: does every rule have a fixture, does its `id` match its filename, are ids unique, does it declare a valid `severity`, does its fixture carry an `invalid:` case, does every `files:` glob resolve to a real file, does a fixture's own `id` name the rule its filename claims to test (ast-grep binds a fixture to a rule by that `id`, not by the filename, so this is the reverse direction of the fixture-exists check), was at least one rule found at all, and is an `allow-unresolved-files` marker still excusing anything or has every glob it named since resolved (a stale opt-out) — so it exits nonzero on any failure instead of always exiting 0. Rule and fixture files are discovered by reading `sgconfig.yml`'s `ruleDirs`/`testConfigs[].testDir` and recursing into them, mirroring ast-grep's own recursive scan of those directories (verified against 0.45.1) rather than a hand-maintained list or a non-recursive, hardcoded `rules`/`rule-tests` pair — except each testDir's snapshot subdirectory (`__snapshots__` by default, or whatever that `testConfigs[]` entry's `snapshotDir:` names), which `ast-grep test` itself never treats as fixtures (Jest-style snapshot storage) and which this checker skips for the same reason. That skip is scoped to a direct child of a testDir, since that is the only place ast-grep gives the name a meaning: a rule at `rules/__snapshots__/no-foo.yml` is live in `ast-grep scan` (measured), so exempting it would hide a real rule from every check here. The `files:` check has an explicit, reason-required opt-out (`# ast-grep-rule-check: allow-unresolved-files <reason>`) for a rule authored before the file it scopes exists, and deliberately doesn't check `ignores:` globs: an unresolved `files:` glob fails _open_ (the rule silently checks nothing), while an unresolved `ignores:` glob fails _safe_ (the rule just over-applies, which shows up as noisy findings). Owned by `architect`, the only role that authors rules.
- `scripts/agent-doc-check/` (`npm run agent-doc-check`) — **the second checker in this list that gates**, over `.claude/**` + CLAUDE.md itself rather than over `rules/`. Five binary facts: (1) every `npm run <script>` reference in `.claude/**/*.md` + CLAUDE.md names a real `package.json` script (excluding `.claude/worktrees/`, a sanctioned slice-worktree location that holds whole other checkouts — their own `.claude/`, their own `node_modules` — rather than this repo's docs); (2) every `.claude/agents/*.md` file's frontmatter validates — `name` matches the filename, `description` is non-empty, `tools` is a subset of the known tool set, `model` is one of `opus`/`sonnet`/`haiku` (parsed with a bespoke line-anchored reader rather than a real YAML parser, because several agent descriptions contain a literal `": "` that a real YAML parser reads as a nested mapping and refuses — measured to fail exactly this way on 2 of the 5 agent files as they stand); (3) no backticked mention of a retired role (`qa`, `refactorer`, `specifier` — a short, git-verified list of every role ever deleted from `.claude/agents/`, not a generic "role-shaped token" scan, which was tried and rejected for flagging six unrelated backticked identifiers to two real hits when tested against this repo's own docs) without a historical qualifier (old/former/then/merge/...) on the same line; (4) the role-cycle string (`product → coder → cleaner → architect → hardener → product`) is byte-identical everywhere it appears, built from whichever roles currently exist rather than a hardcoded chain so a role rename is picked up for free; (5) every `rules/*.yml` is named in CLAUDE.md, and every explicit `rules/<id>.yml` path CLAUDE.md names resolves to a real file. Same shape as `ast-grep-rule-check` deliberately — pure `decide()` over parsed input, I/O isolated to `run.ts`, one file per parsing concern. Check 1 has no notion of "just an example": a hypothetical script name written in prose without angle brackets reads exactly like a real reference and fails the gate the same way a genuine typo would — write a hypothetical one as `npm run <script-name>` instead (see `npm-run-refs.ts`'s module comment; this checker's own development tripped over exactly that).

All six run via `tsx` (`npm run halstead4ts`/`acceptance-mutation`/`gherkin-dry`/`perf-report`/`ast-grep:rules`/`agent-doc-check`, each `tsx scripts/.../run.ts`) and have their own `.test.ts` unit tests runnable via `npm run test:scripts` — a dedicated Node-environment vitest config; `vite.config.ts` excludes `scripts/**` from the main `npm test`/`npm run test:unit` run, so scripts' tests no longer run there.

`sgconfig.yml` + `rules/*.yml` are a seventh checker, and the only one that isn't a `scripts/` program: [ast-grep](https://ast-grep.github.io) structural rules encoding the architectural invariants that were previously prose only. The sixteen current rules cover domain modules importing React (`no-react-in-domain`), touching the DOM (`no-dom-in-domain` — including bare `location.*`, which never mentions `window`), reading the build/process environment (`no-build-env-in-domain`), or holding module-level mutable state (`no-module-state-in-domain` — a domain module may own state, but only state a factory hands back per instance; the matcher sees the `let`/`var` form only, so a clean run is not proof a `const registry = new Map()` isn't there), imports pointing the wrong way through the framework-free-module → hook → component layering (`domain-imports-upward`), manual `useMemo`/`useCallback` under an enabled React Compiler (`no-manual-memo-ts` / `-tsx`), logic of any kind in the composition root (`no-logic-in-composition-root` — see `LifeBoard.tsx` above), a `Camera` import (value _or_ type) reaching the per-cell leaf components (`no-camera-in-cell-leaf` — scoped to `Cell.tsx`/`CellTile.tsx` by concrete path, since `Grid.tsx`, `PatternPreview.tsx` and `LifeBoard.tsx` all import `Camera` legitimately; a `Camera` prop down there re-renders every mounted cell on every pan tick and defeats the world-anchored tile range), a component importing the tile MOUNTING POLICY, `coveringTileRange`/`nextTileRange`, instead of taking the mounted `TileRange` as a prop (`no-tile-policy-in-components` — scoped to `src/components/*.tsx`, since `useCellTiles.ts` is the one legitimate caller; the mounted range and the bare covering set are deliberately different quantities, by up to `EVICT_LAG_TILES` per side, and a component that recomputed the cover for itself would silently reintroduce the boundary thrash the hysteresis fix exists to stop), value imports across the `perf/` ↔ `scripts/perf-report/` boundary (`no-value-import-across-perf-boundary` — `import type` is fine, see above), the black-box layers reading cell aliveness off its Tailwind paint class instead of through `src/test-support/cellQuery.ts` (`no-aliveness-by-paint-class` — scoped to `features/*.ts` + `perf/*.ts`, the two directories where `bg-gray-900`/`bg-white` can only mean aliveness and where no other checker looks at all, since `dry4ts` runs over `src` alone; deliberately not scoped to `src/**/*.test.tsx`, where the same class is legitimate paint and `Cell.test.tsx` keeps one alive/dead pair as the visual contract on purpose), and product code importing from `src/test-support/` (`no-test-support-in-product-ts` / `-tsx` — a TS/TSX twin pair for the usual different-parsers reason; that directory is excluded from `crap4ts.config.ts` and `stryker.config.json`, so such an import moves whatever it pulled in out of mutation testing and coverage scoring with nothing failing, and ships test infrastructure in the production bundle — the live temptation is `Cell.tsx` importing `cellQuery.ts`'s `cellLabel()` to remove the deliberate duplicate of its own `aria-label` format, which `Cell.test.tsx` pins instead), a black-box steps file importing anything at all beyond `./acceptance-harness`, `@amiceli/vitest-cucumber` and `vitest` (`no-domain-imports-in-black-box-steps` — scoped to `features/*.steps.test.tsx`, so it deliberately does not reach `features/acceptance-harness.tsx`, which is the one module licensed to import `src/`. An **allowlist** rather than a blocklist on `src/`, and that is load-bearing: a steps file can reach the app without naming `src/` once, by importing `@testing-library/react` and querying the DOM itself, which a blocklist would pass. Rust regex has no lookarounds, but the negation doesn't need to live in the regex — ast-grep's structural `not:` combinator supplies it around an ordinary positive one, measured against 0.45.1 on this tree), and the TSX half of the paint-class ban (`no-aliveness-by-paint-class-tsx` — `features/*.ts` cannot match a `.tsx` path, and a feature enters the black-box layer by being _renamed_ `.steps.test.ts` → `.steps.test.tsx`, so without this twin every conversion would drop out of its `-ts` twin's coverage at the moment of the rename with nothing failing). Report-only like the four advisory `scripts/` programs above (but unlike `ast-grep:rules` and `agent-doc-check`, which gate) **for findings**: every rule is `severity: warning`, so a rule matching your code does not move the exit code -- read the output rather than `$?`. Promote one to a gate by changing it to `error`. The exit code is not meaningless though, it just answers a different question: measured against ast-grep 0.45.1, **8** means a rule file failed to parse and **1** means an `error`-severity rule matched, so a nonzero exit always warrants investigation.

Note which of these fire on ordinary feature work rather than only on structural change: the two `no-manual-memo` rules are unscoped by path, and `no-logic-in-composition-root` covers exactly the kind of UI wiring a slice normally adds. That's why `coder` runs `npm run ast-grep` in its own workflow rather than waiting for `architect` — see "Structural rules (ast-grep)" in `.claude/agents/articles/engineering.md` for the shared convention on reading a report-only checker, and note that rule files themselves belong to `architect` alone.

`.gherkin-lintrc` is an eighth checker, over `features/*.feature` rather than over TypeScript, and it **gates** (`npm run gherkin-lint`, nonzero on any finding) for `product`, the only role that runs it. Twenty-one of `gherkin-lint-plus`'s registered rules are on. Four facts about it that are easy to get wrong, all measured against the installed copy:

- **The package ships a `duplicate-state` rule file that is not in its registry** (`dist/rules/registry.js`), so naming it in the config aborts the run with `Rule "duplicate-state" does not exist`. The registered set is 31 rules, not the ~35 the `dist/rules/` listing suggests.
- **`name-length`'s and `max-scenarios-per-file`'s library defaults do not fit this repo** — at defaults they report 21 findings against features nobody considers wrong. The caps here are derived from Prettier's 120-char print width (a step line is indented 4 plus its keyword, leaving ~110 for the text; a scenario line is indented 2 plus `Scenario Outline: `, leaving ~100), not fitted to the current text. `max-scenarios-per-file` runs with `countOutlineExamples: false`, because the quantity this repo actually budgets — acceptance mutants — is measured exactly by `npm run acceptance-mutation` and a blunter proxy for it would only ever be tuned.
- **`no-restricted-patterns` compiles every pattern with `new RegExp(pattern, 'i')`, unconditionally.** Case is therefore not available as a signal: a camelCase-identifier detector like `\b[a-z][a-z0-9]*[A-Z]` matches every ordinary word and reported 184 findings when trialled. The list has to be an enumerated vocabulary, not a shape.
- It reads **feature/rule/background/scenario names and descriptions and step text**, and never Examples headers or cells. That is not a hole in practice, because `no-unused-variables` forces every header to appear in some step's `<placeholder>`; the two rules together reach the whole table.

**`no-restricted-patterns`' pattern list belongs to `architect`, in the same sense `rules/*.yml` does**, even though it lives in a config file `product` otherwise owns. It mechanises the domain-altitude judgment — implementation vocabulary must not leak into the contract — and its failure mode is someone widening the list to clear a finding, which is the same move as narrowing a fast-check arbitrary or weakening an ast-grep rule. A role that hits a pattern it believes is wrong routes it back to `architect` rather than editing the list. Each entry names a field, type, or function of a `src/` module (`offsetX`/`offsetY`, `cellSize`, `ScrollbarMetrics`' `thumbRatio`/`thumbOffsetRatio`, `ScrollbarMetrics` itself, `ContentBounds`, `VisibleRange`'s `minX`/`maxX`/`minY`/`maxY`, world-space coordinates, `cellKey`, and `should return`). Verbs are deliberately **not** restricted: `computed` reads as implementation but "the next generation is computed" is a statement about the game, and restricting it would drag the one already-converted feature into every prune's scope for no altitude gain. Neither is `live cells`, which is a type name (`LiveCells`) and simultaneously Conway's own ubiquitous language — the clearest example of why this list is enumerated by hand rather than derived.

**Every rule ships with a fixture in `rule-tests/` and `npm run ast-grep:test` must pass.** This is not ceremony. A malformed ast-grep rule matches nothing and reports nothing — it looks exactly like a clean codebase — and two of these rules were silently inert when first written (metavariables don't interpolate inside string literals, so an import path needs `kind:` + `regex:`; and a `matches:` util is bound to one language, so it never applied to the `.tsx` files the rule existed to check). A rule with no failing fixture has not been shown to work. Note also that TypeScript and TSX use different parsers, which is why `no-manual-memo-ts` and `-tsx` are near-duplicates by necessity rather than by oversight.

## Idea board

`ideas/` is a two-lane kanban of slices not yet started — one Markdown file per idea, and the lane is the directory:

- **`ideas/candidates/`** — raw and unjudged, no limit. An idea lands here the moment it's worth not forgetting.
- **`ideas/todo/`** — examined, and concrete enough to hand to `product`. The orchestrating session owns this board: no role reads it, and an idea reaches `product` as prompt content rather than as a file path. Keep this to about three, matching the two-or-three concurrent-slice ceiling below; a `todo/` lane longer than the number of slices you can actually run is a candidates lane wearing a different hat.

`ideas/TEMPLATE.md` is the file shape: frontmatter (`name`, `title`, `created`) over Context / Sketch / Touches / Open questions.

**There is deliberately no `doing/` or `done/` lane.** `git worktree list` already says what is in flight and `git tag -l 'slice/*'` already lists what is finished — a lane duplicating either is a second source of truth that can disagree with the first.

**`name` is the slice's identity end to end.** It matches the file's own basename, becomes the branch in `git worktree add -b <slice>`, and becomes the `slice/<name>` tag at merge. One slug from idea to tag, so `git log` and the board agree on what a thing is called.

Two rules keep the board honest:

- **Promote with a move-only commit, then edit.** Run `git mv ideas/candidates/<name>.md ideas/todo/<name>.md` and commit _that alone_, before fleshing the file out. Git infers renames from content similarity, and a candidate being expanded into a todo is precisely the case that defeats it: measured here, a move plus a substantial rewrite in one commit is recorded as delete-plus-add rather than a rename, and `git log --follow` then loses everything before the move — even at `-M10%`. Moved by itself the same change scores `R100` and the history survives. (`--follow` is required to read across the move either way; a plain `git log -- ideas/todo/<name>.md` starts at the promotion regardless.)
- **The slice deletes its own idea file.** `git rm ideas/todo/<name>.md` as part of the slice's work, so the deletion lands on the branch alongside the change it describes and the `slice/<name>` tag in merge-protocol step 6 marks a tree that no longer carries it. The tag is the permanent record and carries its own message; a file left behind becomes a third lane nobody maintains.

The lane-as-directory choice runs against the prevailing convention — [Backlog.md](https://github.com/MrLesk/Backlog.md), [MADR](https://adr.github.io/madr/), and most git-native trackers keep a `status:` field and never move the file, because moves conflict when several people edit one board. That objection doesn't reach this repo: slices land **serially** (see the merge protocol), and the board has a single editor. Since the directory _is_ the status, **don't also put a `status:` field in the frontmatter** — one fact, one home.

Nothing enforces any of this. `ideas/` has no gate, no checker, and no test; Prettier formats the Markdown (its ignore list is exclusion-based, so a new top-level path is covered with no config edit) and that is the extent of the tooling. A board-rendering script would have to live in `scripts/`, which would subject it to CRAP ≤ 6, its own vitest suite, `dry4ts`, and mutation testing — more machinery than the board is worth. `ls ideas/todo/` is the board.

## Subagent pipeline

`.claude/agents/` defines a five-role pipeline adapted from unclebob/swarm-forge's six-pack branch, scoped to this repo's actual commands (Gherkin features, `crap4ts`, `halstead4ts`, `dry4ts`, Stryker, `acceptance-mutation`, Playwright) rather than swarm-forge's tmux/file-based-handoff orchestration. (Worktrees are used, but per _slice_ rather than per _role_ — see "Running slices concurrently" below.) Each role's full instructions and boundaries live in its own file — read the relevant one before invoking it rather than relying on this summary. Shared house rules ported from swarm-forge's `main`-branch constitution live in `.claude/agents/articles/` (`engineering.md`, `workflow.md`, `handoffs.md`) — every role reads these too.

Cycle order for a feature: **product → coder → cleaner → architect → hardener → product** — `product` opens and closes every slice, in its SPECIFY and VERIFY modes respectively.

1. `product` (**SPECIFY** mode) — drafts/revises `features/*.feature` scenarios, their executable step tests, and a plain-English end-to-end outline; runs the **acceptance spike** and `acceptance-mutation` scoped to the feature; stops for explicit user approval before handing off. Never writes `src/` or `scripts/`.
2. `coder` — implements one approved slice via TDD; never writes anything under `features/` and never runs the quality-gate tools.
3. `cleaner` — structure-preserving cleanup only (CRAP/DRY/scoped mutation scan on touched files); no new functionality. This is the four-pack's old `refactorer`, narrowed: it no longer runs a full mutation suite, only the scoped scan.
4. `architect` — **four modes: REVIEW, DESIGN, CONTRACT, ADJUDICATE.** In its normal slot it reviews module boundaries/dependency direction and property-test coverage, also reading `halstead4ts`'s Halstead report as an advisory (no-threshold) complexity signal alongside that review. Unlike the old four-pack architect, it does **not** run the full quality gate itself — that moved to `hardener`.
5. `hardener` — owns the full final verification sequence (`test:mutation` → `crap4ts` → `dry4ts`, in that order), fixing whatever each stage surfaces before moving to the next. It does **not** run `acceptance-mutation` — that belongs to `product`.
6. `product` (**VERIFY** mode) — builds and runs `features/*.e2e.spec.ts` (Playwright) from its own outline as the final independent, black-box check through the real UI, runs the full `acceptance-mutation`, and re-confirms `crap4ts`/`dry4ts` clean before declaring the feature done. It **reports** `src/` defects to `architect` rather than fixing them; `architect` rules on whether the code or the contract is wrong (its ADJUDICATE mode). See `.claude/agents/articles/handoffs.md`'s "Defect adjudication".

There's no daemon or persistent process wiring these together — the orchestrating session invokes each role in turn via the `Agent` tool and sequences the handoffs itself.

### The optional architect design pass

> `architect` has four modes. **DESIGN** ratifies an _implementation_ — a file set, interfaces, an ordering — and is what this section is about. **CONTRACT** ratifies a _specification_ during `product`'s acceptance spike: is the drafted contract observable through the UI at all, what accessible affordance does it need that doesn't exist, and is it at the right altitude for Gherkin. **ADJUDICATE** rules on a defect `product` reports at the end of the cycle. A slice may use several; contract review comes first, since there is no point planning an implementation for a contract that can't be verified.

`architect` may be invoked a **second time, before `coder`**, as a design pass that ratifies a file set and interface rather than reviewing landed code. It still runs in its normal post-`cleaner` slot afterward, so the slice gets both a design and a review — the two jobs compete for one pass otherwise, which is the same reasoning that split `hardener` out of the four-pack architect.

**The orchestrating session decides this, not `product`.** Every trigger below is a fact about the current shape of `src/`, and `product` is deliberately blind to it — it reads `src/` but never writes it, precisely so its reach stays honest. `product` may _flag_ that a slice smells structurally large; it doesn't make the call.

Reach for a design pass when:

- The slice is a refactor or restructure with no behavior change — then the design **is** the deliverable, and there's nothing for `coder` to TDD against without one.
- It will create new modules, or move/split existing ones.
- It crosses the framework-free module → hook → component layering.
- A target file is already flagged as oversized — `cleaner`'s 100+ mutant heuristic, or `coder`'s ~1s per-file test-duration budget.
- The change spans three or more existing modules.

A design pass writes **no product code**. Its output is a ratified file set, the interfaces between the new pieces, and an ordering of behavior-preserving steps each of which leaves the suite green — plus, where useful, a mechanical guard (an `ast-grep` rule and fixture) for an invariant the design depends on. `coder` then executes that ordering, usually in more than one invocation, with the existing test suite as the regression net at each step.

The `split-grid-render-props` slice is the worked example: the design pass corrected the prop shape before any code existed, split the riskiest step in two so the pre-existing tests could verify it, and authored `rules/no-logic-in-composition-root.yml` to keep the new composition root wiring-only.

**All five roles carry the `LSP` tool** in their frontmatter allowlist, giving them go-to-definition, find-references, and type errors reported in-turn rather than at the next `npm run build`. Every role writes TypeScript: the four implementing roles write `src/`/`scripts/`, and `product` writes step tests, the acceptance harness, and Playwright specs. What separates them is no longer the tool allowlist — it's the **write boundary**, stated in prose: `product` reads `src/` freely and writes nothing there or in `scripts/`, in either mode. That boundary used to be expressed by withholding `LSP` from `specifier`, which touched no TypeScript at all; after the merge that framing would be dishonest in both directions, since `product` writes real TypeScript and withholding a reading tool would only make its tests worse without narrowing its reach. This needs the `typescript-lsp` plugin installed (`/plugin`) plus a **global** `npm install -g typescript-language-server typescript`; the binary is not a project dependency, so `npm ci` alone does not reproduce it on a new machine. If the server is missing the roles silently fall back to `Grep`/`Read`, so a clean `npm test` is not evidence it's working — check `claude --debug`, which names any LSP server it skipped and why.

The file names in the Architecture section above are a current snapshot, not a frozen contract: `cleaner` and `architect` are expected to update that section (and fix any file-list mention elsewhere in these docs that a split makes stale) as part of performing a behavior-preserving split — see "Where guidance and file names live" in `.claude/agents/articles/engineering.md`.

## Running slices concurrently

Two or three slices can be worked at once: **one slice = one git worktree = one branch = one Claude Code session.** Every role in a cycle runs inside that slice's worktree and commits to that slice's branch; `main` is written to only by the merge protocol below, which the orchestrating session drives. The role-facing half of this lives in `.claude/agents/articles/workflow.md` ("Worktrees and branches") and `handoffs.md` ("Concurrent slices").

Isolation is what makes it safe. Each worktree gets its own `node_modules`, `coverage/`, `reports/` (including the Stryker incremental caches and `reports/perf/`), `test-results/`, `.stryker-tmp*`, `dist/`, and `dist-perf/` — all of which are fixed relative paths, so separate checkouts separate them for free. The one thing a worktree does **not** separate on its own is a TCP port, which is why `dev-port.ts` derives per-checkout ports — a dev-server port (5173+), a Vitest browser-API port (21000+), and a `vite preview` port (41000+, used by `playwright.perf.config.ts`), three disjoint ranges: the primary checkout keeps 5173, each linked worktree hashes its own directory to its own slot, and `vite.config.ts` sets `strictPort` on both the dev server and the preview server. Without that, `playwright.config.ts`'s `reuseExistingServer` finds another worktree's server answering on 5173, attaches, and reports a green e2e suite against the wrong build.

### Setting up a slice

```bash
git worktree add ../gol-claude-worktrees/<slice> -b <slice> main    # or .claude/worktrees/<slice>
cd ../gol-claude-worktrees/<slice> && npm ci
```

Then start a session there, or `EnterWorktree({ path: '../gol-claude-worktrees/<slice>' })`. Both locations work and both are ignored by git, Prettier, oxlint, and vitest. `npx playwright install chromium` is **not** needed — that binary lives in a machine-global cache.

If you use the native `EnterWorktree({ name })` or `Agent({ isolation: 'worktree' })` path, set `"worktree": { "baseRef": "head" }` in `.claude/settings.json`: the default `fresh` branches from `origin/<default-branch>`, which is stale unless `main` is pushed after every merge.

### Merge protocol

**Slices land one at a time, serially.** Parallelism buys concurrent _authoring_, not concurrent _landing_ — the second slice to land pays a full re-verification. That cost is why two or three is the sensible ceiling.

1. **Rebase, don't merge.** In the slice's worktree: `git fetch && git rebase main`. This keeps `main` linear, which is what `workflow.md`'s "a prior role's commit" ordinal reasoning assumes, and keeps each slice's `By <role>.` chain readable in order.
2. **The slice's own session resolves its own conflicts**, in its own worktree — it has the context the orchestrator doesn't. `main` never enters a conflicted state.
3. **Re-run the gate on the rebased branch, still in the worktree.** Invoke `hardener` again. It must use `npm run test:mutation:full`, because the rebase brought in another slice's moved and renamed files — exactly the file-level assumption the incremental cache can't survive — **unless the merge is mutation-invariant, in which case stage 4 does not run at all; see the clause under step 5, and evaluate its predicate here, at this step.** Pay attention to `npm run ast-grep:rules` here specifically: it's the gate most likely to have been broken by the _other_ slice's renames invalidating a `files:` glob, and post-rebase that breakage is legitimately yours.
4. **Fast-forward `main`:** `git checkout main && git merge --ff-only <slice>` from the primary checkout. `--ff-only` is the assertion that step 1 actually happened.
5. **Run the full gate on `main`.** Mandatory, even though step 3 just passed on an identical tree — step 3 ran against a different Stryker cache and a different `coverage/`. This run is what rebuilds `main`'s own caches into a state the next merge can trust:

   ```bash
   rm -f reports/stryker-incremental.json reports/stryker-incremental-scripts.json
   ```

   then invoke `hardener` on `main` with the whole tree as its scope. Deleting the caches is the honest expression of intent: they aren't stale, they're describing a tree that no longer exists — the situation the mutation-testing note in Commands already names.

   **Mutation-invariant merges — the one exemption, and it is stage 4 only.** Steps 3 and 5 both mandate `npm run test:mutation:full`, and for some diffs that is two full runs measuring a quantity that provably did not move. `stryker.config.json`'s `mutate` list covers only `src/**`, and its `ignorePatterns` keeps `features/` out of the sandbox entirely, so for a diff confined to the paths below neither a mutant nor a test that could kill one is reachable. Left unaddressed this is not merely a cost — it is a standing incentive to bundle unrelated features into one slice to pay the bill once, which is the opposite of what the serial-landing rule is for.

   **The predicate is an allowlist of paths that cannot move the score, not a list of the paths that can.** That direction is the whole design: a blocklist fails **open** — a path nobody thought to list silently skips the mutation gate, and a skipped run reads exactly like a passing one — which is the same dangerous direction as the `ignorePatterns` glob that matches nothing, already described in the Commands section. An allowlist fails safe: an unanticipated path simply runs the gate. Stage 4 may be skipped when **every** path in

   ```bash
   git diff --name-only main...HEAD    # in the slice's worktree, after step 1's rebase
   ```

   matches one of `features/**`, `ideas/**`, `.claude/**`, `CLAUDE.md`, `README.md`. **Do not extend that set without measuring the addition**, and the measurement is one command: `npx vitest list` collects test files from `src/` and from `features/` and from nowhere else, so no other listed path can contribute a test to the run, and `features/`'s own tests are excluded from the sandbox on top of that. `stryker.config.json` is deliberately **absent** from the allowlist, as are `vite.config.ts`, `vitest.*.config.ts`, `package.json`/`package-lock.json`, `tsconfig*.json` and `patches/**` — touching any of them re-arms the full run, which is the point of leaving them out rather than an oversight.

   **Every other stage still runs, and `crap4ts` in particular genuinely moves on a `features/`-only diff**: `npm run test:coverage` runs all four vitest projects, the `acceptance` project mounts `<App />`, and its coverage lands on `src/` like any other project's. So this exempts one stage from one run; it is not a fast path through the gate.

   **Compute the predicate once, in step 3's worktree after the rebase, and carry the answer to step 5.** Step 4 is a fast-forward, so the tree step 5 gates is byte-identical to the one step 3 gated — there is no second diff worth taking, and reconstructing one from `main`'s reflog is a worse way to ask the same question.

   **When stage 4 is skipped, step 5 does not delete the incremental caches.** The `rm -f` above exists because the caches describe a tree that no longer exists; under this predicate the tree _Stryker sees_ is byte-identical to the one they were built from. Deleting them would tax the next merge with a full cold run in exchange for nothing. That answers step 5's own "different cache" justification on its own terms rather than waiving it.

   **`hardener` never applies this to itself.** The predicate is evaluated by the orchestrating session and handed to `hardener` in the invoking prompt, naming the diff it was computed over; absent that instruction `hardener` runs stage 4. A role that can excuse itself from its own gate is not a gate. See `.claude/agents/hardener.md`'s stage 4.

6. **Tag the slice's final commit**, annotated, as `slice/<slice-name>`:

   ```bash
   git tag -a slice/<slice> -m "<slice>: <one line on what the slice delivered>"
   ```

   After the fast-forward in step 4 the slice's tip _is_ `main`'s tip, so this marks both. Tag after step 5 rather than before it: the tag says the slice is done, and it isn't done until the gate on `main` passes. The `slice/` prefix is load-bearing — a bare tag sharing the slice branch's name makes every `git log <name>` ambiguous until the branch is deleted in step 9 — and it makes `git tag -l 'slice/*'` a list of every completed slice. Annotated rather than lightweight, so the tag carries its own date and message. If the slice began as an entry on the idea board, its `ideas/todo/<slice>.md` is already gone by now — the slice deletes its own idea file as part of its work (see "Idea board" above), and this tag is what carries the record forward in its place.

7. **Push `main` and the tag:** `git push --follow-tags` (plain `git push` leaves the tag behind).

   This repo sets `push.followTags = true` locally, so a plain `git push` already carries the tag — but the flag stays written out here because `.git/config` isn't tracked, so a fresh clone or a CI checkout won't have the setting. Note the setting only follows **annotated** tags reachable from what you're pushing; a lightweight tag is silently left behind, which is one more reason step 6 specifies `git tag -a`.

8. **Carry the acceptance-mutation figure forward** from `product`'s VERIFY handoff — it comes from there now rather than from `hardener`'s. This is a read, not an edit: `engineering.md` deliberately records **no literal**, and says why in the same breath ("a literal in this file is wrong the moment the second one lands"), so there is nothing in that file to re-record. What the step is actually for is noticing when the figure moved and whether the slice explains it — a slice that touched no `.feature` and no `*.steps.test.*` leaves the Examples-table mutant surface byte-identical, so a moved figure wants an explanation before it is accepted. Note the surface being identical does not by itself guarantee identical kill outcomes — a `src/` change to a module the steps exercise can flip a mutant's fate while the unmutated baseline stays green — which is exactly why a move is a finding to understand rather than a new baseline to record.
9. **Retire the worktree:**

   ```bash
   git worktree remove <path>
   git merge-base --is-ancestor <slice> main && git branch -D <slice>
   git worktree prune
   ```

   Assert the ancestry yourself rather than leaning on `git branch -d`. `-d`'s built-in "fully merged" test measures against whatever branch is currently checked out — and under concurrency the primary checkout is normally sitting on some _other_ slice's branch, so `-d` refuses a slice that is in fact already `main`. (Safe, but it stops you every time.) The check above asserts the condition you actually care about, and `-D` can't do damage because it only runs once that assertion has passed. The tag is what preserves the slice's identity once the branch is gone.

The next slice repeats from step 1 against the new `main`.

**`npm run test:perf` is owned by the orchestrating session, not by any role.** It appears in no role's checklist deliberately: render performance is meant to be held by the architecture — the world-anchored tile keys, the eviction hysteresis — rather than re-measured on every slice, and a per-slice harness stage would quietly recast an architectural guarantee as a test result. So the orchestrator decides when a slice is perf-relevant, runs `npm run test:perf` **followed by** `npm run perf-report` (skipping the second leaves the previous run's `reports/perf/latest.md` in place, reading as a successful run of the current tree), and regenerates the `main` baseline first whenever `src/` or `perf/` has moved since that report's own commit — check it, the report names the commit it was generated from. A role may _recommend_ a run in its handoff, which is a useful signal; no role runs it.

There is deliberately no seventh role for this. The post-merge gate is `hardener`, invoked on `main` and told that it is verifying an integration rather than a slice, so the whole tree is in scope — it already owns exactly that sequence and already knows when to reach for `test:mutation:full`.

## Conventions

- No semicolons, single quotes, 120-char print width (Prettier; `prettier-plugin-tailwindcss` sorts class strings — don't hand-order Tailwind classes).
- Comments are reserved for non-obvious _why_ (subtle invariants, browser quirks, sign-convention mismatches between related functions). This codebase leans heavily on that style in `camera.ts`/`scrollbars.ts` and `Grid.tsx` — read existing comments fully before touching the code they explain, since the reasoning (e.g. pointer-capture propagation, scroll-direction sign conventions, shift+wheel axis workarounds) is often not re-derivable from the code alone.
- React Compiler is enabled (`babel-plugin-react-compiler` in `vite.config.ts`, `react/react-compiler` oxlint rule set to `error`) — avoid manual `useMemo`/`useCallback` unless the compiler can't handle the case.
