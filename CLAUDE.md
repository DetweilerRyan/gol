# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Conway's Game of Life, built as an infinite, pannable/zoomable grid (React 19 + TypeScript + Vite + Tailwind v4). Cells are toggled by click; generations advance manually via the Next Generation button.

There is no separate typecheck script — `npm run build` runs `tsc -b` as its first step. Lint (oxlint) has type-aware rules disabled by default; see README.md if enabling `oxlint-tsgolint`.

**Mutation testing runs incrementally.** `npm run test:mutation` still covers the whole `mutate` list, but Stryker caches results and re-tests only the mutants whose source _or covering tests_ changed — a full run over `src/` took ~10 minutes when that was measured — with `features/` still in the sandbox, which it no longer is (see the sandbox paragraph below); no replacement figure is recorded here, since `hardener`'s next `npm run test:mutation:full` is the thing that produces a current one. An incremental run tracks the size of the diff **above a floor described in the next paragraph**. This matters because Stryker kills a mutant when _any_ test fails, so a mutant in one module is often killed by a test in another; scoping a run to changed source files alone would be blind to "a test moved, and now a mutant in an untouched file survives," whereas incremental mode accounts for it. Reach for `npm run test:mutation:full` whenever the cache's file-level assumptions break — `stryker.config.json` changed in either of the two keys that decide what the run sees (`mutate`, which picks the files to mutate, **or `ignorePatterns`, which picks the files that reach the sandbox at all** and therefore which tests exist to kill anything), a module was split or renamed, or test files were moved/deleted rather than edited in place — and prefer it when genuinely unsure, since a false-clean score is worse than a slow one.

**That floor is `@fast-check/vitest`, and it is structural: ~10% of the mutants and ~3m45s of wall clock get re-tested even when nothing changed at all.** The plugin interpolates the run's seed into the test _title_ (`… (with seed=2041793899)`), unconditionally and with no option to suppress it (measured in `node_modules/@fast-check/vitest/lib/vitest-fast-check.js` — the only way to stabilize the title is to pin the seed), while Stryker's `IncrementalDiffer` matches cached results _by test name_. So every property test looks brand-new on every run and invalidates the ~135 mutants they cover regardless of the diff: measured, 310 of 383 invalidated cached tests carried a `with seed=` marker, and the run reported `1171 of 1306 mutant result(s) are reused`. **Those three test-side figures were measured with `features/` still in the sandbox and have not been remeasured since it was excluded** — the mutant totals are unaffected (`mutate` never covered `features/`, and 1,306 is still the count on the current tree), but the run's test population dropped by the 151 tests in 7 files that Stryker collected from `features/` (its scope, not vitest's — see the sandbox paragraph), so the 310/383 denominators are pre-exclusion and are left as-is rather than quietly adjusted to a number nobody ran. The mechanism the paragraph describes is unchanged either way: property tests live in `src/`, so nothing about the seed-in-the-title problem moved. It fails **safe** — it re-tests more than needed and never falsely reuses a stale result, and three runs on an identical tree gave byte-identical totals — so this is a cost, not a correctness problem, and no reported score has ever been wrong because of it. Don't buy the floor back by pinning the seed globally: the exploration is the whole point of that layer, and this repo separately requires repeated property runs when a slice edits a property file. Pinning a seed only under Stryker, leaving `npm run test:property` exploratory, is the one variant that isn't self-defeating — and it is a slice of its own, since it changes what the mutation gate measures.

**`features/` is not in Stryker's sandbox — and as of `delete-step-test-layer` that entry is belt-and-braces rather than load-bearing.** `stryker.config.json` carries `"ignorePatterns": ["/features"]`, so the whole directory is never copied into `.stryker-tmp/` and nothing in it can run, kill, or be attributed a kill. What it excluded when it landed was a real vitest layer, the seven `*.steps.test.*` files; those are gone, and **`features/` now contributes zero tests to `npm test`**. So the entry subtracts nothing from the run today. Keep it anyway: its remaining job is to stop a _future_ test file placed under `features/` from silently entering the mutation run, and in that role it fails **safe** — such a file would stay out, so the score would drop and `hardener` would investigate, never rise. The measurement below is kept as history, because it is the argument for the entry and the only written account of why a `killedBy` naming a step test never meant what it looked like. On the tree it was taken from, the two scopes genuinely differed: `npx vitest run features/` collected **180** tests from those 7 files (of 837 across 61 files on `ebba2f5`), while the `bd7c388` baseline showed Stryker itself collecting only **151** from the same 7 (of 805 across the same 61 files) — same tree, same files, 32 fewer tests seen by Stryker, because its runner drops any test that finishes without a result (`vitest-test-runner.js` filters on exactly that, with `bail: 1` set). Neither figure describes any tree that exists now; don't quote them forward. What the `stryker-excludes-gherkin` slice removed was a duplicate measurement that was also wrong, not a gate. **Excluded from Stryker is still not unmutated** — `features/` keeps its own mutation signal in `npm run acceptance-mutation`, which mutates the Examples tables and asks whether the steps notice. That runner never touches any of this machinery: it spawns `bddgen` and `playwright test` against a dedicated config (`playwright.acceptance-mutation.config.ts`, via `scripts/acceptance-mutation/playwright-runner.ts`), against the real tree, so Stryker's sandbox and its `ignorePatterns` are not in the picture at all. Three things about the entry are still easy to trip over. **The leading `/` is load-bearing** — it anchors the pattern to the project root (gitignore semantics, per the option's own schema description), so it matches `features/` and not some nested `src/features/`. **`ignorePatterns` has no effect whatsoever under `--inPlace`**, which the schema states outright ("with `true` the `ignorePatterns` has no effect any more") because in-place mode mutates the real tree instead of a sandbox copy; no npm script passes that flag today. **A rename of `features/` breaks this entry silently** — an `ignorePatterns` glob that matches nothing is not an error. That silence is measured, not assumed: a probe config carrying `ignorePatterns: ["/no-such-dir-xyz"]` emits no warning of any kind and collects the identical test count as `ignorePatterns: []` (267, scoped to `is-strict-equal.ts`). Today a silent break here would readmit no test at all, which is why the entry has dropped to belt-and-braces; the consequence was severe only while the layer existed. `npm run gherkin-lint` and `playwright.config.ts`'s `testDir` also hardcode that directory name — `vite.config.ts` no longer does, the `acceptanceTests` glob having gone with the layer.

**The repo's first split between what `crap4ts` sees and what Stryker sees has now closed, and the closing was measured.** While the step layer existed, `npm run test:coverage` ran it through `vite.config.ts` — both step-file forms included — so a line reachable _only_ from a step test read as covered in `npm run crap4ts` while its mutants were killable only by a non-`features/` test, and the two tools could legitimately disagree about the same line. `delete-step-test-layer` removed the layer, so `features/` contributes to neither tool and both again score the same test set. Measured on that slice's probe tree: `npm run crap4ts`'s per-function table is **byte-identical** before and after the deletion — 111 functions, 0 above threshold, worst 6.0 — so the layer was contributing no gated coverage at all. Exactly two `src/` files moved, and **both sit outside `crap4ts.config.ts` and `stryker.config.json` already**: `src/App.tsx` drops out of `coverage/coverage-final.json` entirely (the `acceptance` project was the only vitest project that mounted `<App />`, so its coverage is now Playwright-only — which is what this file already said it was), and `src/test-support/cellQuery.ts` goes 8/8 → 7/8 as `cellSelector` loses its only _instrumented_ caller, its live one being `features/screenplay/elements.ts` on the Playwright side. Neither is a gap to chase. The remedy if the two tools ever disagree again is unchanged and is the same as for the browser-required layer: close it with a jsdom or unit test under `src/`, never by reaching back into `features/`.

The two Stryker configs keep **separate** caches (`incrementalFile`: `reports/stryker-incremental.json` for `src/`, `reports/stryker-incremental-scripts.json` for `scripts/`), the same way they already separate `tempDirName` and their HTML reports — one shared cache across two different `mutate` lists would corrupt both. For the same reason, a `--mutate`-scoped run (as in `cleaner`'s workflow step 3) must never pass `--incremental`: it would record that subset as if it were the whole project and make the next full-scope run report a false-clean score. Both cache paths are gitignored, so a fresh clone or CI pays full cost on the first run — that's the safe default, not a misconfiguration. Note the `scripts/` cache is currently declared rather than used: `npm run test:mutation:scripts` runs `stryker run stryker.scripts.config.json` with **no** `--incremental` flag, so that side always pays full cost and never writes `reports/stryker-incremental-scripts.json` at all. The separate path still earns its line in the config — it is what makes adding the flag safe — but don't read the merge protocol's `rm -f` of both files as evidence the second one exists.

**crap4ts is patched locally (`patches/crap4ts+1.0.1.patch`) and `crap4ts` is pinned to an exact version because of it.** Upstream, crap4ts pairs an AST function span to an Istanbul coverage span only when they overlap by ≥80% of the AST span's lines (`OVERLAP_THRESHOLD = 0.8`), and Istanbul records `fnMap[k].loc` as the function _body_ — starting at the opening brace, never consulting `fnMap[k].decl`. A signature Prettier had to break across lines therefore pushes the two spans apart far enough that no candidate matches, and the function is reported at 0% coverage with an inflated CRAP score even though it is fully exercised. The patch mirrors upstream PR [breezy-bays-labs/crap4ts#37](https://github.com/breezy-bays-labs/crap4ts/pull/37) (open and unmerged since 2026-04-07; `crap4ts@1.x` is in maintenance mode pending a Rust-backed v2 rebuild, so it may never land): `findCandidates` now also accepts a candidate when either span fully contains the other, bypassing the ratio gate in that case. Ranking (`contains` → `ratio` → `nameMatch`) is unchanged.

Three consequences follow. First, the patch targets a **content-hashed tsup chunk** (`dist/chunk-W6RIPRFD.js` plus its CJS twin `dist/chunk-OHOZMDXW.cjs`), so any crap4ts release renames the file and the patch stops applying — which is why `package.json` pins `"crap4ts": "1.0.1"` with no caret, and why **upgrading crap4ts means regenerating the patch by hand**, not just bumping the range. Second, `patch-package` runs from `postinstall`, so the patch is only in effect after a normal `npm install`/`npm ci`. Third, `src/patternLibrary.ts`'s `patternCellPositions` keeps its four-line signature deliberately: it is the live regression fixture for this patch. If the patch ever stops applying, that row drops back to 0.0% in `npm run crap4ts` — don't "tidy" the signature onto one line, and don't chase the 0% as a coverage gap if it reappears. `npm run crap4ts -- --verbose` distinguishes the two cases: an `[unmatched-no-coverage]` warning naming the function means the matcher missed it (patch not applied), whereas a genuine gap shows as a matched row with a low percentage. There is a third cause of the identical `[unmatched-no-coverage]` warning, unrelated to the patch, and it is the one that has actually bitten repeatedly: **`crap4ts` reads `coverage/coverage-final.json` off disk and never regenerates it**, so any source edit since the last `npm run test:coverage` is scored against stale line spans. This is broader than a missing entry for a newly-landed file — _any_ line-shifting edit, including a pure comment change, moves a function's AST span away from the recorded coverage span, and the two failure modes look nothing alike: some functions orphan at 0.0% (indistinguishable from the patch-not-applied case above), while others match an old, shifted entry and read a spurious 100%. The remedy is the same either way, and it is a precondition rather than a fix: **run `npm run test:coverage` (or `npm run test:coverage:scripts` before `npm run crap4ts:scripts`) whenever source has changed since the last coverage run** — which, in a role's pass, is essentially always. (The many `[unmatched-no-ast]` warnings under `--verbose` are unrelated and expected — they are coverage entries in files outside crap4ts's `include` list, plus nested functions crap4ts does not score.)

## Architecture

### Core logic: sixteen framework-free modules, ten hooks, twelve unit-tested components

Sixteen framework-free modules — twelve at `src/` root (`gameOfLife.ts`, `patternLibrary.ts`, `camera.ts`, `gridGeometry.ts`, `cellTiles.ts`, `cellAnchor.ts`, `dragGesture.ts`, `scrollbars.ts`, `patternPlacement.ts`, `liveCellStore.ts`, `liveCellSeed.ts`, and `cache.ts`) and four in `src/equality/` (`container-equality.ts`, `is-shallow-equal.ts`, `is-deep-equal.ts`, `is-strict-equal.ts`) — hold every non-UI rule in the repo, and together with ten hooks in `src/hooks/` (`useCamera.ts`, `useElementSize.ts`, `usePatternPlacement.ts`, `useWheelInput.ts`, `useGridPointerGestures.ts`, `useInitialCentering.ts`, `useLiveCell.ts`, `useContentBounds.ts`, `useCellTiles.ts`, `useRafCoalescedPan.ts`) and twelve components in `src/components/` (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `CellTile.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`) are the modules covered by unit tests and mutation testing (see `stryker.config.json` / `crap4ts.config.ts` — both scope by glob-minus-exclusions rather than by an enumerated list, and `scripts/halstead4ts/run.ts` resolves `crap4ts.config.ts`'s globs rather than restating them, so a new module at `src/` root, `src/hooks/`, or `src/components/` is covered the day it lands with no config edit). Every framework-free module is additionally covered by property tests (the `property` vitest project's `include` is `**/*.property.test.ts`, so a new file with that suffix is picked up automatically) with two deliberate exceptions in `src/equality/`: `is-strict-equal.ts` is a three-line `Object.is` wrapper with no invariant to quantify over, and `container-equality.ts` has no contract of its own to state — it is the shared walker both comparators inject into, so their property tests (reflexivity, symmetry, clone round-trip, Set-member order-independence) are what cover it, from both sides. `src/App.tsx`, `src/main.tsx`, and `src/components/LifeBoard.tsx` remain excluded — still composition-root/bootstrap code exercised by browser testing rather than unit tests, specifically `features/hud-layout-and-shortcuts.e2e.spec.ts`, which drives the HUD and App's own state wiring (including that a stamped pattern really does come to life) through the real app — as does `src/test-support/`, which is shared test infrastructure (jsdom stubs for `ResizeObserver`, `getBoundingClientRect`, and pointer capture in `domStubs.ts`, the fast-check arbitraries the camera-side property tests share in `arbitraries.ts`, the brute-force Life oracle `gameOfLife`'s and `liveCellStore`'s property tests both check against in `lifeReference.ts`, the `#grid-content` DOM query both `Grid.test.tsx` and `LifeBoard.test.tsx` need in `gridDom.ts`, the single encoding of how a cell's aliveness is expressed in the DOM (the `aria-pressed` attribute/value constants and the `Cell x, y` label format, shared by `src/components/*.test.tsx`, `features/*.e2e.spec.ts`, `features/screenplay/`, and `perf/`) in `cellQuery.ts`, and its sibling `rulerQuery.ts` — the single encoding of how the ruler's two axis groups are named (`rulerGroupLabel`, shared by `src/components/GridRuler.test.tsx` and `features/screenplay/elements.ts`); a sibling rather than an addition to `cellQuery.ts`, whose header scopes it to cell aliveness, and deliberately a name function with no CSS-selector twin, since an accessible name is computed rather than stored and only the role engine queries it faithfully, and their sibling `scrollbarQuery.ts` — the single encoding of how a scrollbar words the proportion of the grid currently in view, added by `scrollbar-visible-proportion-affordance` and the **first module here to export a parser alongside its builder** (`visibleProportionText` for `src/components/Scrollbar.test.tsx`, `parseVisibleProportionText` for `features/screenplay/questions.ts`), which makes it the first whose two encodings could drift apart rather than being one shared constant; its header carries both decisions that are invisible from the call sites — why `percent` is spelled out rather than `%`, and what actually catches that drift, measured: breaking the parser's literal alone fails **7 of the 105 tests** in `npm run test:e2e`, the whole `grid-scrollbars` bdd feature, each reporting the function's own named throw) rather than product code. Nothing in `src/` outside a test file may import from `src/test-support/` — the directory sits outside every gate, so such an import silently moves what it pulled in out of mutation testing and coverage scoring; `rules/no-test-support-in-product-ts.yml` and `rules/no-test-support-in-product-tsx.yml` check that mechanically. Keep new domain logic in a framework-free module rather than in a component whenever it can be expressed as pure logic, so it stays covered by property tests and mutation testing, not just unit tests.

- **`src/gameOfLife.ts`** — the actual Game of Life model. Live cells are stored as a sparse `Set<CellKey>` (`CellKey` = `"x,y"` string), not a bounded 2D array — the grid is conceptually infinite. Core functions: `toggleCell` (mutates an Immer draft), `advanceGeneration` (one generation **plus** the exact set of cells whose aliveness flipped, computed in the same pass that decides survival — the delta is never recovered afterwards by diffing two finished sets, and `countNeighbors` seeds each live cell at zero precisely so the isolated cell that dies of underpopulation is a candidate that single pass can see), `getNextGeneration` (a projection of `advanceGeneration` for callers with no use for the delta — the Gherkin step definitions; deliberately not a second implementation of the rules), `computeContentBounds` (bounding box of live cells, used to size scrollbars). Neighbor counting is done only around currently-live cells, never by scanning a bounded region.
- **`src/patternLibrary.ts`** — the catalog of the 8 known Life patterns and the queries over it (`getPatternByName`, `patternsByCategory`), plus the anchor convention shared by `patternCellPositions` and `placePattern`: a `Pattern`'s cells are stored relative to its own bounding-box top-left corner, so stamping and previewing can't drift apart. Split out of `gameOfLife.ts` so the Life rules aren't fused with a data table; the dependency runs catalog → model, never the reverse. Distinct from `patternPlacement.ts` below, which owns the _interaction_, not the data.
- **`src/camera.ts`** — the camera and every transform that produces a new one, independent of both the game rules and what's on screen. `Camera` = `{ offsetX, offsetY, cellSize }` in world-space coordinates. Key conversions: `worldToScreen` / `screenToWorld`, with `rectRelativePixels` as the single translation point from a DOM event's client coordinates into the viewport-relative pixel space every pixel-taking function here (and in `scrollbars.ts`) expects. Handles pan, zoom-at-point (keeps the world point under the cursor fixed), and wheel input (shift+wheel = zoom, plain wheel = pan, with a Firefox/Windows axis-swap workaround — see comment in `applyWheelInput`). Note the deliberate sign asymmetry: wheel-pan and scrollbar-drag follow the "document scroll" convention, drag-to-pan doesn't.
- **`src/gridGeometry.ts`** — which part of the infinite grid is on screen and which coordinates are reference lines: `computeVisibleRange` (viewport plus a small buffer) and major-gridline computation every 10 cells. Takes a `Camera` but never returns one.
- **`src/cellTiles.ts`** — the tile-virtualized mounting policy: which world tiles are mounted, and when that set changes, replacing `cellLattice.ts`'s coverage half. Tiles are fixed `TILE_SPAN_CELLS` (4) cells square, world-anchored rather than viewport-relative, so a retained tile's own cells never change coordinates while it stays mounted — a pan re-renders only the entering/exiting strip of tiles at a boundary, not the whole mounted set. `coveringTileRange` computes the exact minimal `TileRange` a camera/viewport needs; `tileRangeHolds`/`nextTileRange` are eviction hysteresis (`EVICT_LAG_TILES` = 1): keep the previous range while it still contains the required one and exceeds it by at most one tile per side, and otherwise rebuild onto the **eviction-lag-clamped union of the previous range and the required one** — not onto the required range exactly, which is what the `fix-tile-hysteresis` slice changed and what makes a sub-cell wobble at a tile boundary cost one rebuild instead of one per pointermove. That retention is deliberately not admission overscan, and the distinction is the whole design: per axis the clamp can only ever keep a bound the previous range already held, so it defers an eviction rather than admitting a tile (see the module header, which also records the two costs it does add — a monotone pan can rebuild twice per tile span instead of once, eviction-only, and a zoom-**in** rebuild retains a four-sided ring where a zoom-out one does not). `nextTileRange` returns its input **by reference** when it holds and is idempotent on its own result, the same no-infinite-loop guarantee `cellLattice.ts`'s `nextLattice` used to carry alone. Stores no `cellSize` — zoom needs no special case, since zooming out fails containment and zooming in fails the lag test, both already covered by the hold/rebuild rule.
- **`src/cellAnchor.ts`** — precision bounding, and nothing else: keeps `(worldCoordinate − anchor) × cellSize` small enough that the compositor's float32 transform matrix stays exact, which is the only half of `cellLattice.ts`'s old origin this module inherits (coverage moved to `cellTiles.ts`, and the two are independent — `cellAnchor.ts` takes `spanCells` as a parameter rather than importing `cellTiles.ts`). `ANCHOR_DRIFT_CELLS` (4096) is how far the camera's offset may drift from the anchor before `nextAnchor` re-quantises, chosen against the float32 integer-exactness cliff at 2²⁴ px. `anchorOffsetPx` is `cellLattice.ts`'s old `latticeOffsetPx`, deliberately just `worldToScreen`: `screenToWorld` resolves taps and hover, and the two must stay exact inverses or a click lands on a different cell than the one under the cursor — `cellAnchor.property.test.ts` pins that identity. `nextAnchor` carries the same by-reference/idempotent contract as `cellTiles.ts`'s `nextTileRange`, applied independently. Because coverage no longer forces a re-anchor, this re-quantises roughly once per 4,096 cells of camera travel instead of on nearly every rebase — rare enough that the cost of that full re-render (~180–200 ms) is an accepted trade rather than a per-pan concern.
- **`src/dragGesture.ts`** — the pointer-drag gesture: `beginDrag`/`advanceDrag` decide when a drag has crossed `DRAG_THRESHOLD_PX` and become a pan rather than a click (the flag latches, so a drag returning near its origin doesn't fall back to a click), and report the incremental pan delta. Deals only in client pixels — it references no `Camera` at all, which is why it stands alone.
- **`src/scrollbars.ts`** — scrollbar thumb sizing, positioning, and drag math. The one camera-side module that knows about the game model (`ContentBounds`), which is exactly why it's separate from `camera.ts`. Scrollbars represent the union of content bounds and current viewport, not content bounds alone (see comment on `computeAxisScrollbarMetrics`) — this keeps the thumb ratio/offset valid even when panned away from all live cells. **`computeThumbGeometry`'s `trackLengthPx` is the TRACK, never the viewport**, and the `scrollbar-thumb-overflows-its-track` slice is why that is written in capitals: `Scrollbar.tsx` passed the viewport length for it while its own Tailwind `right-2.5`/`bottom-2.5` inset each track by the perpendicular bar's 10px thickness, so every thumb was sized and positioned against a box 10px longer than the one it was drawn in (measured at rest, no content and no gesture: a 1280px horizontal thumb in a 1270px track, 900 in 890). The prop is now `viewportLengthPx` and `Scrollbar.tsx` does the subtraction itself, against its own `SCROLLBAR_THICKNESS_PX` — the CSS knowledge stays in the component and this module stays framework-free.

  **The lesson generalizes past scrollbars, and it is the one worth carrying: a property over a module cannot reach an argument's provenance.** `scrollbars.property.test.ts` already asserted "the thumb never extends past the track, in either length or offset" — and it was green, and correct, throughout the entire life of the defect, because it quantifies over the `trackLengthPx` it is _handed_. The bug lived in the gap between that parameter's name and the value one call site passed for it. No property, and no amount of mutation score, over `scrollbars.ts` can see that gap; the guards that can are the parameter's own name (which is why the rename is part of the fix, not cosmetics) and an observation of the rendered result. Before concluding a module is well covered because its invariants are quantified, ask what its callers actually pass.

  **The `SCROLLBAR_THICKNESS_PX` ↔ Tailwind-class coupling is guarded in two different places, in two different directions, and neither can be collapsed into the other.** The constant's _value_ is pinned by jsdom: `Scrollbar.test.tsx` and `GridScrollbars.test.tsx` deliberately restate `- 10` as a literal rather than importing the constant, so the subtraction carries its own mutants instead of trivially agreeing with the source. The constant's _agreement with the class_ is not visible there at all — jsdom has no stylesheet and no layout — and it is not visible to the generated bdd layer either, which reads `aria-valuenow` and the announced visible proportion, both derived from `computeScrollbarMetrics`, which never sees a track length: measured, all 73 e2e tests then in the suite passed both before and after a change that moves every rendered thumb by 10px. The sole channel is `grid-scrollbars.e2e.spec.ts`'s containment test, comparing the thumb's bounding box against its parent track's in a real browser. Read its guarantee as **one-directional**: it catches the constant _lagging_ the CSS inset (measured — that is exactly the deliberately-red step-1 commit, four failing sample points), and it structurally cannot catch the constant _leading_ it, since a track computed shorter than the painted one still satisfies `computeThumbGeometry`'s pinned containment and merely paints a slightly short thumb. **The leading direction is not unguarded, though — it is guarded by the other layer, and the two do not collapse into each other.** Measured, bumping `SCROLLBAR_THICKNESS_PX` to 20 against an unchanged `right-2.5`: `npm run test:e2e` stays at **74 passed**, the full suite, while exactly **4 of the 21 tests** in `Scrollbar.test.tsx` + `GridScrollbars.test.tsx` red — precisely the four carrying the `- 10` literal restatements, with the sub-thickness clamp test still green. So the coupling is guarded in both directions by two different layers: **lagging by the browser**, the only thing that can see paint; **leading by the jsdom restatements**, the only thing that pins the constant's value. That is also what makes "never import the constant into its own tests" a rule with a measured consequence rather than only a mutation-score rationale — importing it would make expected identical to actual and delete the leading-direction guard outright. The one cell of that matrix nothing covers is a _coordinated_ leading edit, constant and literals moved together, and nothing needs to: its worst case is the benign short thumb the derivation above already describes. Note also that a bare numeric constant is not a mutation site at all in this tree's enumeration (a scoped run over the two components produced 71 mutants, none of them on `SCROLLBAR_THICKNESS_PX`'s value) — the jsdom literal restatements are what stand in for the mutant Stryker will not generate. **No `ast-grep` rule is possible here**: the invariant relates a TypeScript number to a browser-computed layout box, and ast-grep can see neither side of that.

  One more measured fact, about `Scrollbar.tsx` rather than this module, since it reads as defensive code someone will want to delete: the `Math.max(0, …)` at that subtraction site has no mutant expressing its _removal_ (Stryker swaps `Math.max`→`Math.min` and `-`→`+`, both of which the ordinary geometry tests kill), so `Scrollbar.test.tsx`'s sub-thickness-viewport test is its only guard — deleting the clamp reds exactly **1 of 663 tests across all 54 files**, that one. It pins the component's total contract over a `number` prop, not an app-reachable state: `GridScrollbars.tsx` returns `null` unless both dimensions are positive, so nothing in the app passes a viewport that small.

- **`src/patternPlacement.ts`** — the pattern-library interaction as one explicit three-state machine (`idle` / `browsing` / `placing`) rather than separate modal-open, armed-pattern, and preview-cell flags, so combinations like "library open with a pattern already armed" are unrepresentable. Exposes transitions (`toggleLibrary`, `armPattern`, `cancelPlacing`, `movePreviewTo`) and queries (`isLibraryOpen`, `armedPattern`, `previewPositions`); callers go through the queries rather than matching on `mode` themselves.
- **`src/liveCellStore.ts`** — the live-cell state itself, as a factory (`createLiveCellStore`) rather than module state: mutators (`advance`/`toggle`/`place`), per-cell subscriptions (`subscribeCell`/`getCellSnapshot`), and one content-bounds subscription (`subscribeBounds`/`getBoundsSnapshot`). The design is one invariant: **a mutation notifies exactly the cells whose aliveness changed, each exactly once, and nobody else.** That is the whole value of the module — a store notifying every subscriber would render identical pixels and pass every rendering, Gherkin and e2e test — so it is pinned by `liveCellStore.property.test.ts` as per-listener call counts, not by set equality. Two more contracts: every mutator funnels through a single private `publish()`, which re-freezes even though immer already auto-freezes (auto-freeze is a _global_ immer setting and can be defeated by a leaked scope — read the comment before removing it), so `getLiveCells()` is **always** frozen and typed `ReadonlyLiveCells`; and `getBoundsSnapshot()` keeps its object identity whenever the box hasn't moved, which is what stops `useSyncExternalStore` re-rendering the scrollbars every tick. `getLiveCells()` is inspection/export only and **never** a render source — a component reading it during render reads a value it never subscribed to, which is a correctness bug, not a missed optimization.
- **`src/liveCellSeed.ts`** — deterministic live-cell seeding for the render-performance harness (`perf/`): `parseSeedRequest` reads a `?cells=&spread=&seed=` query string, `buildSeededLiveCells` places exactly that many cells from a `Math.imul`-based LCG, and `seedFromSearch` is the two together. Only ever reached from `src/main.tsx` under `MODE=perf`, but deliberately a framework-free module rather than harness code: a seeder that silently produces the wrong population makes every perf number measured against it wrong too, and nothing downstream would notice — so it lives where mutation testing and property tests can see it. It takes the query string as an argument and never reads `location` or `import.meta.env` itself; `rules/no-dom-in-domain.yml` and `rules/no-build-env-in-domain.yml` enforce both.
- **`src/cache.ts`** — a keypath-trie cache (`createCache`, `CacheError`): entries are addressed by an arbitrary `unknown[]` key path, and the trie nodes are `PATH` or `ENTRY` (a node can be both a stored entry and a parent of deeper ones). Deliberately mutable rather than immutable, which its header comment argues at length and which is the reason to read that comment before "modernising" anything here — insert/update/remove mutate each node's `Map` in place so they stay O(keypath), where the clone-per-write immutable form (including immer's, whose `prepareMapCopy` shallow-clones the base Map on first write inside `produce()`) would be O(entries). Iteration is fenced: a mutation during a `for...of` over the cache invalidates the iterator and the next step throws, rather than silently yielding a torn view. The node representation stays private to the file — the exported surface is `createCache`, its two interfaces (`Cache`/`ReadonlyCache`), and `CacheError`.
- **`src/equality/`** — structural equality comparators, four files: `is-strict-equal.ts` (a typed `Object.is`), `container-equality.ts` (the walker: container-kind dispatch over Date/Set/Map/Array/plain object, taking the leaf comparison as an injected `compare` function), and the two one-line comparators that inject into it — `is-shallow-equal.ts` (leaves compare with `Object.is`) and `is-deep-equal.ts` (leaves compare with `isDeepEqual` itself, so it recurses). The injected comparator is the whole design: every branch that isn't a leaf comparison — kind dispatch, mismatch handling, size/key-count guards, Set multiset matching — exists exactly once, which is what stopped the two ported implementations from re-diverging (they were a near-verbatim duplicate of each other, and the mismatch bugs they carried were present in only one of the two directions). Read each comparator's scope contract before reaching for one: these are for small, known-shallow projections, and a Set of non-primitives costs O(n*m) per level.

Those sixteen form a small acyclic graph, and keeping it acyclic is the point of the split: `gameOfLife.ts`, `camera.ts`, `dragGesture.ts`, `cache.ts`, and `is-strict-equal.ts` import nothing; `patternLibrary.ts` → `gameOfLife.ts`; `gridGeometry.ts` → `camera.ts`; `cellTiles.ts` → `camera.ts`; `cellAnchor.ts` → `camera.ts` (neither imports the other — `spanCells` is a parameter both take rather than a shared import); `scrollbars.ts` → `camera.ts` + `gameOfLife.ts` (the single place the camera side touches the game model); `patternPlacement.ts` → `patternLibrary.ts`; `liveCellSeed.ts` → `gameOfLife.ts`; `liveCellStore.ts` → `gameOfLife.ts` + `patternLibrary.ts` + `equality/is-shallow-equal.ts`; `container-equality.ts` → `is-strict-equal.ts`; `is-shallow-equal.ts` → `container-equality.ts` + `is-strict-equal.ts`; `is-deep-equal.ts` → `container-equality.ts`. `cache.ts` and `src/equality/**` are the two general-purpose utilities imported wholesale by the `import-utilities` slice rather than grown from a feature. `is-shallow-equal.ts` acquired its first caller in the `live-cell-store` slice (the bounds-identity check above); `cache.ts` and `is-deep-equal.ts` still have none. They live here, inside every gate, rather than in a `src/catalyst/`-style exclusion, precisely because this repo now maintains them. A new domain module is covered by `rules/*.yml` with no rule edits whether it sits at `src/` root or in a subdirectory: ast-grep's `*` crosses `/`, so the domain rules' `files: src/*.ts` glob reaches `src/<dir>/*.ts`, **and their `ignores: src/*.test.ts` entry reaches `src/<dir>/*.test.ts` by the same rule** — a subdirectory's test files are excluded exactly like a root module's. `crap4ts.config.ts` and `stryker.config.json` scope by `src/**`, so they reach a subdirectory too. Prefer flat at `src/` root for a single cohesive module; a subdirectory is fine for a set of siblings that belong together (see `src/equality/`). (Measured twice against ast-grep 0.45.1 — once before `src/equality/` existed and again on the landed tree, both times with a throwaway probe module plus a `.test.ts` twin: the domain rules fired on the module and never on the twin. This paragraph previously claimed the opposite; it was wrong.) File naming follows the same split: `src/` root modules and `src/hooks/` are camelCase, `src/components/` is PascalCase, and `src/equality/` deliberately keeps the kebab-case names it was ported under — a decision, not drift, since the file names double as the identifiers a reader looks up when tracing these back to their source.

`src/catalyst/` sits apart from all of the above: it's vendored third-party Tailwind Catalyst UI primitives, dropped in as source rather than installed as a dependency. It isn't code this project authors, and it's deliberately outside every quality gate — `crap4ts.config.ts` and `stryker.config.json` each carry an explicit `src/catalyst/**` exclusion (`scripts/halstead4ts/run.ts` inherits it by resolving crap4ts's globs), and `.dry4tsrc.json` ignores `**/catalyst/**`. Note that's an exclusion rather than an omission: since both tools measure `src/**` by glob, anything dropped into `src/` is scored unless something says otherwise, so a second vendored directory would need the same three entries added. Components import from it as needed. Treat it as a library boundary: read it to learn a component's props, but don't refactor it to this repo's conventions or add it to a tool's include list.

### State flow

- **Live-cell state does not live in React at all.** `src/App.tsx` holds one `useState(() => createLiveCellStore(initialLiveCells))` — a stable handle, never a value that changes — and passes the store down as an opaque handle. Nothing between `App` and the leaves re-renders on a generation tick: `LifeBoard`, `Grid` and `GridCells` accept `store` and read nothing out of it, and only the components that actually subscribe (`Cell`, one per visible cell, and `GridScrollbars` for the bounding box) re-render, and only when their own subscription fires. This replaced `use-immer`'s `useImmer` (now removed from `package.json`): a producer hands back a new `Set` identity every tick, which defeats React Compiler's memoization however deep the prop drilling goes, so every visible cell re-rendered on every tick. `App.tsx`'s one optional prop, `initialLiveCells`, exists solely for the perf harness; `undefined` (every normal boot) means the ordinary empty grid.
- `src/components/GenerationHud.tsx` owns the `generation` count and the Next Generation button, advancing only via that button's own click/keyboard handling — there is no global keyboard shortcut for it. It takes `onAdvance` (wired to `store.advance`) and holds no live-cell data, so a tick re-renders the counter and nothing else above the grid.
- `src/main.tsx` is bootstrap, not a composition root: it reads `import.meta.env.MODE` and passes the _result_ down. That check has to be at the entry module for Rolldown to constant-fold it and tree-shake `liveCellSeed.ts` out of a normal production bundle, which is why `rules/no-logic-in-composition-root.yml` deliberately doesn't scope it and `rules/no-build-env-in-domain.yml` guards the same invariant from the other side. The file holds exactly one ternary and no other decision.
- Each hook in `src/hooks/` owns exactly one piece of state or one browser API, and delegates the actual rules to a framework-free module: `useCamera.ts` owns the `Camera` as local `useState` and exposes pan/zoom/wheel/center/scrollbar-drag actions that delegate to `camera.ts` and `scrollbars.ts`; `usePatternPlacement.ts` owns the `PlacementState` and its Escape-to-cancel listener, delegating every transition to `patternPlacement.ts`, and takes the place-a-pattern commit callback so that single-shot stamping (read the armed pattern, commit it, disarm) is one action here rather than a two-call sequence a caller could get wrong; `useElementSize.ts` isolates `ResizeObserver`; `useWheelInput.ts` isolates the native, non-passive `wheel` listener and hands callers a `WheelInput` instead of a DOM event; `useGridPointerGestures.ts` isolates pointer capture and drag-vs-tap resolution (delegating the threshold math to `dragGesture.ts`), reporting rect-relative pixels and never touching a `Camera`; `useInitialCentering.ts` isolates the one-shot first-non-zero-measurement latch (`useLayoutEffect` + a ref, so no frame paints uncentered); `useCellTiles.ts` holds two independent sticky values as two `useState`s — a `TileRange` (mounting coverage) and an `Anchor` (precision bounding) — returning the range as an object (reference-stable by `nextTileRange`'s own contract, so this is not a regression of the old hook's scalar-flattening discipline) alongside the anchor's pixel offset as scalars, delegating the keep-or-rebase decision for each to `cellTiles.ts`'s `nextTileRange` and `cellAnchor.ts`'s `nextAnchor` independently (read the hook's comment on why both coverage checks run during render rather than in a `useEffect`); `useRafCoalescedPan.ts` isolates `requestAnimationFrame`, summing however many pan deltas arrive within one frame into a single `onPan` call and exposing `flush()` so a pointerup settles the camera synchronously instead of waiting on a queued frame. That split is what keeps the rules testable without a jsdom environment — put new logic in the pure module and let the hook stay a thin adapter.
- `src/components/LifeBoard.tsx` is the composition root for the camera and placement state: it calls `useCamera` and `usePatternPlacement`, derives `previewPositions`/`armedPattern` from already-tested pure functions, and supplies `Grid`'s `renderOverlays` render prop with the ruler, zoom-%, scrollbars, toolbar, and pattern-library modal — in that stacking order, since all of them are `position: absolute` with auto z-index and a later sibling wins hit-testing (`GridToolbar` at `top-2 right-2` must render after `GridScrollbars`' track, or it can't be clicked where it overlaps). It deliberately touches **no** live-cell data — it only forwards the `store` handle and `store.toggle` — so a generation tick never re-renders it; the content-bounds subscription that used to sit here was pushed down into `GridScrollbars`, the one overlay that needs it. `LifeBoard.tsx` is deliberately outside every quality gate, like `App.tsx` — kept wiring-only mechanically by `rules/no-logic-in-composition-root.yml` (ast-grep, report-only) rather than by unit-test coverage; its own small `LifeBoard.test.tsx` exists only to recover the two behaviors no unit below it can prove alone (that a pointer tap on the grid actually reaches `usePatternPlacement`'s single-shot `stampArmedPattern`, and the Patterns-button-while-placing cancel path) that would otherwise be e2e-only.
- `src/components/Grid.tsx` owns the measurement (`useElementSize`), the pointer/wheel listeners (`useGridPointerGestures`, `useWheelInput`), the one-shot initial centering (`useInitialCentering`), and the DOM sibling-not-ancestor layering between `#grid-content` and whatever `renderOverlays` returns — but it imports none of `GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, or `Scrollbar.tsx` directly. Those four are inverted: `Grid` takes a `renderOverlays(context)` render prop (`context` carries only what `Grid` measures and its caller can't — viewport `size` and the computed `visibleRange`) instead of importing and rendering them itself, so `LifeBoard` supplies the actual overlay components rather than `Grid` hardcoding them. The deliberate exceptions are `Grid → GridCells → CellTile → Cell` and `Grid → PatternPreview`: cells must render _inside_ `#grid-content`, and owning that containment is exactly why `Grid` exists as its own component rather than folding into `LifeBoard`. Inside `#grid-content`, `Grid` renders two siblings in DOM order — a transformed layer div wrapping `GridCells`, then `PatternPreview` (later-in-DOM wins, and the preview must paint over the cell buttons rather than behind them). **The pan transform sits on that inner layer div and never on `#grid-content` itself**, which is load-bearing rather than stylistic: `useGridPointerGestures` and `useWheelInput` both call `getBoundingClientRect()` on `#grid-content`, so a transform there would shift that rect and silently resolve every tap and hover to the wrong world cell. `Grid.test.tsx` asserts `#grid-content` carries no transform (and, in its own comment next to that assertion, that the layer div's own transform is a pure `translate(...)` with no `scale` — this app re-lays-out on zoom instead of scaling, which keeps `getBoundingClientRect()` and layout units from disagreeing the way a scaled scroll container's would), for exactly that reason. `GridCells` consumes nothing that changes per tick _or per pan_: it iterates `useCellTiles`'s world-anchored `TileRange` (see `cellTiles.ts`), rendering one `CellTile` per mounted tile keyed by `tileKey(tx, ty)` — the tile's own world coordinates, not a lattice-style linear slot index — rather than a camera-derived cells array, and every prop it receives is pan-stable. `CellTile` renders `TILE_SPAN_CELLS²` `Cell`s as a fragment (no DOM node of its own, so the flat button-list DOM shape is unchanged from before tiling); keying by world coordinate is the load-bearing inversion from the lattice design this replaced, where a rebase reused DOM nodes at a new origin under a linear slot index instead — here, a retained tile's `tileX`/`tileY`/`spanCells`/`store`/`onActivate`/`cellSize`/`anchorX`/`anchorY` props never change while it stays mounted, so React's reconciler bails on it entirely and only the entering strip of tiles at a crossed boundary re-renders. `Cell.tsx` owns the `useLiveCell(store, key)` subscription for its own coordinate and takes a finished CSS `transform` string rather than pixel numbers, so it holds neither a `Camera` nor any pixel geometry. `PatternPreview.tsx` is the one place that stays camera-exact — it sits outside the transformed layer and recomputes `worldToScreen` per position, which is affordable because it is bounded by the armed pattern's own size, not by the viewport. That split is the point of the layer: a tick re-renders only the handful of `Cell`s whose membership flipped, not the ~34,000 mounted at min zoom, and a pan that stays within the current tile range's eviction hysteresis re-renders none of them — only a pan that crosses a tile boundary re-renders the entering strip, a small fraction of the mounted set (`cellTiles.ts`'s `enteringStripCellCount`), which is what replaced the old lattice's all-or-nothing rebase. `Grid.tsx` has its own unit tests (`Grid.test.tsx`), now scoped to that composition — the DOM layering contract, the place-vs-toggle dispatch, and one thin wiring test per hook — rather than the ~1,575-button, ~500ms-per-test renders it used to pay for when it rendered the whole tree itself; the hooks and pure modules it composes, and the four inverted overlay components, are each tested on their own.

### Testing structure (three test layers plus the contract they answer to, deliberately separate)

1. **Unit/property tests** — `src/*.test.ts` and `src/*.property.test.ts` (fast-check via `@fast-check/vitest`) for each of the framework-free modules (`src/equality/`'s own tests are one directory deeper, but land in the same two projects), plus `src/hooks/*.test.ts` (`@testing-library/react`'s `renderHook`) and `src/components/*.test.tsx` (`@testing-library/react`'s `render`/`screen`/`fireEvent`, jest-dom matchers via `src/test-setup.ts`) for the twelve unit-tested components (`GridToolbar.tsx`, `PatternLibraryModal.tsx`, `RulerLabel.tsx`, `Scrollbar.tsx`, `Grid.tsx`, `GridCells.tsx`, `CellTile.tsx`, `Cell.tsx`, `PatternPreview.tsx`, `GridRuler.tsx`, `GridScrollbars.tsx`, and `GenerationHud.tsx`). These run across three vitest projects, not one (see `vite.config.ts`'s `test.projects`): the framework-free-module tests run under the `unit` and `property` projects in plain Node — no `document`, no jsdom cost — while the hook and component tests run under the `dom` project in jsdom, since only those actually render. A new test file lands in `unit` by default (it's the project that subtracts rather than includes) and fails loudly if it needed jsdom after all. One consequence worth knowing before writing a property test: `property`'s `include` is the bare `**/*.property.test.ts`, which is _not_ rooted at `src/` root, so a `*.property.test.ts` placed under `src/hooks/` or `src/components/` would be collected by both `property` (Node, no React plugin, no jsdom) and `dom`, and fail in the first. That is a feature, not a gap — property tests belong in the framework-free layer, and a hook-resident invariant worth quantifying over is a signal to extract the rule into a module rather than to reach for a config exception. This is where implementation correctness lives — edge cases, invariants, and the numeric precision (`-0` handling, clamp boundaries, same-reference no-ops) that a Gherkin Examples table can't express.
2. **Browser-required unit tests** — `src/**/*.browser.test.ts` (co-located with the module they cover, run by `npm run test:browser` via `vitest.browser.config.ts` — Vitest Browser Mode driving real Chromium, reusing the Playwright binary `npm run test:e2e` already installs). Same kind of test as layer 1, and owned by the same roles (`coder`/`cleaner`/`architect` — never `product`): it imports one module directly and never boots the app. It exists only for contracts jsdom has no faithful equivalent for, currently just `useElementSize.browser.test.ts`, which pins down that the real `ResizeObserver` fires an initial callback from `observe()` itself and delivers an update on a real size change — neither of which the jsdom stub in `src/test-support/domStubs.ts` reproduces (it fires only when a test calls `.resize()`). This layer is **additive only**: `vite.config.ts` excludes the `*.browser.test.ts` suffix, and since `crap4ts`/`npm run test:mutation` both run through that config, neither can see these files. Moving an assertion out of a jsdom test into one of these silently drops coverage and mutation score on the module — always leave the jsdom test in place. See `.claude/agents/articles/engineering.md` for which layer a given test belongs in.
3. **The Gherkin contract — no longer a test layer of its own.** `features/*.feature` (plain-English specs) is `product`'s manifest and the user-facing contract, end to end. It used to have a second executable form beside the browser one — `features/*.steps.test.ts(x)`, step definitions on `@amiceli/vitest-cucumber` run by vitest in Node or jsdom, plus the `features/harness/` modules the jsdom form mounted `<App />` through. **`delete-step-test-layer` removed all of it**: seven step files and the harness, 1,326 lines, the `acceptance` vitest project, and the `@amiceli/vitest-cucumber` dependency. **`features/` now contributes zero tests to `npm test`.** Every `.feature` file is executed exactly once, by playwright-bdd against the step modules in `features/steps/*.ts`, which is item 4 below — read this item as _what the contract is_ and item 4 as _how it runs_. The **suffix** is still what separates the artifacts inside the directory: `.feature` (the contract), `.e2e.spec.ts` (the hand-written Playwright specs) and `e2e-helpers.ts` (their barrel). **There are two subdirectories, and neither holds a test file**: `features/steps/` (the step definitions bddgen compiles the contract against) and `features/screenplay/` (the helper modules the barrel re-exports), both described in item 4. This layer's purpose is the stakeholder-readable, accepted-behavior contract and the `product`→`coder` handoff (see Subagent pipeline below), not incremental defect detection beyond the unit tests — its assertions overlap substantially with the unit tests covering the same functions, and that overlap is expected rather than duplication to eliminate. The one feature that isn't overlap-redundant is `pattern-library.feature`, whose Examples table is the only place the exact cell geometry of all 8 patterns is pinned down — the unit and property tests check names, categories, and the bounding-box anchor convention, but never the shapes themselves.

   **ARCHIVE — everything below describes a layer that no longer exists, and is kept for its method.** The vitest step layer was first removed from `npm run test:mutation` by `stryker-excludes-gherkin` (`ignorePatterns` keeping `features/` out of the sandbox) on the strength of the measurement below, and then deleted outright by `delete-step-test-layer`. So this is now doubly historical: the exclusion it argues for is belt-and-braces, and the layer it measures is gone. It stays because the reasoning is transferable — it is the only written account of _why_ a `killedBy` naming a step test never meant what it looked like, and that failure recurs the moment any runner compiles one logical case into several `test`s. Read it as method, never as a description of what the gate runs.

   **The removal experiment below can no longer be run at all — there is nothing left to remove, since `features/` holds no vitest test.** It is recorded for its shape. When you need to know whether some layer is the sole killer of a mutant, a removal experiment names _candidates_ and nothing more; the verdict is hand-applying the mutant and running the whole unfiltered suite. Never trust Stryker's `killedBy` when it names a `features/**` test — against a step-per-test runner it is a false positive whenever a scenario's setup steps fall outside the covering set, which is the normal case rather than the exception.** Measured against Stryker 10.0.0 / vitest 4.1.10 / `@amiceli/vitest-cucumber` 7.0.0.

4. **Black-box e2e tests** — `features/*.e2e.spec.ts` (Playwright, real Chromium, run against `npm run dev` on a fixed 1280×900 viewport), alongside the Gherkin layer in `product`'s one directory. `features/e2e-helpers.ts` is the barrel over the shared helpers, which live one module per Screenplay role in `features/screenplay/`; many pixel-math assertions are derived from the exact default camera (`offsetX: -32, offsetY: -22.5, cellSize: 20`) that results from that fixed viewport, declared once in `features/screenplay/viewport.ts` — read that module's comments before changing default camera values or the viewport size. **A hand-written spec is no longer the browser-level counterpart of a `.feature`, and reading it that way is the mistake `triage-paired-specs` existed to correct.** Since playwright-bdd landed, the browser-level execution of a feature _is_ its generated `bdd` spec — same real Chromium, same viewport, driven by `features/steps/*.ts`. A hand-written spec sharing a `.feature`'s name therefore holds only the **residue**: the part of that feature's subject matter no Gherkin scenario can state. An assertion in it that a scenario already makes is duplication rather than defence in depth, which is what that triage deleted 35 tests and one whole spec file on.

   **Three pairing states, all three normal.** A `.feature` **with** a hand-written spec beside it (`camera-pan-and-zoom`, `cell-life-and-death`, `grid-reference-lines`, `grid-scrollbars`, `mouse-wheel-controls`), holding residue only. A `.feature` **without** one (`infinite-grid`, `pattern-library`) — this is the _default_ rather than a gap, and says the feature's claims are stated in Gherkin and driven by its generated spec with no residue left over; an absent `.e2e.spec.ts` is not missing browser coverage. And a hand-written spec **with no** `.feature` (`hud-layout-and-shortcuts`, `modal-inertness`), whose subject matter is residue end to end — those are specified by `product`'s plain-English outline instead, which each records in its own header comment so the accepted behavior stays written down.

   **What residue is — four categories, and nothing else may be added here.** (1) **Hit-testing and stacking**: which element receives a pointer event where two overlap. (2) The **computed accessibility tree** — what a browser's own accessible-name/description algorithm delivers, as distinct from the attributes it is computed from, which a step module can read for itself and jsdom only reimplements. (3) **Rendered pixel geometry**: a measured box, a pixel coordinate, an element resolved by point. (4) **Native-event delivery** — an event carrying fields no step sends, such as a wheel with both axes populated. **Anything expressible as a `.feature` scenario goes there instead.** A claim that seems to need implementation vocabulary is a prompt to re-read `.gherkin-lintrc`'s altitude rules, not a licence to write it here.

   **Every hand-written test carries a header naming the claim it uniquely holds**, and that header is what licenses the test to keep existing — the `feature-prose-honesty` pattern generalized from `.feature` prose to this layer by `triage-paired-specs`, and the durable form of that triage. The reverse obligation comes with it: a test may not be deleted here without its claim being restated in `features/**`. A deletion resting on **subsumption** — a surviving sibling that happens to make the same claim — rather than on a demonstrated failure is the weak case and must say so in the commit that makes it, because such coverage is usually _incidental_ (it holds only for the sibling's current inputs) and can evaporate later with nothing going red. That is the same failure `ruler-label-axis-affordance` measured one affordance earlier.

   **`.features-gen/` is this repo's first generated artifact. Never edit it, never cite it as source, never commit it.** It is gitignored, Prettier-ignored, oxlint-ignored, and subtracted from `vite.config.ts`'s `sharedExclude` (without that last one vitest's unrooted `unit` include collects the generated specs — measured, 63 files instead of 61). The `.feature` file and its step module are the source; a generated spec has the same status as `dist/`, so a finding in one is a finding in one of its two inputs.

   **Nothing regenerates it automatically, which is why `npm run test:e2e` is the only supported way to run Playwright here.** With `.features-gen/` absent the `bdd` project's `testDir` matches nothing and Playwright reports the `e2e` project alone — `Total: 59 tests in 8 files`, exit 0, no warning (measured before the guard described next existed, back when the `e2e` project held 59 tests in 8 files; `triage-paired-specs` has since cut that project to 27 tests in 7 files, but the guard now refuses to load before this scenario is ever reached again, so the figure is left as the historical measurement it is rather than re-run) — the same failure shape as a Stryker `ignorePatterns` glob matching nothing, a `-t` pattern matching nothing, and a vitest project `include` matching nothing, all documented above. A **stale** `.features-gen/` is quieter still: playwright-bdd has no staleness detection of its own, so an edited `.feature` runs against the previous generation's spec. `playwright.config.ts` therefore refuses to load when the generated output is missing, empty, or older than any `features/*.feature` or `features/steps/*.ts`, and says which. That check is skipped only during the generation phase itself, which bddgen marks by setting `PLAYWRIGHT_BDD_GEN=1` (playwright-bdd 9.2.0; read as a bare env var because the helper that sets it is not exported from the package index) — without that branch the guard would refuse to load the config bddgen needs in order to clear the guard. bddgen rewrites every output file unconditionally (measured: two consecutive runs on an unchanged tree advance every mtime), so the staleness check self-heals and a spurious fire costs one `npm run test:e2e`.

   **The step registry is global across `features/steps/`, and bddgen is the only thing that checks it.** playwright-bdd loads every step module for every feature, so a step text defined in two modules is an ambiguous-step error rather than an override, and a step text moved out from under a feature that borrowed it is a missing-definition error. Both exit 1 naming the files involved — measured in both directions. The convention that keeps this legible: **a step shared by several features is defined once, in the module the step is _about_.** `camera-pan-and-zoom.ts` owns the camera and zoom steps `grid-scrollbars` and `mouse-wheel-controls` borrow; `cell-life-and-death.ts` owns the grid, generation and cell-state steps `infinite-grid` and `pattern-library` borrow — the latter takes three of them ("an empty grid", "a live cell at (<x>, <y>)", "the cell at (<x>, <y>) should be alive") and gets them by writing the same text and defining nothing. No import expresses that dependency and none should — `rules/no-domain-imports-in-bdd-steps.yml` forbids a step module importing another, since the sharing is a registry fact and an import would dress it up as a module dependency. **This is the second guarantee riding on the guard above**: skipping bddgen skips the cross-module check as well as the tests, and there is no other. No ast-grep rule can supply it, either — ast-grep matches within a single file and has no cross-file aggregation, and since the shared orientation steps are `RegExp` patterns rather than cucumber expressions, whether two step texts collide is decidable only by cucumber-expressions' own matcher against actual `.feature` text. A homegrown text-uniqueness checker would be answering a different question than the runner does.

   **`features/e2e-helpers.ts` is the single module a step module may import**, mandated rather than conventional: `rules/no-domain-imports-in-bdd-steps.yml`'s allowlist is exactly `playwright-bdd`, `@playwright/test` and `../e2e-helpers`. Anything a step needs that it cannot reach through that module is **added to the `features/screenplay/` module that owns it and re-exported from the barrel**, never imported around. Post-split that is the whole of the instruction that used to read "added there": `e2e-helpers.ts` is now a pure re-export file, so writing a function body in it would be the wrong fix in the other direction. The layer is shared with the hand-written `*.e2e.spec.ts` specs — same layer, same rules — and it is where this layer's ARIA reach-arounds are confined whenever one exists. **The confinement is the discipline, and it is general rather than a note attached to whichever one is outstanding**: a reach-around lives in exactly one function, never as an idiom several call sites reach for, and it carries a **deletion trigger** beside it naming the slice that will retire it. **Zero are live.** Both that have ever been filed have now been paid off, in consecutive slices, and in each case the confinement is what made the landing a small edit rather than an archaeology exercise — which is the argument for keeping the discipline, not evidence that it is finished. `rulerGroup` (in `features/screenplay/elements.ts`) and `axisLabelValues` (in `questions.ts`) read a Tailwind edge class until `ruler-label-axis-affordance` added the named `role="group"` they now reach the ruler through, and that landing was the only edit `features/` needed. `thumbTrackFraction` measured the thumb's bounding box against its parent track's until `scrollbar-visible-proportion-affordance` gave the thumb an `aria-describedby` → visually-hidden description of what proportion of the grid is in view; `visibleProportionPercent` (in `questions.ts`) reads that instead. The second payoff was larger than a swap, and that is the part worth generalizing: the pixel read needed a `FILLS_TRACK = 0.99` threshold and a `toBeCloseTo(0.25, 2)` to absorb sub-pixel layout rounding, where an announced integer serves both dependent `.feature` clauses **exactly** — 100 for "fills its track", 25 for "covers a quarter of it" — so both tolerances were deleted with the function. A reach-around's cost is rarely just the one function; it is usually the slack every assertion downstream of it had to carry. **`patternCategoryInLibrary` is deliberately not a third one, and the distinction is the criterion to apply to the next candidate.** It reads the modal's `h3`-then-buttons document order, which _is_ the affordance heading navigation gives an AT user; the `h3` selector is query mechanics (no by-role locator spans two roles, and the interleaving is the signal), not a substitute for something the user cannot perceive. A reach-around stands in for a perception the accessible tree does not offer at all — a paint class, a pixel proportion — and owes an affordance idea named beside it; a structural query for something a user genuinely can perceive owes nothing, which is why that function has no idea filed and should not grow one. Adding `aria-labelledby` to those sections for query convenience was ruled out as a test hook wearing an affordance's name, and would also stop the check exercising what a user actually relies on. **It has been split, and the file survives the split as a re-exporting barrel** — the `screenplay-e2e-decomposition` slice moved its 468 lines into `features/screenplay/`, one module per Screenplay-pattern role: `viewport.ts` (the fixed camera/viewport facts, importing nothing), `notepad.ts` (scenario-scoped scratch state, keyed by the `page` fixture since this suite has no Actors), `elements.ts` (the PageElements — how a thing is reached), `questions.ts` (reads, never asserts), `interactions.ts` (one user act each), `tasks.ts` (goals composed of interactions) and `expectations.ts` (the assertions). Facts one and three are kept because their subject is not the layer: one is a measured property of a third-party runner and the standing warning against reasoning about a lifecycle instead of measuring it (`architect.md`'s CONTRACT-mode question 4 leans on it), and three is a fact about `src/` that is still exactly true. Fact two is kept because its principle outlived its subject — see its own note.

_First, `@amiceli/vitest-cucumber` compiled every Gherkin **step** into its own vitest `test`, not every scenario._ Measured on 7.0.0, on a tree where that layer still existed: `cell-life-and-death.feature` collected **48 tests, not 13**, with `ancestorTitles` naming the scenario and the test itself named for the step. `src/test-setup.ts` installs a global `afterEach(cleanup)`, so **that cleanup fires _between_ a scenario's `Given` and its `When`** — an RTL-`render`ed tree cannot survive one scenario, and the failure reads as a bare `expected null not to be null` in the `Then`, which looks nothing like a lifecycle problem. `features/harness/board.tsx`, the shared harness core, works around it by owning its own `createRoot` container (`cleanup()` is then a no-op for the board, and `mountBoardRequiring()` unmounts the previous one), which is why it does not call `render()`. There is no future conversion to inherit it, and the `acceptance` project the count was read off no longer exists. **What generalises is the method, not the number**: when a contract will be executed through someone else's runner, read the collected-test count off an actual run rather than reasoning about what the runner probably does. A DESIGN pass asserted the opposite of the fact above from plausible reasoning and was wrong.

_Second, harness-style code is test infrastructure and is **not** expected to carry its own unit tests._ **This is the fact that outlived its subject.** The harness is gone, but `features/steps/` and `features/screenplay/` are the same category and inherit the ruling verbatim: they are the `features/`-side peers of `src/test-support/`, which is already excluded from `crap4ts.config.ts` and `stryker.config.json` for exactly this reason, and requiring coverage of it would gate a category this repo has deliberately decided not to gate. (An ad-hoc `--mutate` run over the **then-monolithic** `features/acceptance-harness.tsx`, outside every configured gate, scored 60.63% with 33 survivors; the `[NoCoverage]` rows are throw paths a passing suite never enters, and the two teardown survivors are individually near-equivalent. That file has since been split into `features/harness/board.tsx` plus one module per feature and the run has **not** been repeated, so the figure stays attributed to the file it was actually measured on rather than carried forward onto either of its successors.) That is not the same as unverified — three things check a harness, and a conversion should be able to point at all three: the steps suite going green end to end (which exercises every mount, query and teardown path a scenario uses), `npm run acceptance-mutation`'s per-mutant collected-test-count discipline, and the harness core's own `assertWindowMounted()`, which fails loudly if the mounted world rectangle ever stops containing the `WorldWindow` the feature's own harness module declares its scenarios and their mutants need. (It took no argument and read a module constant until `split-acceptance-harness` parameterized it — the required window is per-feature state, so it could not stay in the core.)

_Third, a `fireEvent.click` on a cell in this layer is **not** the route a mouse user takes, and the difference is not a jsdom artifact._ `useGridPointerGestures` takes pointer capture on `#grid-content`, which retargets the subsequent native `click` to the container — so `Cell`'s own `onClick` never fires for pointer-driven interaction, and `Grid`'s `onTap` resolves the cell from pointerup pixels through `screenToWorld` instead. `Cell.onClick` is therefore the **keyboard-activation** route (Enter/Space), and jsdom's `fireEvent.click` dispatches a bare `click` with no pointer sequence — so this layer drives that keyboard route and never exercises hit-testing at all. **There is now exactly one black-box layer, and this is why losing the other cost no reach.** The two used to be nested rather than complementary, and the survivor is the outer one. The e2e layer drives _both_ routes: Playwright's `.click()` for the pointer route, and `page.keyboard.press('Enter')` on a focused cell button for the keyboard one (`features/hud-layout-and-shortcuts.e2e.spec.ts:102`). The acceptance layer saw a strict subset of the routes the browser layer sees, plus no hit-testing — it reached nothing Playwright structurally cannot, which is the measured basis for deleting it without replacing its coverage. Measured on this tree by injecting `Cell`'s `onActivate(x, y)` → `(y, x)`: the acceptance project fails (5 of its 48 step-tests), the full Playwright run is **58 passed / 1 failed** — the failure being that keyboard test, on `aria-pressed` — and all **14 tests** in the paired `cell-life-and-death.e2e.spec.ts` pass, every activation there being a `.click()`. What survives of this is the narrow half only, and it is now a warning about a layer nobody can run: **a green jsdom run was never evidence about hit-testing**, which is exactly what it could not see. (Commit `4f6e14d`, "record why the e2e layer cannot see `Cell.onClick`", concluded the opposite — "disjoint activation routes", "passes all 14 e2e specs" — from a Playwright column pre-registered as that one paired spec file, and generalized to the layer; `product`'s VERIFY pass refuted it by running the whole layer. Its subject line and body cannot be rewritten, so this paragraph is the correction.)

There is no single default jsdom run any more — `vite.config.ts`'s `test.projects` splits the main vitest config into `unit`/`property` (Node) and `dom` (jsdom) projects (see Architecture above) — but all three projects still exclude `**/*.e2e.spec.ts`, `**/*.browser.test.ts`, and `**/*.perf.spec.ts` via the shared `exclude` list, so the three runners (this config, `vitest.browser.config.ts`, and Playwright) never collide. That same shared list also subtracts whole **directories** — `scripts/`, `ideas/`, `.claude/`, `.stryker-tmp*/` and `.features-gen/` — because the `unit` project inherits an **unrooted** include (see `vite.config.ts`'s comment on why it subtracts rather than declaring its own), so every directory in the checkout is reachable unless `sharedExclude` names it. That is a live hazard rather than housekeeping: measured on this tree, a stray `.test.ts` dropped into `perf/`, `rules/`, `rule-tests/`, `patches/` or `public/` is still collected into `unit` and run in Node. Those five are deliberately left unexcluded — a name added here to a directory that might one day hold a legitimate colocated test would exclude it silently — and the merge protocol's mutation-invariant clause explains which paths the exclusion is genuinely owed to.

`npm test`/`npx vitest run` with no `--project` flag runs all three (`unit`, `property`, `dom`); `npm run test:unit` and `npm run test:property` narrow to a subset via `--project`, which is the only way to filter which project(s) run once `test.projects` is set — a plain `--exclude` on the CLI has no effect there. `--project` matches by the project's `name`, so `npx vitest run --project dom <path>` (or the bare `name`, or a `!name` negation as `test:unit` uses) is how to run just one project's slice of the suite. Be aware a vitest project whose `include` glob matches nothing simply reports 0 files and exits 0 — there is no warning — so if `dom`'s globs (`src/components/**` and `src/hooks/**`) ever stop matching anything (e.g. one of those directories gets renamed), `npm test` stays green while quietly running 23 fewer files (measured on this tree: `dom` collects 23 files, 175 tests); see the comment in `vite.config.ts` for the other files that same rename would need to update.

`perf/` is a fifth top-level directory of Playwright specs, and deliberately **not** a fifth test layer: it measures render cost and asserts nothing about performance (see `perf/README.md`). It is outside every quality gate on purpose, which is why the split described under "Custom quality tooling" below matters — the numbers themselves are computed in `scripts/perf-report/`, which is gated.

### Custom quality tooling in `scripts/`

`scripts/` is TypeScript, not JavaScript, and is its own project — separate `tsconfig.scripts.json`, `vitest.scripts.config.ts`, `crap4ts.scripts.config.ts`, and `stryker.scripts.config.json` from the ones covering `src/`/`features/` above. It's the tooling every other role's quality gate runs on, so it's held to the same CRAP threshold (6) as `src/`, via its own parallel commands (`npm run test:scripts`, `npm run test:coverage:scripts`, `npm run crap4ts:scripts`, `npm run dry4ts:scripts`, `npm run test:mutation:scripts`) — see `.claude/agents/articles/engineering.md`'s "Working inside scripts/" section for exactly which command each pipeline role substitutes for its usual `src/`-scoped one.

Its layout is two levels and no more: **`scripts/<program>/` holds one program's own modules** (its `run.ts` shell plus the pure modules that shell delegates to), and **a file at `scripts/` root is shared by two or more programs**. `scripts/feature-files.ts` is the current example — `listFeatureFiles` is the one place that answers "which `.feature` files exist", used by both `acceptance-mutation` and `gherkin-dry-checker`, which previously carried two independent hardcoded copies of that list that went stale separately. Shared root modules are ordinary product code and sit inside the gates exactly like a program's own modules; the one exception is `scripts/test-support.ts`, which is test infrastructure and is excluded by the same `**/test-support.ts` glob in `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` that already excludes `scripts/perf-report/test-support.ts`. **Imports run program → shared and never the reverse**, which is what keeps the shared file safe to change: a root module that reached back into a program directory would couple every other program to that program's internals. Nothing checks that direction mechanically yet — with two shared files it's prose, and `architect` should encode it as an ast-grep rule at the first violation or the third shared module, whichever comes first (a `files:` glob can't express "`scripts/` root only", since ast-grep's `*` crosses `/`, so that rule needs the throwaway-probe measurement this file describes for the domain rules).

- `scripts/acceptance-mutation/` — **owned by `product`, not `hardener`** (it mutates the _spec_ and asks whether the scenario notices, so both sides of what it measures are `product`'s). Mutates individual values in `.feature` Examples tables (never source code) and reruns the target's generated Playwright spec to check the scenario actually notices (concept from unclebob's Acceptance-Pipeline-Specification). Every mutant and every baseline copy of a target is written as its own `.feature` file into one shared temp tree (`.features-gen/acceptance-mutation/`, in-tree — playwright-bdd's module resolution fails out-of-tree), and each of the run's two phases (baseline, then mutants) does exactly one `bddgen` generate + one `playwright test` run over the whole batch, rather than one process spawned per mutant — see `run.ts`'s own header comment for the two-phase design. `run.ts` itself is excluded from `crap4ts.scripts.config.ts`/`stryker.scripts.config.json` by their `**/run.ts` globs, so it holds only I/O and composition: what a mutant _is_ (its seed key, its filename's ordinal, its mutated text) lives in `mutant-plan.ts`, and what its filename _looks like_ lives in `mutant-tree.ts`, both inside the gates. That split is load-bearing rather than tidy — classification looks a result up by the mutant's filename, so a record whose name and text came from different cells would misattribute a kill or a survivor with nothing in the output to notice it by. `architect` ratified the batched form over a per-mutant-spawn alternative on cost (measured 215.3s against a >400s floor for the per-mutant form, an identical verdict either way). In practice this hardens the Gherkin layer against itself — the weaknesses it has surfaced so far were in step definitions absorbing a mutated value without noticing, not in the framework-free modules themselves — so treat it as acceptance-suite quality assurance, not as evidence the Gherkin layer is finding core-logic bugs unit tests miss.

  Three things it does before it will score anything, each of them closing a way the runner could report a confident number about nothing. **Targets are discovered from `features/`**, not from a hardcoded table (`discovery.ts`, over `scripts/feature-files.ts`) — every `.feature` file present is a target; discovery no longer pairs a target against a `*.steps.test.ts(x)` file at all, since the generated Playwright spec a mutant actually runs against doesn't exist yet at discovery time (it's produced later, by bddgen, from the mutant `.feature` files the runner writes) — see `discovery.ts`'s own comment for why that pairing check was dropped rather than adapted. **Every active target's unmutated feature runs once, batched with every other target's baseline, before any mutant is written**, and a baseline that isn't green (no matching spec in the report, zero specs collected, a failure, or a skipped spec) aborts the whole run naming the target — there is no trustworthy spec count to compare its mutants against, so proceeding would misreport them rather than merely under-report. **Each outcome is read from Playwright's JSON reporter** (`PLAYWRIGHT_JSON_OUTPUT_FILE`, written to a fresh path per phase so a crashed run can never be scored off a previous one's file), never a regex over console text: `killed` requires the same collected-spec count as the baseline, zero skipped specs, and at least one `unexpected` (failed) spec; a mismatched count or any skipped spec is `error` instead, and a matching, unskipped count with zero failures is `survived`. The error-on-mismatch half continues a repaired defect from this module's original vitest-based form, not a precaution reinvented for Playwright — the old classifier read a nonzero exit plus vitest's ordinary failure chrome as a kill, so a steps file broken at _import_ (0 tests collected, exit 1) scored as a kill on every mutant, and a wholly broken suite would have reported 100%.

  Separately from those three guards, and about the run's **output** rather than its preconditions: **a target with no Examples table contributes zero mutants and is reported as `0 mutants (no Examples table): <feature>` rather than silently dropped**, with the aggregate reading a defined `100.0%` — vacuously clean, nothing ran. That is a designed state, not a warning: since `prune-gherkin-to-domain-language`, **four of the seven features carry no Examples table at all** (`camera-pan-and-zoom`, `grid-scrollbars`, `infinite-grid`, `mouse-wheel-controls`), because a table-less scenario costing zero mutants is the lever that slice pulled — so `npm run acceptance-mutation -- --feature <one of those>` is a routine command, and it used to print `mutation score: NaN%` at exit 0. The label says only what it can actually observe: a target excluded by `--feature` is filtered before it becomes a plan, so it is never in that list.

  **One mutation class an assertion shape has to be built for.** `mutateCommaList` (`scripts/acceptance-mutation/mutation-rules.ts`) splits an Examples cell on `,`, mutates one part **in place**, and rejoins with `,` — so the list never loses an item, but the mutated part frequently stops being a parseable item of it (`(0, )2` and `a1, 1)` are real mutants of `pattern-library.feature`'s cell-geometry column). A step that parses such a cell therefore sees a **shorter expected list** while the screen shows exactly what it always did, and a one-directional "every expected item is present" check passes against it. What kills that class is bidirectional set equality **plus an explicit count** — `features/steps/pattern-library.ts` is the worked example, and hand-applying the Glider mutant fails on the count assertion and on nothing else. This is only about the syntax-breaking mutants; one that stays parseable is caught in either direction.

- `scripts/gherkin-dry-checker/` — advisory-only; scans all `.feature` files for step-text vocabulary duplication/drift, discovering them through `scripts/feature-files.ts` (see above) rather than the hardcoded list it used to carry. Always exits 0 on a successful run (report-only), writes to `reports/gherkin-dry/report.json`.
- `scripts/halstead4ts/` — runs `fta-cli` against the same files as `crap4ts.config.ts`'s `include` list and prints a Halstead (volume/difficulty/effort/bugs) + FTA Score table alongside crap4ts's per-function CRAP table. FTA only reports at file granularity (no per-function breakdown), so this is a second, coarser report rather than something merged into crap4ts's output — and since FTA's own score formula isn't published, it's report-only like `gherkin-dry-checker`, never a CI gate. `run.ts` resolves `crap4ts.config.ts`'s own `include`/`exclude` globs rather than keeping a copy of the file list — the two used to be hand-synchronized arrays of the same 21 paths, and a list like that goes stale silently: a module missing from it is simply never reported on, and nothing fails. fta-cli returns no analysis at all (an empty array, not a zeroed-out one) for any file at or under its own size floor — measured at ≤6 code lines, comments not counted — so a file that small renders as an explicit `not scored (under FTA size floor)` row rather than crashing the tool or, worse, vanishing from the report; `src/equality/is-strict-equal.ts` is the first file to hit it.
- `scripts/perf-report/` — turns the raw `RawScenarioSample` JSON files `perf/` writes under `reports/perf/raw/` into `reports/perf/latest.md`/`latest.json`/`history.jsonl`. Report-only, no thresholds. This is where **every** median, percentile, ratio, and unit conversion in the perf harness lives — `perf/` itself computes none, because `perf/` is outside the gates and a wrong statistic there would be silent and plausible-looking. The boundary between the two is a file on disk, not a module import: `import type` crosses it (erased at compile time), a value import never may, in either direction, and `rules/no-value-import-across-perf-boundary.yml` checks that mechanically. It's also a real compiler boundary — `perf/` is in `tsconfig.app.json` (`moduleResolution: "bundler"`, `lib: DOM`) and `scripts/` in `tsconfig.scripts.json` (`nodenext`, no DOM).
- `scripts/ast-grep-rule-check/` (`npm run ast-grep:rules`) — **this is the first of two checks in this list that gate.** Every other check in this list needs judgment to act on; this one is a set of binary facts about `rules/*.yml` + `rule-tests/*.yml`: does every rule have a fixture, does its `id` match its filename, are ids unique, does it declare a valid `severity`, does its fixture carry an `invalid:` case, does every `files:` glob resolve to a real file, does a fixture's own `id` name the rule its filename claims to test (ast-grep binds a fixture to a rule by that `id`, not by the filename, so this is the reverse direction of the fixture-exists check), was at least one rule found at all, and is an `allow-unresolved-files` marker still excusing anything or has every glob it named since resolved (a stale opt-out) — so it exits nonzero on any failure instead of always exiting 0. Rule and fixture files are discovered by reading `sgconfig.yml`'s `ruleDirs`/`testConfigs[].testDir` and recursing into them, mirroring ast-grep's own recursive scan of those directories (verified against 0.45.1) rather than a hand-maintained list or a non-recursive, hardcoded `rules`/`rule-tests` pair — except each testDir's snapshot subdirectory (`__snapshots__` by default, or whatever that `testConfigs[]` entry's `snapshotDir:` names), which `ast-grep test` itself never treats as fixtures (Jest-style snapshot storage) and which this checker skips for the same reason. That skip is scoped to a direct child of a testDir, since that is the only place ast-grep gives the name a meaning: a rule at `rules/__snapshots__/no-foo.yml` is live in `ast-grep scan` (measured), so exempting it would hide a real rule from every check here. The `files:` check has an explicit, reason-required opt-out (`# ast-grep-rule-check: allow-unresolved-files <reason>`) for a rule authored before the file it scopes exists, and deliberately doesn't check `ignores:` globs: an unresolved `files:` glob fails _open_ (the rule silently checks nothing), while an unresolved `ignores:` glob fails _safe_ (the rule just over-applies, which shows up as noisy findings). Owned by `architect`, the only role that authors rules.
- `scripts/agent-doc-check/` (`npm run agent-doc-check`) — **the second checker in this list that gates**, over `.claude/**` + CLAUDE.md itself rather than over `rules/`. Five binary facts: (1) every `npm run <script>` reference in `.claude/**/*.md` + CLAUDE.md names a real `package.json` script (excluding `.claude/worktrees/`, a sanctioned slice-worktree location that holds whole other checkouts — their own `.claude/`, their own `node_modules` — rather than this repo's docs); (2) every `.claude/agents/*.md` file's frontmatter validates — `name` matches the filename, `description` is non-empty, `tools` is a subset of the known tool set, `model` is one of `opus`/`sonnet`/`haiku` (parsed with a bespoke line-anchored reader rather than a real YAML parser, because several agent descriptions contain a literal `": "` that a real YAML parser reads as a nested mapping and refuses — measured to fail exactly this way on 2 of the 5 agent files as they stand); (3) no backticked mention of a retired role (`qa`, `refactorer`, `specifier` — a short, git-verified list of every role ever deleted from `.claude/agents/`, not a generic "role-shaped token" scan, which was tried and rejected for flagging six unrelated backticked identifiers to two real hits when tested against this repo's own docs) without a historical qualifier (old/former/then/merge/...) on the same line; (4) the role-cycle string (`product → coder → cleaner → architect → hardener → product`) is byte-identical everywhere it appears, built from whichever roles currently exist rather than a hardcoded chain so a role rename is picked up for free; (5) every `rules/*.yml` is named in CLAUDE.md, and every explicit `rules/<id>.yml` path CLAUDE.md names resolves to a real file. Same shape as `ast-grep-rule-check` deliberately — pure `decide()` over parsed input, I/O isolated to `run.ts`, one file per parsing concern. Check 1 has no notion of "just an example": a hypothetical script name written in prose without angle brackets reads exactly like a real reference and fails the gate the same way a genuine typo would — write a hypothetical one as `npm run <script-name>` instead (see `npm-run-refs.ts`'s module comment; this checker's own development tripped over exactly that).

All six run via `tsx` (`npm run halstead4ts`/`acceptance-mutation`/`gherkin-dry`/`perf-report`/`ast-grep:rules`/`agent-doc-check`, each `tsx scripts/.../run.ts`) and have their own `.test.ts` unit tests runnable via `npm run test:scripts` — a dedicated Node-environment vitest config; `vite.config.ts` excludes `scripts/**` from the main `npm test`/`npm run test:unit` run, so scripts' tests no longer run there.

`sgconfig.yml` + `rules/*.yml` are a seventh checker, and the only one that isn't a `scripts/` program: [ast-grep](https://ast-grep.github.io) structural rules encoding the architectural invariants that were previously prose only. The twenty-one current rules cover domain modules importing React (`no-react-in-domain`), touching the DOM (`no-dom-in-domain` — including bare `location.*`, which never mentions `window`), reading the build/process environment (`no-build-env-in-domain`), or holding module-level mutable state (`no-module-state-in-domain` — a domain module may own state, but only state a factory hands back per instance; deliberately not scoped to `src/**/*.test.tsx`, where the same class is legitimate paint and `Cell.test.tsx` keeps one alive/dead pair as the visual contract on purpose), and product code importing from `src/test-support/` (`no-test-support-in-product-ts` / `-tsx` — a TS/TSX twin pair for the usual different-parsers reason; `delete-step-test-layer` deleted them). `language: TypeScript`, not the retired `.steps.test.tsx` sibling's `Tsx` — the two parsers are different and a rule declared for the wrong one matches nothing and reports nothing. Measured against `@stryker-mutator/instrumenter@10.0.0`: `string-literal-mutator.js`'s `isValidParent()` excludes `types.isJSXAttribute(parent)` and keys on the **direct** parent, so `aria-label="Zoom in"` carries no mutant while `aria-label={'Zoom in'}` does — bracing nine sites took `GridToolbar.tsx` from 1 mutant to 5, `GridRuler.tsx` from 5 to 9 and `Scrollbar.tsx` from 52 to 53, every one of the nine killed by a test that already existed. This rule encodes a **workaround, not a principle** — nothing about accessibility wants braces — and its real job is catching a revert rather than the original omission: oxlint's `react/jsx-curly-brace-presence` has an autofixer that strips exactly this form, is off in `.oxlintrc.json` today, and measured with it enabled `oxlint --fix` rewrites all nine sites back to bare strings, deleting nine mutants with no threshold anywhere noticing, since a mutation score is a ratio over the mutants that exist. If a future Stryker release closes the opening it fails **safe** — the mutant count falls, it never falsely rises — and the response is to retire the rule and keep the tests. Residual it does not close: the string-literal mutator replaces a string with `""` or filler and never **swaps** two names, so a clean run over these nine sites is not evidence that swapping `Column ruler` with `Row ruler` would be caught; that stays a hand-written membership test in `GridRuler.test.tsx`), and the acceptance-mutation Playwright config importing the e2e one (`no-playwright-config-import-in-mutation-config` — scoped by concrete path to the single root-level file `playwright.acceptance-mutation.config.ts`, `language: TypeScript` since that file is `.ts`. The matcher is `has: { field: source }`, **not** a regex over the statement's own text, and that is measured rather than stylistic: `export default defineConfig({ … })` is itself an `export_statement`, so a statement-text regex reads the comments inside that object literal — this config's body mentions `playwright.config.ts` in one, and the first form of this rule reported the whole 23-line default export as a violation. Verified on the real tree with a throwaway probe: zero findings clean, exactly one when the import is planted), and the two invariants the `features/screenplay/` decomposition rests on — a screenplay module importing the barrel back (`no-barrel-import-in-screenplay`, which is what keeps the layering underneath acyclic; ESM tolerates a cycle silently until an evaluation order puts a `const` in its temporal dead zone, and the failure then surfaces as `Cannot access 'CENTER' before initialization` from a module that never mentions `CENTER`) and `questions.ts` importing `expect` (`no-expect-in-screenplay-questions`, scoped to that one file on purpose — Playwright's retrying assertion is the sanctioned WAIT primitive and `interactions.ts` uses it as one, so a directory-wide "only expectations may assert" ban would report two correct functions and push the fix toward `page.waitForSelector`). Both were authored in that slice's DESIGN pass, ahead of the directory they scope, so each carried an `allow-unresolved-files` marker until the REVIEW pass deleted it — at which point each was live-probed against the real landed path (a planted `import { CENTER } from '../e2e-helpers'` in `viewport.ts`, and `expect` added to `questions.ts`'s existing `@playwright/test` import), one finding each and nothing else. That sequence is the standing bargain for authoring a rule ahead of its target: the fixture proves the matcher, the probe proves the `files:` glob, and the marker is what makes the debt visible in between (`npm run ast-grep:rules` reports it as stale the moment the glob resolves). Report-only like the four advisory `scripts/` programs above (but unlike `ast-grep:rules` and `agent-doc-check`, which gate) **for findings**: every rule is `severity: warning`, so a rule matching your code does not move the exit code -- read the output rather than `$?`. Promote one to a gate by changing it to `error`. The exit code is not meaningless though, it just answers a different question: measured against ast-grep 0.45.1, **8** means a rule file failed to parse and **1** means an `error`-severity rule matched, so a nonzero exit always warrants investigation.

Note which of these fire on ordinary feature work rather than only on structural change: the two `no-manual-memo` rules are unscoped by path, `no-logic-in-composition-root` covers exactly the kind of UI wiring a slice normally adds, and `no-unbraced-accessible-name` fires the moment a component grows a new `aria-label`, `role`, `title` or `aria-valuetext` — which is ordinary feature work, not restructuring. That's why `coder` runs `npm run ast-grep` in its own workflow rather than waiting for `architect` — see "Structural rules (ast-grep)" in `.claude/agents/articles/engineering.md` for the shared convention on reading a report-only checker, and note that rule files themselves belong to `architect` alone.

`.gherkin-lintrc` is an eighth checker, over `features/*.feature` rather than over TypeScript, and it **gates** (`npm run gherkin-lint`, nonzero on any finding) for `product`, the only role that runs it. Twenty-one of `gherkin-lint-plus`'s registered rules are on. Four facts about it that are easy to get wrong, all measured against the installed copy:

- **The package ships a `duplicate-state` rule file that is not in its registry** (`dist/rules/registry.js`), so naming it in the config aborts the run with `Rule "duplicate-state" does not exist`. The registered set is 31 rules, not the ~35 the `dist/rules/` listing suggests.
- **`name-length`'s and `max-scenarios-per-file`'s library defaults do not fit this repo** — at defaults they report 21 findings against features nobody considers wrong. The caps here are derived from Prettier's 120-char print width (a step line is indented 4 plus its keyword, leaving ~110 for the text; a scenario line is indented 2 plus `Scenario Outline: `, leaving ~100), not fitted to the current text. `max-scenarios-per-file` runs with `countOutlineExamples: false`, because the quantity this repo actually budgets — acceptance mutants — is measured exactly by `npm run acceptance-mutation` and a blunter proxy for it would only ever be tuned.
- **`no-restricted-patterns` compiles every pattern with `new RegExp(pattern, 'i')`, unconditionally.** Case is therefore not available as a signal: a camelCase-identifier detector like `\b[a-z][a-z0-9]*[A-Z]` matches every ordinary word and reported 184 findings when trialled. The list has to be an enumerated vocabulary, not a shape.
- It reads **feature/rule/background/scenario names and descriptions and step text**, and never Examples headers or cells. That is not a hole in practice, because `no-unused-variables` forces every header to appear in some step's `<placeholder>`; the two rules together reach the whole table.

**`no-restricted-patterns`' pattern list belongs to `architect`, in the same sense `rules/*.yml` does**, even though it lives in a config file `product` otherwise owns. It mechanises the domain-altitude judgment — implementation vocabulary must not leak into the contract — and its failure mode is someone widening the list to clear a finding, which is the same move as narrowing a fast-check arbitrary or weakening an ast-grep rule. A role that hits a pattern it believes is wrong routes it back to `architect` rather than editing the list. Each entry names a field, type, or function of a `src/` module (`offsetX`/`offsetY`, `cellSize`, `ScrollbarMetrics`' `thumbRatio`/`thumbOffsetRatio`, `ScrollbarMetrics` itself, `ContentBounds`, `VisibleRange`'s `minX`/`maxX`/`minY`/`maxY`, world-space coordinates, `cellKey`, and `should return`). Verbs are deliberately **not** restricted: `computed` reads as implementation but "the next generation is computed" is a statement about the game, and restricting it would drag the one already-converted feature into every prune's scope for no altitude gain. Neither is `live cells`, which is a type name (`LiveCells`) and simultaneously Conway's own ubiquitous language — the clearest example of why this list is enumerated by hand rather than derived.

**Every rule ships with a fixture in `rule-tests/` and `npm run ast-grep:test` must pass.** This is not ceremony. A malformed ast-grep rule matches nothing and reports nothing — it looks exactly like a clean codebase — and two of these rules were silently inert when first written (metavariables don't interpolate inside string literals, so an import path needs `kind:` + `regex:`; and a `matches:` util is bound to one language, so it never applied to the `.tsx` files the rule existed to check). A rule with no failing fixture has not been shown to work. Note also that TypeScript and TSX use different parsers, which is why `no-manual-memo-ts` and `-tsx` are near-duplicates by necessity rather than by oversight.

## Idea board

`ideas/` is a two-lane kanban of slices not yet started — one Markdown file per idea, and the lane is the directory:

- **`ideas/candidates/`** — raw and unjudged, no limit. An idea lands here the moment it's worth not forgetting.
- **`ideas/todo/`** — examined, and concrete enough to hand to `product`. The orchestrating session owns this board: no role reads it, and an idea reaches `product` as prompt content rather than as a file path. Keep this to about three, matching the two-or-three concurrent-slice ceiling below; a `todo/` lane longer than the number of slices you can actually run is a candidates lane wearing a different hat.

`ideas/TEMPLATE.md` is the file shape: frontmatter (`name`, `title`, `created`) over Context / Sketch / Touches / Open questions.

**There is deliberately no `doing/` or `done/` lane.** `git worktree list` already says what is in flight and `git tag -l 'slice/*'` already lists what is finished — a lane duplicating either is a second source of truth that can disagree with the first.

**`name` is the slice's identity end to end.** It matches the file's own basename, becomes the branch in `git worktree add -b <slice>`, and becomes the `slice/<name>` tag at merge. One slug from idea to tag, so `git log` and the board agree on what a thing is called.

Two rules keep the board honest:

- **Promote with a move-only commit, then edit.** Run `git mv ideas/candidates/<name>.md ideas/todo/<name>.md` and commit _that alone_, before fleshing the file out. Git infers renames from content similarity, and a candidate being expanded into a todo is precisely the case that defeats it: measured here, a move plus a substantial rewrite in one commit is recorded as delete-plus-add rather than a rename, and `git log --follow` then loses everything before the move — even at `-M10%`. Moved by itself the same change scores `R100` and the history survives. (`--follow` is required to read across the move either way; a plain `git log -- ideas/todo/<name>.md` starts at the promotion regardless.)
- **The slice deletes its own idea file.** `git rm ideas/todo/<name>.md` as part of the slice's work, so the deletion lands on the branch alongside the change it describes and the `slice/<name>` tag in merge-protocol step 6 marks a tree that no longer carries it. The tag is the permanent record and carries its own message; a file left behind becomes a third lane nobody maintains.

The lane-as-directory choice runs against the prevailing convention — [Backlog.md](https://github.com/MrLesk/Backlog.md), [MADR](https://adr.github.io/madr/), and most git-native trackers keep a `status:` field and never move the file, because moves conflict when several people edit one board. That objection doesn't reach this repo: slices land **serially** (see the merge protocol), and the board has a single editor. Since the directory _is_ the status, **don't also put a `status:` field in the frontmatter** — one fact, one home.

Nothing enforces any of this. `ideas/` has no gate, no checker, and no test; Prettier formats the Markdown (its ignore list is exclusion-based, so a new top-level path is covered with no config edit) and that is the extent of the tooling. A board-rendering script would have to live in `scripts/`, which would subject it to CRAP ≤ 6, its own vitest suite, `dry4ts`, and mutation testing — more machinery than the board is worth. `ls ideas/todo/` is the board.

## Subagent pipeline

`.claude/agents/` defines a five-role pipeline adapted from unclebob/swarm-forge's six-pack branch, scoped to this repo's actual commands (Gherkin features, `crap4ts`, `halstead4ts`, `dry4ts`, Stryker, `acceptance-mutation`, Playwright) rather than swarm-forge's tmux/file-based-handoff orchestration. (Worktrees are used, but per _slice_ rather than per _role_ — see "Running slices concurrently" below.) Each role's full instructions and boundaries live in its own file — read the relevant one before invoking it rather than relying on this summary. Shared house rules ported from swarm-forge's `main`-branch constitution live in `.claude/agents/articles/` (`engineering.md`, `workflow.md`, `handoffs.md`) — every role reads these too.

Cycle order for a feature: **product → coder → cleaner → architect → hardener → product** — `product` opens and closes every slice, in its SPECIFY and VERIFY modes respectively.

1. `product` (**SPECIFY** mode) — drafts/revises `features/*.feature` scenarios, the `features/steps/*.ts` step modules playwright-bdd compiles them against, and a plain-English end-to-end outline; runs the **acceptance spike** and `acceptance-mutation` scoped to the feature; stops for explicit user approval before handing off. Never writes `src/` or `scripts/`.
2. `coder` — implements one approved slice via TDD; never writes anything under `features/` and never runs the quality-gate tools.
3. `cleaner` — structure-preserving cleanup only (CRAP/DRY/scoped mutation scan on touched files); no new functionality. This is the four-pack's old `refactorer`, narrowed: it no longer runs a full mutation suite, only the scoped scan.
4. `architect` — **four modes: REVIEW, DESIGN, CONTRACT, ADJUDICATE.** In its normal slot it reviews module boundaries/dependency direction and property-test coverage, also reading `halstead4ts`'s Halstead report as an advisory (no-threshold) complexity signal alongside that review. Unlike the old four-pack architect, it does **not** run the full quality gate itself — that moved to `hardener`.
5. `hardener` — owns the full final verification sequence (`test:mutation` → `crap4ts` → `dry4ts`, in that order), fixing whatever each stage surfaces before moving to the next. It does **not** run `acceptance-mutation` — that belongs to `product`.
6. `product` (**VERIFY** mode) — builds and runs `features/*.e2e.spec.ts` (Playwright) from its own outline as the final independent, black-box check through the real UI, runs the full `acceptance-mutation`, and re-confirms `crap4ts`/`dry4ts` clean before declaring the feature done. It **reports** `src/` defects to `architect` rather than fixing them; `architect` rules on whether the code or the contract is wrong (its ADJUDICATE mode). See `.claude/agents/articles/handoffs.md`'s "Defect adjudication".

There's no daemon or persistent process wiring these together — the orchestrating session invokes each role in turn via the `Agent` tool and sequences the handoffs itself.

### The optional architect design pass

> `architect` has four modes. **DESIGN** ratifies an _implementation_ — a file set, interfaces, an ordering — and is what this section is about. **CONTRACT** ratifies a _specification_ during `product`'s acceptance spike: is the drafted contract observable through the UI at all, what accessible affordance does it need that doesn't exist, and is it at the right altitude for Gherkin. **ADJUDICATE** rules on a defect `product` reports at the end of the cycle. A slice may use several; contract review comes first, since there is no point planning an implementation for a contract that can't be verified.

`architect` may be invoked a **second time, before `coder`**, as a design pass that ratifies a file set and interface rather than reviewing landed code. It still runs in its normal post-`cleaner` slot afterward, so the slice gets both a design and a review — the two jobs compete for one pass otherwise, which is the same reasoning that split `hardener` out of the four-pack architect.

**The orchestrating session decides this, not `product`.** Every trigger below is a fact about the current shape of `src/`, and `product` is deliberately blind to it — it reads `src/` but never writes it, precisely so its reach stays honest. `product` may _flag_ that a slice smells structurally large; it doesn't make the call.

Reach for a design pass when:

- The slice is a refactor or restructure with no behavior change — then the design **is** the deliverable, and there's nothing for `coder` to TDD against without one.
- It will create new modules, or move/split existing ones.
- It crosses the framework-free module → hook → component layering.
- A target file is already flagged as oversized — `cleaner`'s 100+ mutant heuristic, or `coder`'s ~1s per-file test-duration budget.
- The change spans three or more existing modules.

A design pass writes **no product code**. Its output is a ratified file set, the interfaces between the new pieces, and an ordering of behavior-preserving steps each of which leaves the suite green — plus, where useful, a mechanical guard (an `ast-grep` rule and fixture) for an invariant the design depends on. `coder` then executes that ordering, usually in more than one invocation, with the existing test suite as the regression net at each step.

The `split-grid-render-props` slice is the worked example: the design pass corrected the prop shape before any code existed, split the riskiest step in two so the pre-existing tests could verify it, and authored `rules/no-logic-in-composition-root.yml` to keep the new composition root wiring-only.

**All five roles carry the `LSP` tool** in their frontmatter allowlist, giving them go-to-definition, find-references, and type errors reported in-turn rather than at the next `npm run build`. Every role writes TypeScript: the four implementing roles write `src/`/`scripts/`, and `product` writes the `features/steps/*.ts` step modules and the Playwright specs. What separates them is no longer the tool allowlist — it's the **write boundary**, stated in prose: `product` reads `src/` freely and writes nothing there or in `scripts/`, in either mode. That boundary used to be expressed by withholding `LSP` from `specifier`, which touched no TypeScript at all; after the merge that framing would be dishonest in both directions, since `product` writes real TypeScript and withholding a reading tool would only make its tests worse without narrowing its reach. This needs the `typescript-lsp` plugin installed (`/plugin`) plus a **global** `npm install -g typescript-language-server typescript`; the binary is not a project dependency, so `npm ci` alone does not reproduce it on a new machine. If the server is missing the roles silently fall back to `Grep`/`Read`, so a clean `npm test` is not evidence it's working — check `claude --debug`, which names any LSP server it skipped and why.

The file names in the Architecture section above are a current snapshot, not a frozen contract: `cleaner` and `architect` are expected to update that section (and fix any file-list mention elsewhere in these docs that a split makes stale) as part of performing a behavior-preserving split — see "Where guidance and file names live" in `.claude/agents/articles/engineering.md`.

## Running slices concurrently

Two or three slices can be worked at once: **one slice = one git worktree = one branch = one Claude Code session.** Every role in a cycle runs inside that slice's worktree and commits to that slice's branch; `main` is written to only by the merge protocol below, which the orchestrating session drives. The role-facing half of this lives in `.claude/agents/articles/workflow.md` ("Worktrees and branches") and `handoffs.md` ("Concurrent slices").

Isolation is what makes it safe. Each worktree gets its own `node_modules`, `coverage/`, `reports/` (including the Stryker incremental caches and `reports/perf/`), `test-results/`, `.stryker-tmp*`, `dist/`, and `dist-perf/` — all of which are fixed relative paths, so separate checkouts separate them for free. The one thing a worktree does **not** separate on its own is a TCP port, which is why `dev-port.ts` derives per-checkout ports — a dev-server port (5173+), a Vitest browser-API port (21000+), and a `vite preview` port (41000+, used by `playwright.perf.config.ts`), three disjoint ranges: the primary checkout keeps 5173, each linked worktree hashes its own directory to its own slot, and `vite.config.ts` sets `strictPort` on both the dev server and the preview server. Without that, `playwright.config.ts`'s `reuseExistingServer` finds another worktree's server answering on 5173, attaches, and reports a green e2e suite against the wrong build.

### Setting up a slice

```bash
git worktree add ../gol-claude-worktrees/<slice> -b <slice> main    # or .claude/worktrees/<slice>
cd ../gol-claude-worktrees/<slice> && npm ci
```

Then start a session there, or `EnterWorktree({ path: '../gol-claude-worktrees/<slice>' })`. Both locations work and both are ignored by git, Prettier, oxlint, and vitest. `npx playwright install chromium` is **not** needed — that binary lives in a machine-global cache.

If you use the native `EnterWorktree({ name })` or `Agent({ isolation: 'worktree' })` path, set `"worktree": { "baseRef": "head" }` in `.claude/settings.json`: the default `fresh` branches from `origin/<default-branch>`, which is stale unless `main` is pushed after every merge.

### Merge protocol

**Slices land one at a time, serially.** Parallelism buys concurrent _authoring_, not concurrent _landing_ — the second slice to land pays a full re-verification. That cost is why two or three is the sensible ceiling.

1. **Rebase, don't merge.** In the slice's worktree: `git fetch && git rebase main`. This keeps `main` linear, which is what `workflow.md`'s "a prior role's commit" ordinal reasoning assumes, and keeps each slice's `By <role>.` chain readable in order.
2. **The slice's own session resolves its own conflicts**, in its own worktree — it has the context the orchestrator doesn't. `main` never enters a conflicted state.
3. **Re-run the gate on the rebased branch, still in the worktree.** Invoke `hardener` again. It must use `npm run test:mutation:full`, because the rebase brought in another slice's moved and renamed files — exactly the file-level assumption the incremental cache can't survive — **unless the merge is mutation-invariant, in which case stage 4 does not run at all; see the clause under step 5, and evaluate its predicate here, at this step.** Pay attention to `npm run ast-grep:rules` here specifically: it's the gate most likely to have been broken by the _other_ slice's renames invalidating a `files:` glob, and post-rebase that breakage is legitimately yours.
4. **Fast-forward `main`:** `git checkout main && git merge --ff-only <slice>` from the primary checkout. `--ff-only` is the assertion that step 1 actually happened.
5. **Run the full gate on `main`.** Mandatory, even though step 3 just passed on an identical tree — step 3 ran against a different Stryker cache and a different `coverage/`. This run is what rebuilds `main`'s own caches into a state the next merge can trust — **unless this is a mutation-invariant merge, in which case skip this deletion entirely; read the clause below before running it**:

   ```bash
   rm -f reports/stryker-incremental.json reports/stryker-incremental-scripts.json
   ```

   then invoke `hardener` on `main` with the whole tree as its scope. Deleting the caches is the honest expression of intent: they aren't stale, they're describing a tree that no longer exists — the situation the mutation-testing note in Commands already names.

   **Mutation-invariant merges — the one exemption, and it is stage 4 only.** Steps 3 and 5 both mandate `npm run test:mutation:full`, and for some diffs that is two full runs measuring a quantity that provably did not move. `stryker.config.json`'s `mutate` list covers only `src/**`, and its `ignorePatterns` keeps `features/` out of the sandbox entirely, so for a diff confined to the paths below neither a mutant nor a test that could kill one is reachable. Left unaddressed this is not merely a cost — it is a standing incentive to bundle unrelated features into one slice to pay the bill once, which is the opposite of what the serial-landing rule is for.

   **The predicate is an allowlist of paths that cannot move the score, not a list of the paths that can.** That direction is the whole design: a blocklist fails **open** — a path nobody thought to list silently skips the mutation gate, and a skipped run reads exactly like a passing one — which is the same dangerous direction as the `ignorePatterns` glob that matches nothing, already described in the Commands section. An allowlist fails safe: an unanticipated path simply runs the gate.

   **The predicate is a single path check.** Evaluated over the landing diff:

   ```bash
   git diff --name-only main...HEAD    # in the slice's worktree, after step 1's rebase

   # every path matches one of:  features/**  ideas/**  .claude/**  CLAUDE.md  README.md
   ```

   **Every entry on that allowlist is structurally safe, and two of them became so only in the `shared-exclude-covers-docs-dirs` slice.** `features/**` is unreachable because `stryker.config.json`'s `ignorePatterns` keeps it out of the sandbox; `CLAUDE.md` and `README.md` because a fixed filename cannot match a test glob; `ideas/**` and `.claude/**` because `vite.config.ts`'s `sharedExclude` now names both directories, so a test file placed in either is collected by no vitest project and can therefore kill nothing. Note what secures each: the two filenames are safe as a matter of fact, the other three as a matter of configuration — and **those three config entries are load-bearing for this exemption specifically**, not just for a tidy test run. Deleting `sharedExclude`'s `'ideas/**'` or `'.claude/**'` re-opens the hole described next, and the predicate would have to grow its second conjunct back; `vite.config.ts`'s comment on those two entries says the same thing from the other side. Deleting `ignorePatterns`' `/features` breaks the allowlist a different way — no conjunct would help, because the Gherkin layer would simply be back in the sandbox — and that failure is silent and moves the score _up_, which is why the Commands section warns about it separately.

   **The hole those two entries closed, for the record — it is this clause's soundness argument, not decoration.** `vite.config.ts`'s `unit` project inherits the **unrooted** `**/*.{test,spec}.?(c|m)[jt]s?(x)` include, and until that slice `sharedExclude` covered `scripts/**` and `.claude/worktrees/**` but neither `ideas/` nor `.claude/` as a whole. Measured twice with throwaway probes, `npx vitest list` collected `[unit] .claude/__probe.test.ts` **and** `[unit] ideas/__probe.test.ts` — and the second imported `src/gameOfLife`, so it would have run inside Stryker's sandbox and changed mutant fates while the path check still answered "invariant". The predicate therefore carried a second conjunct — the diff must name no `*.test.*`/`*.spec.*` path under either directory — from the pass that found the hole until the pass that cured it. **That conjunct is retired.** The invariant now lives in `sharedExclude`, where a config entry holds it rather than a per-merge grep nobody can be relied on to run.

   **Making a path structurally safe is a precondition for putting it on the allowlist, not a follow-up.** The unrooted include reaches every directory in the checkout that `sharedExclude` doesn't name, and measurably still does: probes dropped into `perf/`, `rules/`, `rule-tests/`, `patches/` and `public/` are all collected into `unit` on the landed tree (66 files against the usual 61). None of those five is on the allowlist, which is exactly why they need no exclusion — a diff touching one fails the path check and the gate runs — and exactly why adding any of them to the allowlist would first mean excluding it from vitest.

   **Gitignored paths cannot reach this predicate at all**, which is a different fact from being excluded from vitest, and it is why `.stryker-tmp*/**` and `.features-gen/**` need `sharedExclude` entries yet want no allowlist entry: they never appear in `git diff --name-only main...HEAD`. (A `git add -f` would put one there — at which point it is tracked, fails the allowlist, and the gate runs. Fails safe.) Don't invert that into "gitignored, therefore safe from collection": those two entries exist precisely because it isn't.

   `stryker.config.json` is deliberately **absent** from the allowlist, as are `vite.config.ts`, `vitest.*.config.ts`, `package.json`/`package-lock.json`, `tsconfig*.json` and `patches/**` — touching any of them re-arms the full run, which is the point of leaving them out rather than an oversight.

   **Every other stage still runs — but re-derive which of them can actually move, because the old argument here died with the `acceptance` project.** That argument was that `npm run test:coverage` ran four projects, the `acceptance` one mounted `<App />`, and its coverage landed on `src/`, so `crap4ts` genuinely moved on a `features/`-only diff. `delete-step-test-layer` removed that project, and **measured on the landed tree, `coverage/coverage-final.json` now contains zero `features/` entries** — no vitest project loads anything in that directory, so a `features/`-only diff moves neither `crap4ts` nor `dry4ts` (which scores `src` alone). What still moves on such a diff is **`npm run build`** — `tsconfig.app.json`'s `include` is `["src", "features", "perf"]`, so a type error there fails stage 1 — and, for the `.claude/**`/`CLAUDE.md` entries, **`npm run agent-doc-check`**. Note this does not weaken the exemption: the predicate is an allowlist of paths that cannot move the **mutation score**, and that is more clearly true now, not less. It does mean the honest claim is narrower than it used to be — this exempts one stage from one run, and the stages that remain are fewer than the sentence this replaces implied. It is still not a fast path through the gate.

   **Compute the predicate once, in step 3's worktree after the rebase, and carry the answer to step 5.** Step 4 is a fast-forward, so the tree step 5 gates is byte-identical to the one step 3 gated — there is no second diff worth taking, and reconstructing one from `main`'s reflog is a worse way to ask the same question.

   **When stage 4 is skipped, step 5 does not delete the incremental caches.** The `rm -f` above exists because the caches describe a tree that no longer exists; under this predicate **no mutated file and no collected test differs** from the one they were built from. State it that way and not as "the tree Stryker sees is byte-identical", which is literally false and false in the dangerous direction: `ideas/`, `.claude/` and `CLAUDE.md` are tracked and _are_ copied into the sandbox — only `/features` is ignored — so a reader who checks the stronger claim, finds it false, and reasons "well, these are in the sandbox too" would extend the allowlist by exactly the wrong logic. Deleting the caches would tax the next merge with a full cold run in exchange for nothing, which answers step 5's own "different cache" justification on its own terms rather than waiving it.

   **`hardener` may refuse an exemption; it may never grant itself one.** The rule is deliberately asymmetric, because the two errors are: wrongly granting is silent and permanent, wrongly refusing costs one mutation run. So the predicate is evaluated by the orchestrating session and handed to `hardener` in the invoking prompt, naming the diff it was computed over — absent that instruction `hardener` runs stage 4, full stop — but `hardener` **may** check the handed-down claim against `git diff --name-only` and **must** run stage 4 anyway if it can falsify it. A verification that comes back "invariant" grants nothing on its own; only the instruction does. That is the narrower prohibition the safety argument actually justifies: a role that can excuse itself from its own gate is not a gate, which says nothing about a role that can decline an excuse.

   **Record every skip, and know which option was not taken.** A skipped stage produces no artifact, which is the same property that makes wrongly granting an exemption dangerous — so `hardener`'s handoff must name the skip, the instruction it was handed, and the diff that instruction covered, and this merge carries that forward. A written record is not a score, but it makes a skip distinguishable from a pass, which was the actual gap. **The middle option was considered and is not what this clause does**: since the cache is retained here by design, a plain `npm run test:mutation` would cost roughly the `@fast-check/vitest` floor and still produce a real score — most of the saving _plus_ the missing evidence. It is not adopted yet for one unmeasured reason, and the reason is specific to step 3: that branch was **just rebased onto a `main` that moved**, so the worktree's cache is stale with respect to everything the rebase brought in, which is the protocol's own stated reason for mandating `:full` there. The floor figure is measured for a warm cache on an unchanged tree and has never been measured for that case. The argument is much stronger at step 5, where `main`'s own cache differs from the tree by exactly the invariant diff — so the middle option is really a step-5 proposal, and since it changes what the gate measures it is a slice of its own rather than a paragraph here.

   **The exemption is self-revoking.** If `hardener`'s own remediation at any stage writes a file outside the allowlist, the exemption is void from that point and stage 4 runs. This is not hypothetical and it is the exemption's most likely failure: stage 4 is skipped, stage 5 then legitimately moves (see the paragraph above), and `hardener`'s standing duty is to close a coverage shortfall with a test under `src/` — which adds a file Stryker mutates, _after_ the stage that would have measured it was skipped. Written as a self-revocation rather than as a caveat because it then resolves safely for a careless reader: the skip instruction is the more specific and more recent one, so anything phrased as an exception to it loses. See `.claude/agents/hardener.md`'s stage 4.

6. **Tag the slice's final commit**, annotated, as `slice/<slice-name>`:

   ```bash
   git tag -a slice/<slice> -m "<slice>: <one line on what the slice delivered>"
   ```

   After the fast-forward in step 4 the slice's tip _is_ `main`'s tip, so this marks both. Tag after step 5 rather than before it: the tag says the slice is done, and it isn't done until the gate on `main` passes. The `slice/` prefix is load-bearing — a bare tag sharing the slice branch's name makes every `git log <name>` ambiguous until the branch is deleted in step 9 — and it makes `git tag -l 'slice/*'` a list of every completed slice. Annotated rather than lightweight, so the tag carries its own date and message. If the slice began as an entry on the idea board, its `ideas/todo/<slice>.md` is already gone by now — the slice deletes its own idea file as part of its work (see "Idea board" above), and this tag is what carries the record forward in its place.

7. **Push `main` and the tag:** `git push --follow-tags` (plain `git push` leaves the tag behind).

   This repo sets `push.followTags = true` locally, so a plain `git push` already carries the tag — but the flag stays written out here because `.git/config` isn't tracked, so a fresh clone or a CI checkout won't have the setting. Note the setting only follows **annotated** tags reachable from what you're pushing; a lightweight tag is silently left behind, which is one more reason step 6 specifies `git tag -a`.

8. **Carry the acceptance-mutation figure forward** from `product`'s VERIFY handoff — it comes from there now rather than from `hardener`'s. This is a read, not an edit: `engineering.md` deliberately records **no literal**, and says why in the same breath ("a literal in this file is wrong the moment the second one lands"), so there is nothing in that file to re-record. What the step is actually for is noticing when the figure moved and whether the slice explains it — a slice that touched no `.feature` and no `features/steps/*.ts` leaves the Examples-table mutant surface byte-identical, so a moved figure wants an explanation before it is accepted. (Those are the two inputs since `acceptance-mutation-on-playwright`; `*.steps.test.*` was the second one before it, and the runner no longer touches that layer at all.) Note the surface being identical does not by itself guarantee identical kill outcomes — a `src/` change to a module the steps exercise can flip a mutant's fate while the unmutated baseline stays green — which is exactly why a move is a finding to understand rather than a new baseline to record.
9. **Retire the worktree:**

   ```bash
   git worktree remove <path>
   git merge-base --is-ancestor <slice> main && git branch -D <slice>
   git worktree prune
   ```

   Assert the ancestry yourself rather than leaning on `git branch -d`. `-d`'s built-in "fully merged" test measures against whatever branch is currently checked out — and under concurrency the primary checkout is normally sitting on some _other_ slice's branch, so `-d` refuses a slice that is in fact already `main`. (Safe, but it stops you every time.) The check above asserts the condition you actually care about, and `-D` can't do damage because it only runs once that assertion has passed. The tag is what preserves the slice's identity once the branch is gone.

The next slice repeats from step 1 against the new `main`.

**`npm run test:perf` is owned by the orchestrating session, not by any role.** It appears in no role's checklist deliberately: render performance is meant to be held by the architecture — the world-anchored tile keys, the eviction hysteresis — rather than re-measured on every slice, and a per-slice harness stage would quietly recast an architectural guarantee as a test result. So the orchestrator decides when a slice is perf-relevant, runs `npm run test:perf` **followed by** `npm run perf-report` (skipping the second leaves the previous run's `reports/perf/latest.md` in place, reading as a successful run of the current tree), and regenerates the `main` baseline first whenever `src/` or `perf/` has moved since that report's own commit — check it, the report names the commit it was generated from. A role may _recommend_ a run in its handoff, which is a useful signal; no role runs it.

There is deliberately no seventh role for this. The post-merge gate is `hardener`, invoked on `main` and told that it is verifying an integration rather than a slice, so the whole tree is in scope — it already owns exactly that sequence and already knows when to reach for `test:mutation:full`.

## Conventions

- No semicolons, single quotes, 120-char print width (Prettier; `prettier-plugin-tailwindcss` sorts class strings — don't hand-order Tailwind classes).
- Comments are reserved for non-obvious _why_ (subtle invariants, browser quirks, sign-convention mismatches between related functions). This codebase leans heavily on that style in `camera.ts`/`scrollbars.ts` and `Grid.tsx` — read existing comments fully before touching the code they explain, since the reasoning (e.g. pointer-capture propagation, scroll-direction sign conventions, shift+wheel axis workarounds) is often not re-derivable from the code alone.
- React Compiler is enabled (`babel-plugin-react-compiler` in `vite.config.ts`, `react/react-compiler` oxlint rule set to `error`) — avoid manual `useMemo`/`useCallback` unless the compiler can't handle the case.
- **Accessible names are sentence case** — capital on the first word only, and no role word inside the name (AT appends "group", "button" itself). Every name this app ships follows it: `Cell 3, 5`, `Zoom in`, `Zoom out`, `Reset view`, `Open pattern library`, `Pattern library`, `Pattern preview cell 3, 5`, `Horizontal scroll`, `Vertical scroll`, `Column ruler`, `Row ruler`.
- **An accessible name says what a thing _means_, not what shape it is — and the `Scrollbar.tsx` / `GridRuler.tsx` mismatch is deliberate, not drift to tidy up.** `Scrollbar.tsx` names its axes `Horizontal scroll`/`Vertical scroll`; `GridRuler.tsx` names its two axis groups `Column ruler`/`Row ruler`, and `Horizontal ruler`/`Vertical ruler` was rejected on the record. Scrolling is a _geometric action_ — you genuinely scroll horizontally — so geometry is the right vocabulary and there is no coordinate meaning to lose. Ruler digits _are_ coordinates: "Horizontal ruler: 0, 10, 20" is mapping-neutral and tells a user nothing about whether `10` is the first or the second coordinate of `Cell 10, 5`, whereas `Column ruler` says exactly that. The mapping, which is the one failure mode that leaves every test green while being confidently wrong: **top strip = `Column ruler` = the first coordinate of `Cell x, y`; left strip = `Row ruler` = the second** — note the top strip is itself a _horizontal_ run of labels carrying _column_ numbers, so naming a strip after its own geometry is precisely the inversion to avoid. `GridRuler.test.tsx`'s membership test is what pins it (asserting the two names exist is not enough — that passes with the wrappers swapped), and `rules/no-ruler-axis-by-paint-class*.yml` keeps the black-box layers reading the group rather than the edge class.
